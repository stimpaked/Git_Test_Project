### DL-35-001 · 35번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-10
- **대상:** `conversions/35_워크스루_리뷰_conversion.md`, `templates/35_워크스루_리뷰_template.md`, `guides/35_워크스루_리뷰_guide.md` (그룹 J의 34·36번과 병렬로 만든 복제)
- **결정 주체:** 사용자 승인 (그룹 단위 진행을 승인함(DL-05-005))
- **배경:** 샘플 해부 55행(SA-01~55)과 누락 탐색 28행(OM-01~28)을 같은 절차로 만들었다. 단계 정의의 목적은 시나리오 전체를 따라가는 확인과 역할별 리뷰로 표 중심의 검사가 놓친 누락을 찾는 것이고 산출물은 워크스루 결과, 역할별 리뷰 의견, 신규 발견 수, 기능 목록 v1.0 후보다. 샘플은 사람이 하는 활동(테스트 참가자, 역할 의견, 서명)의 결과를 모두 `(가상)`으로 채웠고(SA-08, SA-24, SA-48), 워크스루는 정상 경로 위주이며(OM-02), 발견 유형이 셋뿐이고(OM-06), 종료 조건이 뒤 단계의 일을 조건으로 둔다(SA-45, SA-46). 도메인 교체 시험은 작업 순서 6단계에서 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 04·05번처럼 도출 질문 → 후보 → 판정 → 목록의 구성으로 하는 안, 29·30번처럼 외부 기준의 항목을 한 행씩 판정하는 안, 샘플의 구성(검증 방법, 워크스루, 인스펙션, 프로토타입, 발견, 라운드, 종료 조건, 산출물)을 그대로 따르는 안, 세 방법의 결과 표 → 발견 → 라운드 → 종료 판정 → 집계의 구성으로 하는 안을 비교했다. 이 단계는 후보를 찾는 단계도 외부 기준을 맞대는 단계도 아니어서 앞의 두 안은 버렸다. 샘플 구성은 방법을 고르는 표와 작성 결과를 보여 주는 표(분포, 서명 예시)를 값으로 담아 버렸다.
- **결정:** 값 표 일곱을 둔다. 워크스루(목록 표, 정의 ID `WK`), 역할검토(목록 표, `WR`), 프로토타입(목록 표, `WP`), 발견(목록 표, `WF`), 라운드(목록 표, 정의 ID 없음), 종료조건(속성 표, 없음, 항목 6행), 집계(속성 표, 없음, 22행). 필드는 모두 77개다. 선택 블록과 표 없는 절은 없다. 표 키는 그룹 J의 약속(`워크스루`, `역할검토`, `프로토타입`, `발견`, `라운드`, `종료조건`, `집계`)을 그대로 따랐고 정의 ID 접두어도 약속의 `WK`, `WR`, `WP`, `WF`를 썼다(TP-28에 맞게 기존 `WA`, `WQ`, `WT`, `WD`와 겹치지 않는다). 절 제목은 작성 순서(따라가고, 역할이 보고, 사용자가 쓰고, 발견을 모으고, 라운드를 세고, 종료를 판정하고, 센다)를 따른다.
- **이유:** 템플릿의 모든 표와 필드가 분석서의 줄에 대응한다(정의서 6절 4번, CV-K04). 방법마다 표를 두면 사람이 하는 활동의 결과(역할검토, 프로토타입)와 에이전트가 하는 일(워크스루)이 칸 단위로 갈려 값이 없을 때 `미정`으로 닫을 수 있다. 발견을 하나의 표로 모으면 세 방법의 환류가 같은 칸으로 간다.
- **영향:** 도메인 교체 시험(작업 순서 6단계)이 남았다. 인터페이스 표는 DL-35-009~011에 쓴다.
- **상태:** 유효

### DL-35-002 · 단계 정의에 없는 프로토타입 테스트를 사용자가 확정한 설계에 따라 둔다
- **날짜:** 2026-10-10
- **대상:** `templates/35_워크스루_리뷰_template.md` 표 `프로토타입`, `docs/단계_정의.md` (참고)
- **결정 주체:** 유지보수자 판단
- **배경:** 단계 정의의 35번 목적은 시나리오 전체를 따라가는 확인과 역할별 리뷰이고 산출물은 워크스루 결과, 역할별 리뷰 의견, 신규 발견 수, 기능 목록 v1.0 후보다. 프로토타입 테스트는 산출물에 없다. 샘플은 세 방법의 하나로 두고(SA-13), 사용자가 확정한 그룹 J의 약속은 `프로토타입` 표(접두어 `WP`)를 정했다.
- **검토한 대안:** (a) 단계 정의에 없으므로 표를 빼고 워크스루와 역할 검토만 둔다 / (b) 약속대로 프로토타입 표를 둔다
- **결정:** (b). 표를 두되 프로토타입을 만들지 않거나 만들 수 없는 프로젝트를 위해 입력이 하지 않기로 한 결정을 보여 줄 때 표를 한 줄 `해당 없음`(사유)으로 닫는 법을 가이드에 두었다(OM-12, OM-23, OM-28).
- **이유:** 사용자가 정한 설계를 따른다. 단계 정의의 산출물 설명을 고치는 것은 이 세트의 일이 아니다.
- **영향:** 단계 정의의 35번 산출물에 프로토타입 테스트 결과를 더할지는 사용자 결정이다. 더하면 단계 정의 버전을 올리고 문서 정보 블록이 바뀐다.
- **상태:** 검토 대기

### DL-35-003 · 사람이 하는 활동은 외부 입력으로 받고 없으면 `미정`으로 닫는다
- **날짜:** 2026-10-10
- **대상:** `templates/35_워크스루_리뷰_template.md` 표 `역할검토`(의견, 검토자, 결과, 일자), 표 `프로토타입`, 표 `종료조건`, `guides/35_워크스루_리뷰_guide.md` 3.2, 3.3, 3.6, 5절, `tools/data/interfaces.csv` (IF-EX-35-001~009)
- **결정 주체:** 유지보수자 판단
- **배경:** 사용자가 확정한 설계(쟁점 1)는 프로토타입 테스트의 결과, 역할별 검토 의견과 서명을 에이전트가 지어내지 않고 입력으로 받게 한다. 샘플의 해당 값은 모두 가상이다(SA-08, SA-24, SA-48, OM-03).
- **검토한 대안:** (a) 에이전트가 역할의 관점으로 의견을 쓰고 서명은 비워 둔다 / (b) 템플릿은 결과를 기록하는 칸만 두고 값이 없으면 `미정`으로 닫으며 사람이 주는 자료를 외부 입력 줄로 둔다
- **결정:** (b). 외부 입력은 `EXT:프로토타입_테스트_기록`(과제, 참가자 수, 완료 수, 찾지 못한 것, 기대했으나 없던 것 다섯 줄), `EXT:역할별_검토_의견`(의견 한 줄), `EXT:역할별_서명_기록`(검토자, 결과, 일자 세 줄)이고 연결 ID는 `IF-EX-35-001~009`다. 필수는 모두 `아니오`다(없으면 `미정`으로 닫고 진행한다). 기록이 없으면 프로토타입은 ID와 라운드만 쓰고 나머지를 `미정`으로 한 줄에 닫으며, 이 기록이 필요한 종료 조건과 종료 판정도 `미정`(충족 미정)이다. 프로토타입을 만들지 않기로 한 결정을 입력이 보여 주면 프로토타입 표를 한 줄 `해당 없음`(사유)으로 닫는다(OM-12, OM-23).
- **이유:** (a)는 가상 의견을 산출물에 섞고 서명 칸이 서명이 아닌 것을 담는다. 역할과 검토 범위는 에이전트가 앞 단계 산출물에서 정할 수 있어 칸으로 남겼고 사람이 아니면 알 수 없는 값만 외부 입력으로 뺐다. 입력이 얇을 때 `미정`이 많은 것은 구조의 결함이 아니다.
- **영향:** 외부 입력 이름은 사용자가 정한 이름이 아니라 이 세트가 붙인 이름이므로 확인이 필요하다. 사람이 주는 자료의 형식(검토 기록 양식, 테스트 기록 양식)은 이 체계가 정하지 않는다.
- **상태:** 검토 대기

### DL-35-004 · 워크스루 표는 시나리오 한 번의 수행을 한 행으로 쓰고 단계 문장은 두지 않는다
- **날짜:** 2026-10-10
- **대상:** `templates/35_워크스루_리뷰_template.md` 표 `워크스루`, `guides/35_워크스루_리뷰_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 시나리오마다 제목(인물, 인물 ID, 이름)과 단계 표(번호, 단계 문장, 사용하는 기능)를 둔다(SA-15, SA-16). 단계가 지난 플로우와 화면은 적지 않는다(OM-01). 시나리오는 하루가 아닐 수 있고 대상이 둘이거나 비사람일 수 있다(OM-24, OM-26, OM-27). 라운드마다 같은 시나리오를 다시 수행한다(OM-14).
- **검토한 대안:** (a) 샘플처럼 시나리오 표와 단계 표를 따로 둔다 / (b) 단계마다 한 행으로 쓰고 시나리오 이름을 행마다 되풀이한다 / (c) 시나리오 수행 한 번을 한 행으로 쓰고 따라간 기능과 화면을 순서대로 나열한다
- **결정:** (c). 열은 ID, 라운드, 시나리오, 대상 액터, 플로우, 따라간 기능, 화면, 비정상 경로 포함, 결과, 근거다. 단계 문장은 두지 않고 따라간 기능과 화면의 나열 순서가 단계의 순서를 보여 준다. 끊김은 `결과`로 닫고 어디서 끊겼는지는 발견 표가 이 행을 출처로 가리켜 쓴다.
- **이유:** (a)는 표가 하나 더 늘고 단계마다 같은 칸(근거, 라운드)을 되풀이해 닫아야 한다. (b)는 시나리오 이름이 행마다 되풀이되고 라운드 표가 수행을 시나리오 단위로 맞댈 수 없다. (c)는 라운드 표의 수행이 행 ID로 맞고 시나리오가 닿은 기능을 집계로 센다. 단계 문장은 사람이 읽는 해설이어서 뒤 단계가 쓰지 않고 따라간 기능과 발견이 같은 정보를 더 정확히 갖는다. 대가는 시나리오 안에서 어느 단계가 끊겼는지가 행에는 없고 발견의 서술에만 있다는 점이다.
- **영향:** 단계 단위 검사(끊긴 단계 수 등)는 하지 못한다. 단계 문장을 되살리려면 목록 표를 하나 더하고 템플릿 버전을 올린다. 사용자 확인이 필요하다.
- **상태:** 검토 대기

### DL-35-005 · 역할검토·프로토타입에도 라운드 열을 두고 서명은 마지막 라운드의 행으로 판정한다
- **날짜:** 2026-10-10
- **대상:** `templates/35_워크스루_리뷰_template.md` 표 `역할검토`, `프로토타입`, `워크스루`, `라운드`의 라운드 열, `집계`의 역할 결과 수
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 라운드 2와 3은 워크스루, 인스펙션, 프로토타입을 다시 수행하는데 워크스루와 인스펙션 표에는 라운드가 없다(OM-14, SA-20). 서명은 한 번에 한꺼번에 받은 것으로 되어 있다(SA-47).
- **검토한 대안:** (a) 역할당 한 행으로 쓰고 라운드를 두지 않는다 / (b) 세 표 모두 라운드 열을 두고 역할의 한 번의 검토를 한 행으로 쓴다
- **결정:** (b). 같은 역할이 다시 검토하면 라운드를 올려 새 행을 쓰고 서명은 역할마다 마지막 라운드의 행으로 판정한다. 집계는 서로 다른 역할의 수와 역할마다 마지막 행의 결과 수 넷(승인, 조건부 승인, 반려, 서명 미정)을 센다.
- **이유:** (a)는 의견이 여러 라운드에 걸쳐 바뀌는 이력과 마지막 서명을 한 행에 섞는다. 라운드 표의 수행 칸이 세 표의 행 ID로 맞으려면 세 표가 같은 라운드 열을 가져야 한다.
- **영향:** 역할이 라운드마다 새 행을 쓰므로 표가 길어진다. 사용자가 한 번의 서명만 받는 프로젝트에서는 라운드 열이 모두 같은 값이 된다.
- **상태:** 검토 대기

### DL-35-006 · 발견의 조치 유형을 역추적 검증의 어휘에 맞추고 반영 상태와 환류 대상을 둔다
- **날짜:** 2026-10-10
- **대상:** `templates/35_워크스루_리뷰_template.md` 표 `발견`(조치 유형, 대상 기능, 조치, 환류 대상, 반영 상태), `guides/35_워크스루_리뷰_guide.md` 3.4
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 발견 유형은 신규 기능, 기존 기능 보강, 변경 없음(확인) 셋이고 조치 칸에 기능 ID, 이름, 조치, 다른 단계의 ID가 섞인다(SA-32, SA-33, OM-05, OM-06, OM-07). 그룹 J의 약속은 역추적 검증의 갭 로그가 조치 유형(기능 추가 / 태그 수정 / 기능 삭제 / 의도적 제외 / 상류 단계 환류)을 쓴다고 정했다. 기능 계층·ID·태그 단계가 이미 34·35번의 환류를 기능 ID, 기능명, 설명, 근거 ID, 태그, 결번으로 받겠다고 목록을 남겼다(DL-32-010).
- **검토한 대안:** (a) 샘플의 셋을 그대로 쓴다 / (b) 역추적 검증의 어휘 네 값에 `기존 기능 보강`과 `변경 없음`을 더해 여섯으로 쓴다 / (c) 의도적 제외까지 더한다
- **결정:** (b). 선택지는 기능 추가 / 기존 기능 보강 / 태그 수정 / 기능 삭제 / 상류 단계 환류 / 변경 없음이다. `의도적 제외`는 두지 않는다. 범위·제약의 제외·후속 목록이 이미 정한 것이면 `변경 없음`이고, 범위 밖으로 보이는 새 제안은 기능 추가로 올리지 않고 `상류 단계 환류`로 쓰고 사용자에게 알린다. 대상 기능은 기능 ID 하나이고 기능 추가는 새 ID를 기능 트리가 붙이므로 반영 전에는 `미정`이다. 반영 상태(반영함 / 반영 대기)는 환류가 받는 산출물에 반영되고 버전이 올랐는지다. 환류 대상은 앞 단계의 번호와 이름이다. `기존 기능 보강`의 수용 조건은 이 체계 밖의 명세 단계가 받으므로 설명을 고치지 않는 보강은 환류 대상을 `해당 없음`(사유)으로 닫는다.
- **이유:** (a)는 삭제와 태그 수정, 앞 단계 산출물의 문제를 담지 못한다. 같은 값을 두 단계가 다른 어휘로 쓰지 않는다는 교훈에 따라 역추적 검증과 어휘를 맞췄다(`신규 기능`을 `기능 추가`로). (c)는 범위를 정하는 일이 사람의 몫인 이 단계에서 에이전트가 제외를 정하게 된다. 역추적 검증의 템플릿이 이 복사본에 없어 어휘는 약속을 가정한 것이다.
