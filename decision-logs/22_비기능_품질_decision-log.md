### DL-22-001 · 22번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-09
- **대상:** `conversions/22_비기능_품질_conversion.md`, `templates/22_비기능_품질_template.md`, `guides/22_비기능_품질_guide.md` (작업 순서 6단계, 그룹 F 병렬 작성)
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 샘플 해부 29행(SA-01~29)과 누락 탐색 20행(OM-01~20)을 앞 단계와 같은 절차로 만들었다. 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 구성(도출 질문 → 후보 → 판정 → 목록)을 따르지 않고 이 단계의 목적(품질 요구를 측정 가능하게 정하고 기능으로 만들어야 하는 항목을 가려낸다)에 맞춰 값 표를 셋으로 둔다. 1번 표 `요구목록`은 요구 하나(지표 하나)를 행 하나로 하는 목록(정의 ID `QN`), 2번 표 `특성점검`은 품질 특성마다 요구가 있는지 닫는 고정 질문 열세 개(정의 ID `QK`, 속성 표), 3번 표 `기능후보`는 승격·설계 요구에서 도출한 후보(정의 ID `QC`)다(SA-10, SA-19, SA-20, OM-01, OM-06). 그림이나 표 없는 필수 블록, 선택 블록은 없다.
- **이유:** 이 단계의 본질은 품질 요구를 지표·목표값·측정 방법으로 측정 가능하게 정하고 처리(승격·기준·설계)를 가르는 것이다. 후보는 승격과 설계 줄에서만 나온다. 템플릿의 모든 변경이 분석서의 줄에 대응한다(정의서 6절 4번).
- **영향:** 도메인 교체 시험(8번)이 남았다. 인터페이스 표에 22번 보내는 줄 36개와 외부 입력 줄 3개를 더하고 잠정 줄 24개를 바꿨다(DL-22-004).
- **상태:** 검토 대기

### DL-22-002 · 요구 목록은 지표 하나를 행 하나로 두고 측정 가능성을 열로 나눈다
- **날짜:** 2026-10-09
- **대상:** `templates/22_비기능_품질_template.md` 1절 (필드 `대상`, `요구`, `지표`, `목표값`, `측정 방법`, `원천`), `guides/22_비기능_품질_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 요구를 한 칸에 문장·측정량·값·조건을 섞어 쓰고(SA-14), 근거 칸에 입력의 ID, 가정, 빈 칸 대용 `—`가 섞인다(SA-16). 복구 시점과 복구 시간처럼 지표가 둘인 요구가 있다(OM-11). 목표값의 적용 조건(몰리는 시각, 운영 시간대)이 문장에 묻힌다(OM-13, OM-16). 요구가 기대는 연동과 기술 제약을 따라갈 수 없다(OM-03, OM-14).
- **검토한 대안:** (a) 샘플처럼 요구 한 칸에 모두 쓴다 / (b) 지표·목표값·측정 방법을 열로 나눈다 / (c) 속성 표로 요구 하나마다 표를 둔다
- **결정:** (b). 01번 목표지표 표와 같은 어휘(지표, 목표값, 측정 방법)를 쓴다. 대상 열과 원천 열(입력 항목 ID)을 더하고 근거 칸은 문서·위치로 쓴다. `집계` 표는 두지 않고 처리별 개수의 일치는 완료 체크가 맡는다(SA-18, OM-05).
- **이유:** (a)는 측정 가능한지 칸 단위로 점검할 수 없다(OM-01). (c)는 요구 수만큼 표가 늘어난다. 같은 값을 두 단계가 다른 어휘로 쓰지 않으려고 01번의 열 이름을 따랐다.
- **영향:** 요구 목록의 대상·근거는 뒤 단계가 값으로 읽지 않아 `최종 소비자 없음`이다(DL-22-004). 열 열 개로 행당 칸이 많아져 입력이 얇으면 `미정`이 많아진다. 이는 입력 부족이지 구조의 결함이 아니다.
- **상태:** 검토 대기

### DL-22-003 · 처리 칸은 선택지만 두고 후보는 3번 표가 가리키며, 설계 항목도 모두 후보로 올린다
- **날짜:** 2026-10-09
- **대상:** `templates/22_비기능_품질_template.md` (필드 `처리`, `구분`, `출처`), `guides/22_비기능_품질_guide.md` 3.1, 3.3
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 처리 칸은 `승격 → CF-16-14`처럼 2절의 후보 ID를 앞서 참조한다(SA-15, TP-16 위반). 설계 4건 중 1건은 후보 없이 관리해 샘플 자신의 완료 기준과 어긋난다(SA-19, SA-29, OM-07). 후보 문장에 `기능 아님`이 굵은 표시로 붙는다(SA-23). 복구 훈련 같은 절차도 후보가 된다(OM-09).
- **검토한 대안:** (a) 처리 칸에 후보 ID를 쓴다 / (b) 처리는 선택지만 두고 후보 표의 출처가 요구 ID를 가리키게 한다 / (c) 설계 항목 가운데 후보가 없는 것을 허용한다
- **결정:** (b)와 설계 항목은 모두 구분이 `설계 기준`인 후보로 올린다. 구분 어휘는 앞 단계와 같다(기능 후보 / 후속 후보 / 설계 기준 / 프로세스; 19번, 16번). 입력에 같은 기능의 후보가 이미 있는 승격 줄은 근거가 그 ID를 가리킨다(OM-04). 처리 값 `승격`·`기준`·`설계`는 단계 정의 산출물의 "기능으로 승격된 항목 표시"에 해당하는 이 단계의 어휘이고 구분과 목적이 다르다(처리는 요구의 운명, 구분은 후보의 성격).
- **이유:** (a)는 앞 표가 뒤 표 ID를 참조한다. (c)는 통합 단계가 제외 사유를 읽을 수 없다. 완료 체크가 승격·설계 줄이 후보에 닿는지 확인한다.
- **영향:** 요구 목록과 기능 후보가 서로 맞는지는 도구가 검사하지 못하고 완료 체크가 맡는다(DL-22-009). 통합·정규화 단계가 구분의 `프로세스`와 `설계 기준`을 읽어야 한다(IF-22-034).
- **상태:** 검토 대기

### DL-22-004 · 인터페이스 표: 22번 보내는 줄 36개와 외부 입력 줄 3개를 추가하고 잠정 줄 24개를 필드 수준으로 바꾼다
- **날짜:** 2026-10-09
- **대상:** `tools/data/interfaces.csv` (IF-22-001~030, 032, 034~038, IF-EX-22-001~003 추가; 수정: IF-02-029, IF-02-031, IF-02-033, IF-02-035, IF-03-041, IF-03-056, IF-03-057, IF-03-065, IF-03-066, IF-05-037, IF-13-023, IF-14-015, IF-14-019, IF-14-021, IF-14-023, IF-14-026, IF-17-015, IF-18-004, IF-18-007, IF-18-010, IF-19-007, IF-19-010, IF-19-012, IF-19-013)
- **결정 주체:** 유지보수자 판단
- **배경:** 22번 템플릿 필드 29개는 모두 보내는 필드로 한 줄 이상 나와야 한다(IR-07). 쓰이는 곳의 근거는 샘플의 표시 `승격분 → 후보 풀 · 나머지는 (36 이후) 인수조건과 비기능 테스트 기준`(SA-08)과 단계 정의다. 앞 단계가 22번에 보내던 잠정 줄 24개는 22번 필드로 바꿀 수 있게 되었다(IR-10). 샘플 머리말이 목표값의 확정 근거로 든 부하 추정·사용자 조사·비용 한도는 사람이 주는 자료다(SA-04).
- **검토한 대안:** (a) 22번이 받는 입력도 줄로 모두 더한다 / (b) 보내는 줄과 기존 잠정 줄만 다룬다
- **결정:** (b). 요구 목록의 지표·목표값·측정 방법·요구·ID는 36번(출시 게이트의 비기능 기준), 처리·기능 후보는 31번, 원천·ID·출처는 34번, 특성은 32번에 연결했다. 요구는 보안·데이터 성격의 요구를 맞대 보는 23·24·25번에도 문서 수준 잠정 값으로 연결했다(추정: 가정). 대상과 근거, 특성 점검의 열세 항목, 기능 후보의 근거는 `최종 소비자 없음`과 사유를 적었다. 기능 후보의 공통·고유(잠정)는 31번에 연결했다. 20번 도메인 공통·고유 템플릿에는 연결하지 않았다. 20번은 22번보다 앞이어서 22번 후보를 보내면 환류가 되고, 20번은 입력 후보를 22번 산출물 안에서 읽는 구조가 아니기 때문이다. 수정한 줄은 받는 쪽 칸(`22`)을 22번 필드 키로 바꾸고 근거에 이 항목의 ID를 덧붙였다. 외부 입력은 부하 추정, 사용성 조사, 비용 한도 세 줄이다.
- **이유:** 입력 줄은 보내는 단계 번호로 연결 ID를 매기므로(IR-04) 병렬로 만드는 다른 단계의 작업과 번호가 겹칠 수 있어 새로 만들지 않았다. 36번 이후의 템플릿이 없어 받는 쪽은 문서 수준 잠정 값이다.
- **영향:** 해당 템플릿이 생기면 잠정 줄을 필드 수준으로 바꾼다. 22번 템플릿의 입력(생성 블록)에는 지금 02, 03, 05, 13, 14, 17, 18, 19번만 나온다. 나머지 입력 줄은 DL-22-005에 정리했다.
- **상태:** 검토 대기

- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 목표값은 모두 가정이고(SA-04, OM-02), 가용성이 외부 연동의 한도에 기대며(OM-14), 요구끼리 충돌할 수 있고(OM-18), 요구가 없는 특성이 흔하다(OM-16).
- **검토한 대안:** (a) 입력에 없는 목표값은 합리적인 값을 가정해 쓴다 / (b) 입력에 없으면 `미정`(확인처·담당·기한)으로 닫고, 아는 부분을 먼저 쓴다
- **결정:** (b). 목표값, 한도, 기간, 횟수, 비율은 입력에 없으면 `미정`이다. 지표를 못 정하면 목표값과 측정 방법도 `미정`으로 이어 닫는다. 선택지 칸과 ID 칸도 모르면 `미정`이다. 특성 점검의 `해당 없음`은 닫힌 목록이나 입력이 배제할 때만 쓴다. 앞 단계 표가 비어 있는 이유가 질문 `미정`이면 `미정`, 없다는 확인이면 `해당 없음`이다(DL-19-011과 같은 기준). 요구끼리 충돌하면 둘 다 `미정`으로 닫는다. 입력의 상한을 넘는 목표값은 쓰지 않는다.
- **이유:** 틀린 목표값은 출시 게이트와 비기능 테스트로 퍼져 되돌리기 어렵다. 공통 가이드 3절 3번을 이 단계에 적용한 가장 보수적인 쪽이다.
- **영향:** 입력이 얇으면 `미정`이 많아진다. 이는 구조의 결함이 아니라 입력 부족이다. 도메인 교체 시험에서 확인한다.
- **상태:** 검토 대기

### DL-22-007 · 보안·규제·데이터 성격의 요구는 측정 가능한 수준만 이 단계에서 다룬다
- **날짜:** 2026-10-09
- **대상:** `guides/22_비기능_품질_guide.md` 3.2 (QK-06, QK-12), 4절, 6절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 로그인 2단계 필수, 원문 열람 기록, 세션 폐기, 보존 기간 이행, 수집 항목 제한을 이 단계의 요구로 올렸다(OM-10, OM-19). 같은 기능을 위협 목록, 규제 매핑, 데이터 생애 정책도 정의할 수 있다.
- **검토한 대안:** (a) 보안성·데이터·프라이버시 특성을 이 단계에서 제외한다 / (b) 측정 가능한 보호 수준의 요구만 이 단계에서 쓰고 위협·법령·보존 정책은 각 단계의 몫으로 가리킨다 / (c) 샘플처럼 모두 이 단계에서 정한다
- **결정:** (b). 보호 수준은 측정 가능한 요구(적용 비율, 폐기까지의 시간 등)로 쓰고, 위협을 나열하고 방어 기능을 정하는 일, 법령 근거의 매핑, 보존 기간의 정책은 각각 보안·어뷰징, 규제·정책, 데이터 생애 단계에 맡긴다. 같은 기능이 여러 단계에서 후보가 되는 중복은 통합 단계가 병합한다.
- **이유:** (a)는 단계 정의의 목적(품질 요구를 빠짐없이 정한다)에서 보안성을 빼 버린다. (c)는 정의를 세 단계가 나눠 갖게 된다.
- **영향:** 22번 요구가 23·24·25번의 입력이 되는 잠정 줄을 두었다(IF-22-006~008). 같은 그룹의 다른 세트와 경계가 맞는지는 병합 때 확인한다.
- **상태:** 검토 대기

### DL-22-008 · ID 접두어는 요구 목록 `QN`, 특성 점검 `QK`, 기능 후보 `QC`로 하고 후보 표의 열 이름을 통일 규칙에 맞춘다
- **날짜:** 2026-10-09

- **배경:** 샘플은 요구 ID를 `NF-nn`, 후보 ID를 `CF-22-nn`으로 쓴다(SA-12, SA-21). 템플릿 규칙(TP-28)은 접두어가 모든 템플릿에 걸쳐 유일하라고 하고, 이번 호출은 `Q`로 시작하는 접두어만 쓰게 했다. 후보 표의 열 이름은 지시서의 통일 규칙(`ID | 후보 문장 | 구분 | 공통·고유(잠정) | 출처 | (단계 열) | 근거`)을 따랐다.

- **결정:** (b)와 후보 표는 통일 규칙의 열 이름과 순서를 쓴다. 이 단계에서만 필요한 열은 없다.

- **영향:** 17~21번 후보 표의 열 이름을 같은 규칙으로 맞출지는 사용자 결정이다(수정목록 G13).

### DL-22-009 · 제안: 표 사이와 산출물 사이의 정합 검사는 도구가 하지 못한다
- **날짜:** 2026-10-09
- **대상:** `tools/tools-decision-log.md` (알려진 한계), `docs/규칙_템플릿.md`, `docs/규칙_인터페이스표.md`
- **결정 주체:** 유지보수자 판단
- **배경:** 22번 세트를 만들며 도구가 확인하지 못하는 곳 둘을 만났다. (1) 처리가 승격인 요구가 후보의 출처에 나오는지, 설계 요구의 후보가 구분 설계 기준인지, 요구 목록의 모든 줄이 맞는 특성 점검의 답에 나오는지, 처리별 개수가 맞는지는 값을 맞대 보아야 안다(OM-05, OM-07). 현재 산출물 검사(TP-K13)는 구조만 비교한다. (2) 요구의 원천 ID가 앞 단계 산출물에 실제로 있는지는 `check_chain.py`가 ID 형식을 알아야 확인한다. (3) 앞 단계 템플릿이 아직 없는 입력을 받는 연결은 연결 ID가 보내는 단계 번호로 시작해 병렬 작업에서 겹칠 수 있다(DL-19-010과 같은 종류).
- **검토한 대안:** 해당 없음 — 도구와 규칙 문서는 이번 호출의 수정 대상이 아니다. 제안만 남긴다.
- **결정:** 규칙 문서와 도구는 바꾸지 않는다. 표 사이의 ID 참조 일치와 처리·구분의 짝 검사를 도입할지 사용자가 정하게 한다. 그때까지는 완료 체크와 가이드의 누락 점검이 맡는다.
- **이유:** 규칙·도구의 변경은 유지보수자가 단독으로 하지 않는다.
- **영향:** 도입하면 `tools/checks.py`에 검사를 더하고 규칙_템플릿에 대응 규칙을 정한다.
- **상태:** 검토 대기

### DL-22-010 · 특성 선택지는 품질 모델의 이름을 고정하지 않고 열두 개로 둔다
- **날짜:** 2026-10-09
- **대상:** `templates/22_비기능_품질_template.md` (필드 `특성`, 표 `특성점검`), `guides/22_비기능_품질_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 외부 표준의 이름과 판본을 일반 서술로 인용하고 세부 명칭이 판본에 따라 다를 수 있다고 쓴다(SA-09). 샘플의 특성 열에는 그 표준의 아홉 특성에 관측성·비용·데이터·프라이버시가 더해져 있다(SA-13). 이 체계는 외부 표준을 검증하지 않았다(출처 유형 `일반 지식(미검증)`).
- **검토한 대안:** (a) 외부 표준의 이름과 판본을 템플릿에 쓴다 / (b) 아홉 특성의 이름을 고정하되 표준 이름은 쓰지 않고 관측성·비용·데이터·프라이버시를 덧붙인다 / (c) 특성을 자유 서술로 둔다
- **결정:** (b). 열두 특성을 선택지로 고정하고 특성 점검은 열두 개에 개방 질문을 더한 열세 개다. 프로젝트 자료가 품질 모델을 지정하면 가이드의 대응 방법(이름을 선택지에 맞추고 원래 이름은 근거에 남긴다)을 따른다.
- **이유:** (a)는 검증하지 않은 외부 사실을 템플릿에 쓰게 된다(TP-02). (c)는 특성 점검과 요구 목록을 맞댈 수 없다.
- **영향:** 사용자가 특정 품질 모델의 이름과 범위를 확정하려면 외부 자료를 확인해 이 항목을 대체해야 한다. 선택지가 바뀌면 특성 점검 항목도 같이 고친다.
- **상태:** 검토 대기
