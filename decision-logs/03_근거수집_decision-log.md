### DL-03-001 · 03번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-09
- **대상:** `conversions/03_근거수집_conversion.md`, `templates/03_근거수집_template.md`, `guides/03_근거수집_guide.md`
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 그룹 A의 세 번째 세트로 03번을 만든다. 샘플 해부 66행(SA-01~66)과 누락 탐색 21행(OM-01~21)을 04번 이후와 같은 절차로 만들었다. 샘플의 인터뷰 열 건, 유사 서비스 서른네 행, 규제 열여섯 행, 기술 제약 일곱 행은 값 표 단위로 묶어 해부했다(CV-06). 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서의 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 "도출 질문 → 후보 → 판정 → 목록" 흐름을 쓰지 않고 단계의 목적(가설과 범위를 외부 자료로 확인해 뒤 단계의 값이 근거에 기대게 한다)에서 구성을 정했다. 구성은 DL-03-002에 있다. 도메인 교체 시험은 하지 않았다.
- **이유:** 이 단계는 사람이 가진 정보를 묻고 정리하는 단계라 도출 질문과 판정으로 후보를 걸러낼 대상이 없다. 샘플을 해부하고 누락을 찾은 결과가 템플릿의 모든 변경에 대응한다(정의서 6절 4번, 검사 CV-K04).
- **영향:** 도메인 교체 시험과 변환 분석서 `승인`이 남았다. 입력이 얇으면 `미정`이 많이 나오는데 이것은 구조의 결함이 아니라 입력 부족이다. 인터페이스 표는 DL-03-010에, 병합 때 더할 줄은 DL-03-011에 있다.
- **상태:** 유효

### DL-03-002 · 구성은 조사 개요와 여섯 개의 근거 표로 한다
- **날짜:** 2026-10-09
- **대상:** `templates/03_근거수집_template.md` (1~7절), `conversions/03_근거수집_conversion.md` (SA-04, SA-21, SA-30, SA-33, SA-40, SA-49, OM-02)
- **결정 주체:** 유지보수자 판단
- **배경:** 단계 정의의 산출물은 사용자 인사이트, 유사 서비스 기능표, 규제·정책 목록, 기술 제약 메모이고 항목마다 출처 유형을 쓴다. 샘플은 이 네 가지를 표 넷으로 두고 출처 유형 열을 각 표에 붙였다. 유사 서비스 표는 서비스를 열 세 개로 고정한 교차표다(SA-33).
- **검토한 대안:** (a) 샘플처럼 네 표로 두고 열만 일반화한다 / (b) 04·05번처럼 도출 질문과 판정 표를 앞에 둔다 / (c) 조사 개요 표 하나에 네 근거 표를 잇고 유사 서비스는 서비스, 기능, 칸의 세 표로 나눈다
- **결정:** (c). 구성은 조사 개요(속성 표) → 사용자 조사 → 유사 서비스 → 비교 기능 → 기능별 제공 현황 → 규제·정책 → 기술 제약이다. 정의 ID 접두어는 DL-03-008에 있다.
- **이유:** (a)는 서비스 수가 달라지면 열이 바뀌고 칸마다 근거와 차이를 붙일 수 없다. (b)는 이 단계에 걸러낼 후보가 없다(DL-03-001). (c)는 06번 DL-06-006과 12번 DL-12-010의 매트릭스 표기(칸 하나가 행 하나)와 같고, 서비스와 기능에 ID를 주어 유사 서비스 대조 단계가 가리킬 수 있게 한다.
- **영향:** 기능 × 서비스 조합마다 한 행이 생겨 서비스와 기능이 많으면 표가 길다. 조합이 빠지거나 겹치는지를 도구가 검사하지 못해 완료 체크와 사람의 확인에 맡긴다. 규칙 문서 변경 제안은 DL-03-012에 있다.
- **상태:** 검토 대기

### DL-03-003 · 조사 개요 표를 두어 실제로 한 조사를 밝힌다
- **날짜:** 2026-10-09
- **대상:** `templates/03_근거수집_template.md` 1절 (표 키 `조사개요`), `guides/03_근거수집_guide.md` 3.1, 5절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 "이 문서의 모든 값은 근거 없는 가상 값"이라고 문서 맨 앞에서 고지한다(SA-04~06). 실제 산출물에서 이 고지의 자리는 영역마다 실제로 무엇을 했는지, 무엇을 못 했는지다(OM-02). 근거 칸의 `조사:`는 출처·확인일·버전을 요구하지만(SA-06) 영역 전체를 조사하지 않았다는 사실은 칸 단위로 드러나지 않는다.
- **검토한 대안:** (a) 표를 두지 않고 근거 칸만으로 드러낸다 / (b) 조사 개요 속성 표를 두고 네 영역의 방법·기간·수·확인자를 쓴다 / (c) 영역마다 수행 여부를 선택지로 둔다
- **결정:** (b). 영역은 사용자 조사, 유사 서비스 조사, 규제·정책 확인, 기술 제약 확인이다. 하지 않은 영역은 `미정`(확인처·담당·기한)으로 닫는다. 이 표의 네 항목은 사람이 읽는 설명이라 뒤 단계가 값으로 쓰지 않는다(`최종 소비자 없음`).
- **이유:** (a)는 영역 전체가 비었는지 칸마다 열어 봐야 알 수 있다. (c)는 방법·기간·수와 법무 같은 전문가 검토 여부를 담지 못한다. 근거 칸의 형식(CM-18)은 바꾸지 않았다.
- **영향:** 표 하나와 필드 네 개가 늘었다. 사용자가 이 표의 필요성을 확인한다(DL-03-013).
- **상태:** 검토 대기

### DL-03-004 · 사용자 조사 표의 열: 조사 대상, 사용자의 말, 종류, 빈도, 가설과의 관계
- **날짜:** 2026-10-09
- **대상:** `templates/03_근거수집_template.md` 2절 (표 키 `사용자조사`), `guides/03_근거수집_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 인사이트 한 칸은 따옴표 인용과 해석이 섞여 있고(SA-23), 출처는 참가자 번호뿐이다(SA-24). 사람 액터를 찾는 04번 가이드는 조사에 나온 사람의 유형을 읽고, 저니 매트릭스 가이드는 인사이트에서 불편·위험·이탈 지점을 찾고, 엔티티 가이드는 조사에 나온 사용자의 말을 표준 용어 후보로 읽는다(OM-03, OM-04). 04번 변환은 샘플 04의 `03번 조사 대상` 열을 이 단계가 맡도록 넘겼다(04번 DL-04-005). 목적은 가설을 외부 자료로 확인하는 것이다(OM-09).
- **검토한 대안:** (a) 샘플처럼 인사이트·출처·관련 가설·영향 영역만 둔다 / (b) 사용자의 말과 인사이트를 나누고 조사 대상(역할이나 유형)과 빈도, 종류를 더한다 / (c) (b)에 가설과의 관계(뒷받침·일부 뒷받침·반박)를 더한다
- **결정:** (c). 종류는 불편·위험 / 이탈 계기 / 기대·욕구 / 현재 방식이다. 관련 가설이 없으면 `해당 없음`(확인한 목록)이고 가설과의 관계도 같다. 기록 없는 팀의 기억은 인사이트 행으로 쓰지 않는다(가이드 3.2).
- **이유:** (a)는 사람 유형과 불편을 읽는 뒤 단계가 이 문서에서 값을 가져갈 수 없다. (b)만으로는 반박하는 근거가 가설과 같은 쪽으로 읽힐 수 있다(OM-09). `현재 방식`은 사내 도구처럼 경쟁 서비스가 없는 도메인에서 사용자의 말이 대부분 현재 방식의 불편이라서 둔다(OM-14).
- **영향:** 열이 10개이고 필드가 10개 늘었다. 가설과의 관계는 가설 확인 상태를 되돌려 고치는 환류 줄(`03.사용자조사.가설과의 관계` → 목표·가치)로 연결했다. 가설과의 관계 열을 유지할지는 사용자가 확인한다(DL-03-013).
- **상태:** 검토 대기

### DL-03-005 · 유사 서비스를 서비스, 기능, 칸의 세 표로 나눈다
- **날짜:** 2026-10-09
- **대상:** `templates/03_근거수집_template.md` 3~5절 (표 키 `유사서비스`, `비교기능`, `비교칸`), `guides/03_근거수집_guide.md` 3.3~3.5
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 기능표는 서비스를 A·B·C 열로 고정한 교차표이고 `비고`가 차이와 범위 참조를 섞는다(SA-31, SA-33, SA-37). 샘플은 서비스 선정, 확인 방법, 외부에서 보이지 않는 한계를 설명하는 절차를 문장으로만 두었다(SA-16~20, OM-08). 비교할 서비스와 기능에는 ID가 있어야 유사 서비스 대조 단계가 가리킨다(SA-59).
- **검토한 대안:** (a) 서비스를 열로 둔 교차표를 유지한다 / (b) 서비스 목록과 기능 목록을 두고 기능 × 서비스를 칸 하나가 행 하나인 표로 쓴다 / (c) 기능 목록 표 없이 칸 표에 기능 이름을 쓴다
- **결정:** (b). 서비스 표는 선정 이유, 확인 방법(직접 사용 / 공식 문서 / 릴리스 노트·소개 자료 / 제3자 자료), 확인 한계를 갖는다. 기능 표는 기능과 범위 항목(범위·제약 산출물의 ID 참조)을 갖는다. 칸 표는 제공 여부(제공 / 일부 제공 / 제공하지 않음)와 차이를 갖는다. 확인하지 못한 칸은 `미정`이다.
- **이유:** 06번 DL-06-006과 12번 DL-12-010의 매트릭스 표기 선례와 같다. (c)는 같은 기능 이름이 행마다 되풀이되어 어긋난다. `×`의 `없음`은 권한 없음의 `없음`과 헷갈려 `제공하지 않음`으로 바꿨다(SA-32).
- **영향:** 서비스 수 × 기능 수만큼 행이 생긴다(DL-03-002). 범위 항목에 해당하는 항목이 없으면 `미정`으로 닫는다(범위에 아직 없는 기능이 갭 후보로 드러난다). 범위 항목의 ID 접두어는 범위·제약 단계가 정한다.
- **상태:** 검토 대기

### DL-03-006 · 규제·정책 표의 열: 종류, 요구 유형, 대상 정보·기록, 기한·기간, 적용 여부
- **날짜:** 2026-10-09
- **대상:** `templates/03_근거수집_template.md` 6절 (표 키 `규제정책`), `guides/03_근거수집_guide.md` 3.6
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 규제 표는 분류, 요건, 적용 이유를 두고 분류가 법령의 주제와 요구하는 곳(스토어, 플랫폼, 정책)을 섞는다(SA-42). 뒤 단계가 서로 다른 것을 읽는다: 엔티티 가이드는 일반 개인정보와 달리 다루라고 정한 정보와 보관 의무가 있는 기록을(DL-11-005), 시간·주기 가이드는 규제가 정한 기한을, 소유·권한 가이드는 접근 제한 요건을, CRUD 매트릭스 가이드는 제외 방침(정책·규제)의 출처를, 플랫폼·채널 가이드는 플랫폼 정책 문서의 이름과 확인일을 읽는다(OM-05). 샘플은 `의무 여부는 법무 확인` 같은 모름을 값처럼 적었다(SA-48, OM-06).
- **검토한 대안:** (a) 샘플의 분류·요건·적용 이유만 둔다 / (b) 종류와 주제를 나누고 요구 유형·대상 정보·기록·기한·기간을 더한다 / (c) (b)에 적용 여부를 더한다
- **결정:** (c). 종류는 법령·규정 / 플랫폼·스토어 정책 / 업계 표준·인증 / 조직 내부 정책이다. 요구 유형은 여덟 가지(동의·접근 제한, 정보 취급 기준, 보존·파기·기한, 고지·공개, 제공·노출 제한, 사용자 권리 보장, 신고·등록·심사, 품질 기준)이고 한 요건이 둘에 걸치면 더 무거운 쪽을 고른다. 적용 여부는 적용 / 적용 후보 / 적용 제외이고 전문가 검토 없이는 `적용`으로 올리지 않는다. 기한·기간은 모르면 `미정`(확인처: 법무 담당)이고 "법무 확인 필요"는 값이 아니다. 법령 이름이나 조문은 가이드에 쓰지 않았다.
- **이유:** (a)는 열 몇 개를 뒤 단계가 문장에서 직접 뽑아야 한다. 일반 개인정보와 구별해 취급하라는 요건은 구별을 요건 문장에 밝히게 하고 엔티티 단계가 읽는다(별도 `정보 구분` 열은 한 요건이 둘에 걸칠 때 선택지가 겹쳐 두지 않았다).
- **영향:** 열이 10개이고 필드가 10개 늘었다. 요구 유형이 여덟 가지로 많아 도메인 교체 시험에서 고르기 어려운 값이 있는지 본다. 규제 문서를 읽을 전문가가 없으면 적용 여부가 대부분 `적용 후보`로 남는다.
- **상태:** 검토 대기

- **날짜:** 2026-10-09
