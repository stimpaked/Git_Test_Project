# 결정 로그 — 16. 이벤트

> 16번 세트(템플릿, 단계 가이드, 변환 분석서, 인터페이스 표의 16 관련 연결)의 결정 이력이다. 항목은 추가만 하고 과거 항목은 고치지 않는다(`docs/규칙_결정로그.md`).
> 변환 분석서의 줄 ID(`SA-nn`, `OM-nn`)를 `배경`에 적어 근거를 가리킨다(CV-13).

### DL-16-001 · 16번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `conversions/16_이벤트_conversion.md`, `templates/16_이벤트_template.md`, `guides/16_이벤트_guide.md`
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 04~10번에 이어 16번 세트를 만든다. 샘플 해부 36행(SA-01~36)과 누락 탐색 15행(OM-01~15)을 같은 절차로 만들었다. 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 구성(도출 질문 → 후보 → 판정 → 목록)을 따르지 않고 이 단계의 목적(서비스 안의 사건과 그것을 받아 처리하는 기능을 정리해 후속 처리 기능을 도출한다)에 맞춰 값 표를 둘로 한다. 1번 표 `이벤트목록`은 사건과 발생 기능, 소비 기능 네 종류의 목록(정의 ID `VE`)이고, 2번 표 `기능후보`는 이벤트에서 새로 드러난 기능 후보의 목록(정의 ID `VC`)이다(SA-09, SA-26, OM-01~06). 그림이나 표 없는 필수 블록은 없다.
- **이유:** 이 단계의 본질은 사건을 나열하고 사건마다 누가 일으키고 누가 받는지 쓰는 것이며, 산출물의 핵심은 소비 기능에서 드러난 후속 기능 후보다. 도출 질문과 판정 단계는 이 단계에 해당하지 않는다. 템플릿의 모든 변경이 분석서의 줄에 대응한다(정의서 6절 4번).
- **영향:** 도메인 교체 시험(8번)이 남았다. 인터페이스 표에 16번 보내는 줄 17개를 더했다(DL-16-008).
- **상태:** 유효

### DL-16-002 · 이벤트 목록을 기능 후보 표보다 앞에 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/16_이벤트_template.md` 1·2절, `docs/규칙_템플릿.md` (TP-16)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 이벤트 목록의 알림·후속 처리 칸 안에서 2절 후보 표의 ID(`CF-16-07` 등)를 앞서 참조한다(SA-22). 앞 표가 뒤 표의 ID를 참조하는 순서 오류이며 검사 TP-K07도 이를 막는다. 반대로 후보 표의 출처가 이벤트 ID를 가리키므로 두 표는 서로를 참조하려 한다.
- **검토한 대안:** (a) 샘플 순서를 유지하고 칸에 후보 ID를 쓴다 / (b) 후보 표를 앞에 두고 이벤트 칸이 후보 ID를 참조하게 한다 / (c) 이벤트 목록을 앞에 두고 칸은 소비 기능을 서술하며 후보 표의 출처가 이벤트 ID를 가리키게 한다
- **결정:** (c). 이벤트 목록을 1번, 기능 후보를 2번으로 두고 이벤트 칸에는 후보 ID를 쓰지 않는다. 입력 산출물에 이미 있는 후보의 ID는 칸에 쓸 수 있다(그 ID는 앞 단계가 부여한 것이다).
- **이유:** (a)는 TP-16 위반이다. (b)는 후보가 이벤트에서 나오는 도출 방향과 반대이고 사건을 먼저 찾는 작성 순서와 맞지 않는다. (c)는 사건을 찾고 소비 기능을 따진 뒤 새 기능을 후보로 모으는 순서와 같다.
- **영향:** 이벤트 목록의 소비 기능과 후보 표 행이 서로 맞는지(칸의 새 기능이 후보 표에 모두 있는지, 후보 표의 출처가 이벤트 목록에 있는지)는 도구가 검사하지 못하고 완료 체크와 가이드의 누락 점검이 맡는다(DL-16-009).
- **상태:** 검토 대기

### DL-16-003 · 소비 기능의 네 종류를 열로 유지하고 칸은 서술 칸으로 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/16_이벤트_template.md` 1절 (필드 `알림`, `로그`, `분석`, `후속 처리`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 소비 기능을 알림·로그·분석·후속 처리의 네 열로 쓰고 소비가 없는 칸을 `없음(사유)`와 `—`로 섞어 쓴다(SA-13~17). 외부 시스템 호출이나 장치 제어처럼 네 종류에 딱 맞지 않는 소비도 있다(OM-09). 한 사건에 같은 종류의 소비 기능이 여럿인 경우도 있다(OM-13).
- **검토한 대안:** (a) 소비 기능마다 한 행씩 두는 정규화된 목록 표로 바꾼다 / (b) 네 열을 유지하고 칸에 소비 기능을 서술한다 / (c) 열을 다섯 이상으로 늘려 외부 전달 같은 종류를 더한다
- **결정:** (b). 네 열을 유지하고 칸은 자유 서술(여럿이면 쉼표로 구분)로 한다. 네 종류에 들지 않는 소비는 후속 처리에 두는 기준을 가이드에 쓰고, 소비가 없는 칸은 공통 규칙의 `해당 없음`과 사유로 닫는다. 칸 안에 후보 표의 ID를 쓰지 않는다(DL-16-002).
- **이유:** (a)는 사건 하나의 소비 기능을 한눈에 보는 구조를 잃고 행이 몇 배로 늘어난다. (c)는 외부 전달 같은 종류가 단계 정의가 말하는 알림·기록·분석 등의 범위를 넘고, 외부 연동의 기능 도출은 뒤 단계의 몫이다. (b)는 샘플 구조를 지키면서 소비 종류별 기능을 모을 수 있다.
- **영향:** 외부 시스템 전달 같은 소비를 후속 처리에 섞어 쓰므로 외부 연동 단계는 후속 처리 칸에서 그것을 가려내야 할 수 있다. 도메인 교체 시험에서 이 부담이 과한지 본다. 칸이 자유 서술이라 소비 기능 하나를 정확히 가리키는 ID 참조가 되지 않는다.
- **상태:** 검토 대기

### DL-16-004 · 이벤트 한 행은 사건 하나로 쓴다는 기준을 가이드에 둔다
- **날짜:** 2026-10-08
- **대상:** `guides/16_이벤트_guide.md` 3.1, 4절, 6절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 `이의제기가 접수·결정되었다`, `문의가 접수되었다 / 답변이 완료되었다`처럼 사건 둘을 한 행에 묶고(SA-19), 포괄적인 행과 구체적인 행이 같은 사건을 겹쳐 쓰며(SA-20), 열 이름이 과거형인데 `다가온다`처럼 현재형으로 쓴 행이 있다(SA-21). 사건을 나누는 입도는 소비 기능 구성이 갈린다는 판단 기준이다(OM-07).
- **검토한 대안:** (a) 입도 기준을 템플릿의 힌트로 둔다 / (b) 가이드에만 쓴다 / (c) 입도를 정하지 않는다
- **결정:** (b). 한 행은 사건 하나이고, 하나의 사건이 여러 값으로 나뉘면 소비 기능이 모두 같을 때만 한 행으로 쓰고 하나라도 다르면 나눈다. 시간이 일으키는 사건은 시점에 도달한 사실로 쓴다. 보수적으로 나누는 쪽(소비 기능이 갈리면 나눔)을 골랐다.
- **이유:** 힌트는 조건 없는 한 문장이어야 하므로(TP-18) 조건이 있는 입도 기준은 가이드의 몫이다(정의서 4절 판별법 2). 사건을 묶으면 한 칸에 다른 사건의 소비 기능이 섞여 후보 도출에서 빠지기 쉽다.
- **영향:** 나누는 쪽으로 기울어 행이 늘 수 있다. 도메인 교체 시험에서 입도 기준이 흔들리는지 본다.
- **상태:** 검토 대기

### DL-16-005 · 기능 후보 표에 구분 열을 두고 앞 단계의 같은 어휘를 쓴다
- **날짜:** 2026-10-08
- **대상:** `templates/16_이벤트_template.md` 2절 (필드 `구분`, `공통·고유(잠정)`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 기능이 아닌 설계 결정을 문장 속 굵은 표시로(SA-31), 후속으로 미룬 소비 기능을 칸 안의 괄호로만 표시한다(SA-25). 후보 표의 `도메인 구분(잠정)`은 `도메인`이 모호하다(SA-30). 앞 단계(시나리오 5유형)가 같은 문제를 `구분`(기능 후보 / 후속 후보 / 설계 기준)과 `공통·고유(잠정)`(공통 / 고유)로 풀었다(DL-10-004).
- **검토한 대안:** (a) 샘플처럼 표시를 문장 속에 둔다 / (b) 앞 단계와 같은 `구분`, `공통·고유(잠정)` 열을 쓴다 / (c) 이 단계만의 새 어휘를 만든다
- **결정:** (b). 같은 값을 두 단계가 서로 다른 어휘로 쓰지 않는다. `공통·고유(잠정)`은 판단이 갈리면 `고유`를 고른다(유저 플로우 단계의 기준과 같은 보수적 쪽). 앞 단계의 시나리오 5유형은 근거가 없으면 `미정`으로 닫게 하는 점이 다르므로 이 단계 가이드는 갈릴 때와 근거가 없을 때를 구분해 쓴다.
- **이유:** 뒤 단계(통합·정규화, 도메인 공통·고유)가 여러 단계의 후보를 한 어휘로 읽어야 한다. 공통으로 잘못 보면 재사용을 기대해 설계가 빠지고, 고유로 잘못 보면 판정 단계가 바로잡는다.
- **영향:** 후속 후보의 후속 항목을 읽는 입력(범위·제약의 후속 목록)이 인터페이스 표에 아직 없다(DL-16-008).
- **상태:** 검토 대기

### DL-16-006 · ID 접두어는 이벤트 `VE`, 기능 후보 `VC`로 한다
- **날짜:** 2026-10-08
- **대상:** `templates/16_이벤트_template.md` (정의 ID `VE`, `VC`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 `EV-`와 `CF-16-`을 쓴다. `CF-16-nn`은 단계 번호를 ID 안에 넣는다(SA-10, SA-27). 템플릿 규칙(TP-28)은 접두어가 모든 템플릿에 걸쳐 유일하라고 하고, 이번 호출은 `V`로 시작하는 접두어만 쓰게 했다.
- **검토한 대안:** (a) 샘플의 `EV`, `CF`를 그대로 쓴다 / (b) `V`로 시작하는 접두어를 쓴다
- **결정:** (b). 이벤트는 `VE`(Event), 기능 후보는 `VC`(Candidate)로 하고 `01`부터 연번을 매긴다.
- **이유:** 다른 단계를 만드는 에이전트와 접두어가 겹치는 것을 막는다(TP-K14가 검사한다). 접두어만으로 어느 단계의 ID인지 알 수 있다.
- **영향:** 분석서 SA-10, SA-27에 기록했다. 이 접두어는 다른 템플릿이 쓰는 기존 접두어(A, AC, AQ, AR, NC, NQ, X, FL, FQ, HQ, JS)와 겹치지 않는다.
- **상태:** 검토 대기

### DL-16-007 · 분석 칸에는 측정 이벤트의 이름을 짓지 않는다
- **날짜:** 2026-10-08
- **대상:** `templates/16_이벤트_template.md` 1절 (필드 `분석`), `guides/16_이벤트_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 분석 칸은 `signup_complete`처럼 측정 이벤트의 이름을 확정해 쓴다(SA-23). 그런데 이름과 속성의 표준은 같은 문서의 아래 후보로 아직 정해지지 않았고, 측정할 이벤트의 계획은 성장·측정 단계가 정한다. 이 단계의 목적은 사건을 받는 기능을 드러내는 것이다.
- **검토한 대안:** (a) 샘플처럼 측정 이벤트 이름을 쓴다 / (b) 무엇을 측정하는 기능인지만 서술하고 이름은 짓지 않는다
- **결정:** (b). 이름을 정하는 일은 성장·측정 단계의 몫으로 남긴다.
- **이유:** 앞 단계가 뒤 단계의 표준을 앞서 정하면 뒤 단계에서 이름이 바뀔 때 두 곳이 어긋난다(CM-12). 샘플의 형식은 특정 분석 도구의 관행에 기대고 있다.
- **영향:** 성장·측정 단계가 이 단계의 분석 칸을 입력으로 읽을 때 이름을 새로 정해야 한다(인터페이스 표 IF-16-001, 002, 008).
- **상태:** 검토 대기

### DL-16-008 · 인터페이스 표: 16번 보내는 줄 17개를 추가하고 입력 줄은 더하지 않는다
- **날짜:** 2026-10-08
- **대상:** `tools/data/interfaces.csv` (IF-16-001~017)
- **결정 주체:** 유지보수자 판단
- **배경:** 16번 템플릿의 필드 14개가 모두 보내는 필드로 나와야 한다(IR-07). 앞 단계(04~10번)가 16번에 보내는 잠정 줄은 없어서 바꿀 줄이 없다. 뒤 단계 템플릿(20, 28, 31, 33)은 없어서 받는 쪽은 문서 수준 잠정 값 `NN`이다(IR-10). 쓰이는 곳의 근거는 샘플의 표시 `소비 기능 → 후보 풀 · 28(트래킹 이벤트 계획) · 33(알림·로그 공통 기능과의 uses 관계)`(SA-07)와 단계 정의다.
- **검토한 대안:** (a) 이벤트 목록의 모든 칸을 소비자와 연결한다 / (b) 샘플이 말하는 만큼만 연결하고 사건이 나온 근거 칸은 `최종 소비자 없음`으로 닫는다 / (c) 입력 줄(유저 플로우 → 이벤트)도 이번에 더한다
- **결정:** (b). 소비 기능 네 칸은 후보 풀 대조를 위해 31번에, 분석은 28번에, 알림·로그와 발생 기능은 33번에 판단 입력으로 연결했다. 후보 표의 ID·기능 후보는 31번에, 구분은 31번에, 공통·고유(잠정)는 20번에 연결했다. 20번은 샘플의 쓰이는 곳 표시에 없으나 같은 열을 앞 단계가 20번으로 연결한 선례를 따랐다. 근거 칸 둘은 사유와 함께 `최종 소비자 없음`으로 닫았다. 입력 줄은 더하지 않았다. 유저 플로우 → 이벤트(IF-09-nnn)와 다른 그룹 단계(상태 전이, 시간·주기, 소유·권한, 범위·제약의 후속 목록)에서 이벤트로 오는 줄이 없어 템플릿의 `입력` 블록이 `연결 미작성`으로 나온다. 유저 플로우의 줄은 같은 번호 구간을 다른 단계도 쓸 수 있어 이번 호출에서 더하지 않았다.
- **이유:** 샘플과 단계 정의가 뒷받침하는 만큼만 소비자를 주장한다. 입력 줄은 보내는 단계 번호로 연결 ID를 매기므로 다른 단계의 작업과 번호가 겹칠 수 있다.
- **영향:** 합칠 때 사용자가 정해야 한다. 유저 플로우 → 이벤트 목록(`09.질문목록.ID`가 발생 기능을 가리키는 참조, `09.질문목록.기능 후보`가 사건을 찾는 판단 입력, `09.등장상태.상태`와 상태 전이 단계가 사건의 출처)과 시간·주기, 소유·권한 단계에서 이벤트 목록의 발생 기능으로 오는 줄, 범위·제약 → 구분의 후속 목록 줄(IF-02-004의 선례가 있다)이 필요하다. 20, 28, 31, 33번 템플릿이 생기면 해당 잠정 줄을 필드 수준으로 바꾼다.
- **상태:** 검토 대기

### DL-16-009 · 제안: 표 사이와 칸 사이의 정합 검사는 도구가 하지 못한다
- **날짜:** 2026-10-08
- **대상:** `tools/tools-decision-log.md` (알려진 한계), `docs/규칙_템플릿.md`
- **결정 주체:** 유지보수자 판단
- **배경:** 이벤트 목록의 새 소비 기능이 후보 표에 모두 있는지, 후보 표의 출처 `VE-` ID가 이벤트 목록에 있는지, 이벤트마다 네 소비 칸 중 하나 이상에 소비 기능이 있는지는 값을 맞대 보아야 안다. 현재 산출물 검사(TP-K13)는 구조만 비교한다(DL-10-008과 같은 한계).
- **검토한 대안:** 해당 없음 — 도구와 규칙 문서는 이번 호출의 수정 대상이 아니다. 제안만 남긴다.
- **결정:** 규칙 문서와 도구는 바꾸지 않는다. 표 사이 ID 참조 일치와 같은 행 안의 칸 사이 조건(네 칸 중 하나 이상이 값)을 검사할지 사용자가 정하게 한다. 그때까지는 완료 체크와 가이드의 누락 점검이 맡는다.
- **이유:** 규칙·도구의 변경은 유지보수자가 단독으로 하지 않는다.
- **영향:** 도입하면 `tools/checks.py`에 검사를 더하고 규칙_템플릿에 대응 규칙을 정한다. 시나리오 5유형과 유저 플로우에도 같은 구조가 있어 한 번에 도입하는 편이 낫다.
- **상태:** 검토 대기

### DL-16-010 · 후보 표 열을 통일한다(수정목록 G13)
- **날짜:** 2026-10-09
- **대상:** `templates/16_*_template.md` v1.1, `tools/data/interfaces.csv`, `conversions/16_*_conversion.md`
- **결정 주체:** 사용자 결정
- **배경:** DL-20-013에서 후보 표의 열 이름과 순서가 단계마다 달라 20번 작성자가 스크립트로 파싱해야 한다고 보고했다. 사용자가 통일하기로 했고 그룹 F 뒤에 한꺼번에 하기로 했다. 통일 모양은 `ID | 후보 문장 | 구분 | 공통·고유(잠정) | 출처 | (단계 고유 열) | 근거`다.
- **검토한 대안:** (a) 그대로 둔다 / (b) 통일한다
- **결정:** (b). 열 이름 `기능 후보`를 `후보 문장`으로 바꾸고 열 순서를 통일했다. 구분 선택지에 `프로세스`를 더했다. 필드 키가 바뀌어 인터페이스 표와 변환 분석서의 이름을 맞췄다. `구분`의 선택지는 `기능 후보`, `후속 후보`, `설계 기준`, `프로세스` 네 가지다.
- **이유:** 뒤 단계(20, 31, 34)가 후보 표를 단계마다 다른 열로 읽지 않게 한다.
- **영향:** 템플릿 버전이 올랐다. 이 단계의 가이드는 열 이름과 `구분` 설명을 맞춰야 한다. 이미 쓴 이 단계의 시험 산출물은 열 구성이 달라 다시 써야 한다.
- **상태:** 검토 대기
