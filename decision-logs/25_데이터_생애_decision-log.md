### DL-25-001 · 25번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-09
- **대상:** `conversions/25_데이터_생애_conversion.md`, `templates/25_데이터_생애_template.md`, `guides/25_데이터_생애_guide.md`
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 22~25번 네 단계를 병렬로 만든다. 샘플 해부 44행(SA-01~44)과 누락 탐색 25행(OM-01~25)을 앞 단계와 같은 절차로 만들었다. 샘플의 생애표 27행과 후보 8행은 같은 틀을 되풀이해 표 단위로 묶었다(CV-06). 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 구성(도출 질문 → 후보 → 판정 → 목록)을 따르지 않고 이 단계의 목적(데이터가 만들어져 없어지기까지의 정책을 정하고 필요한 기능을 도출한다)에 맞춰 값 표를 셋으로 둔다. 1번 표 `생애정책`은 엔티티 하나가 행 하나인 목록(정의 ID `YP`), 2번 표 `공통정책`은 서비스 전체에 걸치는 정책을 찾는 고정 질문 열두 개의 속성 표(`YQ`), 3번 표 `기능후보`는 두 표에서 도출한 후보(`YC`)다. 표 없는 필수 블록과 선택 블록은 없다.
- **이유:** 이 단계의 본질은 엔티티마다 보존·파기 정책을 닫고 서비스 전체 정책을 점검해 기능을 모으는 것이다. 템플릿의 모든 변경이 분석서의 줄에 대응한다(정의서 6절 4번).
- **영향:** 도메인 교체 시험(8번)이 남았다. 인터페이스 표에 25번 보내는 줄 36개와 외부 입력 줄 2개를 더하고 잠정 줄 11개를 바꿨다(DL-25-007).
- **상태:** 유효

### DL-25-002 · 생애 정책은 엔티티 하나를 행 하나로 두고 정책 항목은 열로 둔다
- **날짜:** 2026-10-09
- **대상:** `templates/25_데이터_생애_template.md` 1절 (표 `생애정책`), `guides/25_데이터_생애_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 엔티티 단위 정책이라 엔티티 목록을 행의 출발로 쓰되, 엔티티와 정책 항목의 교차곱으로 행이 수백 개가 되면 안 된다. 샘플은 엔티티마다 한 줄이지만 행 ID가 없고(SA-11), 한 열에 서로 다른 개념이 섞여 있다(SA-13, SA-14, SA-17, SA-19). 후보의 출처가 서술이라 어느 정책에서 나왔는지 따라갈 수 없다(OM-01).
- **검토한 대안:** (a) 샘플처럼 열을 그대로 두고 행 ID만 더한다 / (b) 엔티티 행 아래에 정책 항목별 하위 행을 둔다 / (c) 엔티티 하나를 행 하나로 두고 섞인 열을 개념별로 갈라 열 열 개(ID, 엔티티, 보존 기간, 보존 사유, 기간 경과 시, 계정 종료 시, 보존 연장 조건, 법정 보존, 관련 규제, 열람·내보내기)와 근거로 한다 / (d) 엔티티×정책 항목 매트릭스
- **결정:** (c). 개인정보 열은 엔티티 단계의 값을 옮기는 일이라 지운다(SA-12, 같은 사실을 두 곳에 쓰지 않는다). 서비스 전체 정책(분리 보관 방식, 처리 방법)은 공통 정책 표가 갖는다. 엔티티 수가 N이면 행도 N이다. 매트릭스(d)는 쓰지 않았다.
- **이유:** (b)와 (d)는 교차곱이라 행 수가 엔티티 수 곱하기 정책 항목 수가 된다. (a)는 섞인 열이 칸을 닫기 어렵게 한다. (c)는 행 하나가 판단 묶음 하나이고 열마다 선택지나 값이 하나다.
- **영향:** 같은 엔티티에서 당사자나 속성별로 처리가 갈리면 선택지 하나로 닫기 어렵다(OM-23, OM-25). 이는 단계 가이드가 주된 처리와 예외로 나눠 쓰게 한다. 가이드 3.1과 완료 체크가 한 줄 규칙을 갖는다.
- **상태:** 검토 대기

### DL-25-003 · 기능 후보 표는 통일된 열 순서를 따르고 구분에 `프로세스`를 포함한다
- **날짜:** 2026-10-09
- **대상:** `templates/25_데이터_생애_template.md` 3절 (표 `기능후보`), `guides/25_데이터_생애_guide.md` 3.3
- **결정 주체:** 유지보수자 판단
- **배경:** 후보 표의 열 순서를 통일하라는 사용자 규칙(수정목록 G13)이 있다: `ID | 후보 문장 | 구분 | 공통·고유(잠정) | 출처 | (이 단계에서만 필요한 열) | 근거`. 샘플은 기능이 아닌 데이터 이전 절차를 문장 속 굵은 표시로만 구분하고(SA-37), 같은 기능의 최소판과 후속판이 후보 둘로 나뉜다(SA-38). 후보가 다루는 엔티티가 출처 서술에 묻혀 있다(OM-21).
- **검토한 대안:** (a) 18번과 19번의 열 순서(`출처`, `기능 후보`, `구분` …)를 따른다 / (b) 통일 규칙의 순서를 따르고 이 단계에서만 필요한 열을 근거 앞에 둔다 / (c) 대상 엔티티를 출처에 합친다
- **결정:** (b). 열은 `ID | 후보 문장 | 구분 | 공통·고유(잠정) | 출처 | 대상 엔티티 | 근거`이고 `구분` 선택지는 19번과 같은 어휘(기능 후보 / 후속 후보 / 설계 기준 / 프로세스)다. 대상 엔티티는 이 단계에만 필요한 열이다.
- **이유:** (a)는 사용자가 정한 통일 규칙보다 앞 단계의 모양을 우선한다. (c)는 한 칸에 정책 ID와 엔티티 ID가 섞여 샘플의 문제(SA-34)가 되풀이된다. 데이터 이전 같은 절차를 가르는 구분 값 `프로세스`가 필요하다.
- **영향:** 17~21번의 후보 표와 열 순서가 다르다. 통합·정규화 단계가 `후보 문장`, `구분`을 읽는다(IF-25-029, IF-25-032).
- **상태:** 검토 대기

### DL-25-004 · 공통 정책은 고정 질문 열두 개의 속성 표로 둔다
- **날짜:** 2026-10-09
- **대상:** `templates/25_데이터_생애_template.md` 2절 (표 `공통정책`), `guides/25_데이터_생애_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 공통 정책은 여섯 항목이고 값으로 적혀 있다(SA-23~SA-31). 도메인을 대입해 보니 더 필요한 정책이 있다: 파기를 미루는 사건(OM-07, OM-17), 파기 기록(OM-10, OM-16), 외부에 넘긴 데이터의 파기(OM-14), 기기 안 데이터(OM-15), 정정·삭제 요청을 포함한 정보 주체 요청(OM-16, OM-18).
- **검토한 대안:** (a) 샘플처럼 여섯 항목을 값으로 둔다 / (b) 여섯 항목을 질문으로 바꾸고 다섯 질문과 개방 질문을 더한다 / (c) 정책 없이 생애 정책 행의 후보로만 도출한다
- **결정:** (b). 질문 열두 개는 종료·삭제 유예, 기간 경과 파기, 분리 보관, 익명화 규칙, 파기 보류, 백업, 정보 주체 요청, 외부 전달 데이터의 파기, 기기 안 데이터, 파기 기록, 이전·변경, 개방 질문이다. 정책 ID `DL-nn`은 결정 로그 항목 ID와 앞부분이 같아 혼동되므로 `YQ`로 바꿨다(SA-24). 답이 값인 항목은 기능 후보의 출처가 된다.
- **이유:** (a)는 놓친 종류를 확인할 방법이 없다(OM-08). (c)는 서비스 전체에 걸치는 정책이 행마다 중복되거나 빠진다. 질문 수는 외부 연동 단계의 열 개보다 둘 많으나 개방 질문이 마지막에 있다.
- **영향:** 질문 열두 개가 충분한지는 도메인 교체 시험에서 본다. 열 항목 필드는 뒤 단계가 값으로 쓰지 않는 것은 `최종 소비자 없음`이다(IF-25-014, IF-25-016 등).
- **상태:** 검토 대기

### DL-25-005 · ID 접두어는 생애 정책 `YP`, 공통 정책 `YQ`, 기능 후보 `YC`로 한다
- **날짜:** 2026-10-09
- **대상:** `templates/25_데이터_생애_template.md` (정의 ID `YP`, `YQ`, `YC`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 후보 ID를 `CF-25-nn`, 정책 ID를 `DL-nn`으로 쓴다(SA-24, SA-33). 템플릿 규칙(TP-28)은 접두어가 모든 템플릿에 걸쳐 유일하라고 하고, 이번 호출은 `Y`로 시작하는 접두어만 쓰게 했다.
- **검토한 대안:** (a) 샘플의 `CF`와 `DL`을 그대로 쓴다 / (b) `Y`로 시작하는 접두어를 쓴다
- **결정:** (b). `YP`(Policy), `YQ`(Question), `YC`(Candidate)이고 `01`부터 연번이다.
- **이유:** 다른 단계를 만드는 에이전트와 접두어가 겹치는 것을 막는다(TP-K14가 검사한다). `DL`은 결정 로그 ID와 혼동된다.
- **영향:** 분석서 SA-24, SA-33에 기록했다.
- **상태:** 검토 대기

### DL-25-006 · 25번이 앞 단계로 보내는 환류 줄을 인터페이스 표에 둔다
- **날짜:** 2026-10-09
- **대상:** `tools/data/interfaces.csv` (IF-25-003, IF-25-005, IF-25-013, IF-25-015, IF-25-018, IF-25-027, IF-25-030, IF-25-033)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 `22(복구 목표 근거)`를 쓰이는 곳으로 적는데 22가 25보다 앞 번호라 순서 오류다(SA-29, OM-22). 기간 경과 파기와 유예 만료는 시간이 계기인 동작이라 시간·주기 단계가 정의하는데, 이 단계에서 처음 드러날 수 있다(OM-12). 분리 보관은 접근 통제 위협의 대상이다.
- **검토한 대안:** (a) 환류 줄을 두지 않는다 / (b) 22(보존 기간, 백업)와 14(기간 경과 시, 종료·삭제 유예)와 24(분리 보관)와 20(후보의 공통·고유 판정 입력)에 환류 줄을 둔다
- **결정:** (b). 모두 방향 `환류`이고 근거에 `추정: 가정`을 쓴 것은 샘플의 표시가 없는 연결이다. 백업→22는 샘플의 쓰이는 곳 표시와 단계 정의가 뒷받침한다(필수 `예`).
- **이유:** (a)는 이 단계에서 발견한 누락 동작과 복구 목표가 앞 단계로 돌아가는 흐름이 표에 남지 않는다. 환류가 일어나면 앞 단계 문서의 버전을 올리고 결정 로그에 기록한다(IR-06).
- **영향:** 사용자가 환류를 인정하지 않으면 해당 줄을 지우고 가이드 3.1의 시간·주기 문장과 3.2의 백업 문장을 고친다.
- **상태:** 검토 대기

### DL-25-007 · 인터페이스 표: 25번 보내는 줄 36개와 외부 입력 줄 2개를 추가하고 잠정 줄 11개를 필드 수준으로 바꾼다
- **날짜:** 2026-10-09
- **대상:** `tools/data/interfaces.csv` (IF-25-001~036, IF-EX-25-001~002 추가, IF-03-048, IF-03-050, IF-11-006, IF-11-011, IF-11-016, IF-11-018, IF-11-025, IF-11-028, IF-11-029, IF-12-008, IF-14-018 수정)
- **결정 주체:** 유지보수자 판단
- **배경:** 25번 템플릿 필드 30개(생애정책 11, 공통정책 12, 기능후보 7)는 모두 보내는 필드로 한 줄 이상 나와야 한다(IR-07). 쓰이는 곳은 샘플의 표시 `후보 풀로 합류 · 22(복구 목표 근거) · 36(필수 게이트: 삭제권 등)`(SA-08)과 단계 정의다. 받는 쪽이 `25`인 잠정 줄 11개는 필드 키로 바꿀 수 있게 되었다(IR-10).
- **검토한 대안:** (a) 25번이 받는 입력(범위·제약, 비사람 액터 등)도 줄로 더한다 / (b) 보내는 줄과 기존 잠정 줄만 다룬다
- **결정:** (b)이고 소비자는 샘플과 단계 정의가 뒷받침하는 만큼만 주장했다. 샘플의 표시가 없는 연결에는 근거에 `추정: 가정`을 썼다. 수정한 줄의 받는 쪽: IF-03-048→`25.생애정책.법정 보존`, IF-03-050→`25.생애정책.보존 기간`, IF-11-006→`25.생애정책.엔티티`, IF-11-011→`25.생애정책.보존 기간`, IF-11-016→`25.생애정책.계정 종료 시`, IF-11-018→`25.생애정책.기간 경과 시`, IF-11-025·028·029→`25.생애정책.계정 종료 시`, IF-12-008→`25.생애정책.열람·내보내기`, IF-14-018→`25.생애정책.기간 경과 시`. 근거에 이 항목의 ID를 덧붙였다. 외부 입력은 `EXT:데이터_보존_정책_자료`(보존 기간)와 `EXT:백업_복구_운영_자료`(백업)다(OM-02, OM-09). 후보 표는 31번(ID, 후보 문장, 구분, 출처), 20번(ID, 후보 문장, 공통·고유(잠정)), 32번(ID), 34번(ID, 대상 엔티티), 36번(후보 문장)에 연결했다. 22, 23, 24, 26, 31, 32, 33, 34, 36번 템플릿은 아직 없어 받는 쪽은 문서 수준 잠정 값이다.

### DL-25-009 · 가이드에 둔 판단 기준: 모르는 기간 닫기, 법정 보존 판단, 계정 종료 시의 처리 선택
- **날짜:** 2026-10-09
- **대상:** `guides/25_데이터_생애_guide.md` 3.1, 3.2, 5절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 보존 기간은 모두 예시이고 `법무 확인`이 값 옆에 붙어 있다(SA-04, SA-14, OM-03). 보존 기간이나 복구 목표를 그럴듯하게 쓰면 법정 보존 위반이나 과잉 보관으로 이어진다. 한 엔티티에서 처리가 갈리는 경우(OM-23, OM-25)와 시간 기반 기능과의 경계(OM-12), 엔티티가 아닌 저장물(OM-19)은 선택지 하나로 닫히지 않는다.

- **영향:** 입력이 얇으면 `미정`이 많아질 수 있다. 이는 구조의 결함이 아니라 입력 부족이다. 도메인 교체 시험에서 확인한다.

### DL-25-011 · 제안: 22~25번이 서로 읽는 잠정 줄과 표 사이의 정합 검사를 정할지 사용자가 정한다
- **날짜:** 2026-10-09

- **배경:** 25번 세트를 만들며 도구가 확인하지 못하는 곳 셋을 만났다. (1) 생애 정책의 엔티티 칸이 엔티티 목록의 모든 엔티티를 정확히 한 번씩 덮는지, 기능 후보의 출처 ID가 앞 표에 있는지는 값을 맞대 보아야 안다(OM-01). 현재 산출물 검사(TP-K13)는 구조만 비교한다.
