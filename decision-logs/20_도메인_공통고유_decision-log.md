### DL-20-001 · 20번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `conversions/20_도메인_공통고유_conversion.md`, `templates/20_도메인_공통고유_template.md`, `guides/20_도메인_공통고유_guide.md` (04번, 05번, 08번에 이은 복제)
- **결정 주체:** 사용자 승인 (그룹 단위 진행을 승인함(DL-05-005))
- **배경:** 샘플 해부 45행(SA-01~45)과 누락 탐색 18행(OM-01~18)을 같은 절차로 만들었다. 단계 정의의 목적은 후보를 서비스 고유의 것과 여러 영역이 공유하는 것으로 가려 공통 기능을 한 번만 만들 수 있게 하는 것이고 산출물은 공통·고유 판정이 붙은 후보와 공통 기능 목록 초안이다. 08번(액터 공통·고유)은 목표를 액터 기준으로 가르는 단계인 반면 이 단계는 여러 앞 단계의 후보를 기능 기준으로 가른다. 샘플은 후보를 클러스터 단위로 판정하고 판정 기준이 순서대로 읽히지 않으며(SA-12, SA-13), 혼합 사례와 공통 기능 목록이 후보와 이어지지 않는다(SA-25, SA-33).
- **검토한 대안:** 04·05번처럼 도출 질문 → 후보 → 판정 → 목록의 네 단계로 구성하는 안, 08번처럼 공통 정의 → 판정 → 집계의 세 표로 구성하는 안, 08번 구성에 혼합 분리와 신규 후보를 더하는 안을 비교했다. 후보가 이미 앞 단계에서 주어져 후보를 찾는 질문이 필요 없으므로 첫 안은 버렸다. 08번 구성만으로는 판정 값 `혼합`의 뒤처리(공통 장치와 고유 정책의 분리, 새로 정의할 후보)를 담을 표가 없어 셋째 안을 골랐다.
- **결정:** 값 표 다섯을 둔다. 공통기능(목록 표, 정의 ID `DC`), 후보판정(목록 표, 정의 ID 없음), 신규후보(목록 표, 정의 ID `DF`), 혼합분리(목록 표, 정의 ID 없음), 집계(속성 표, 정의 ID 없음). 필드는 모두 26개다. 선택 블록과 표 없는 절은 없다. 샘플의 `판정 기준` 절은 단계 가이드가, 클러스터 표는 후보판정 표가, 혼합 사례 표는 후보판정 표의 판정 값과 혼합분리 표가, 공통 기능 목록은 공통기능 표가, 후보 풀로 전달 표는 신규후보 표가 맡는다(SA-09, SA-13, SA-21, SA-28, SA-35).
- **이유:** 템플릿의 모든 표와 필드가 분석서의 줄에 대응한다(정의서 6절 4번). 08번과의 차이(판정 단위가 목표가 아니라 여러 표에서 온 후보, 판정 값에 혼합, 신규 후보)는 분석서 머리말에 정리했다.
- **영향:** 도메인 교체 시험(작업 순서 8번)이 남았다. 시험 전까지 변환 분석서의 상태는 `초안`이다. 인터페이스 표는 DL-20-002, DL-20-003.
- **상태:** 유효

### DL-20-002 · 인터페이스 표: 잠정 줄 9개를 필드 수준으로 바꾸고 20번 보내는 줄 35개를 추가한다
- **날짜:** 2026-10-08
- **대상:** `tools/data/interfaces.csv` (IF-09-026, IF-10-009, IF-12-020, IF-13-035, IF-14-038, IF-15-004, IF-15-016, IF-15-035, IF-16-016 수정, IF-20-001~035 추가)

- **이유:** 템플릿 필드마다 소비자가 있거나 사유가 있어야 한다. 집계는 이 산출물 안의 완결성 점검이라 뒤 단계가 값으로 쓰는 근거가 없어 소비자를 만들지 않았다(08번의 선례).
- **영향:** 21, 29, 31, 32, 33, 36번 템플릿이 생기면 해당 잠정 줄을 필드 수준으로 바꾼다. 아래 DL-20-003의 입력 줄을 더하기 전에는 20번 템플릿 머리말의 입력이 후보 표의 잠정 구분 칸과 소유·권한의 두 칸만 보인다.
- **상태:** 검토 대기

### DL-20-004 · 판정을 클러스터가 아니라 후보 단위로 하고 영역·묶음 이름을 표에 두지 않는다
- **날짜:** 2026-10-08
- **대상:** `templates/20_도메인_공통고유_template.md` 2절 (표 `후보판정`), `guides/20_도메인_공통고유_guide.md` 2절, 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 영역 후보 클러스터마다 대표 후보의 ID 범위와 판정을 쓴다(SA-13, SA-15). 클러스터 이름은 영역 구성을 앞서 정하며 영역은 다음 이후 단계가 정한다(SA-14). 단계 정의의 산출물은 판정이 붙은 후보다. 후보를 낸 앞 단계는 일곱이고 후보 표마다 ID 접두어가 다르다(OM-01, OM-02, OM-05). 판정을 못 내리는 후보를 둘 곳도 없다(OM-03).
- **검토한 대안:** (가) 샘플처럼 클러스터 표를 둔다 / (나) 후보 단위 표에 묶음 열을 더한다 / (다) 후보 단위 표만 두고 묶음은 작성자의 메모로 한다
- **결정:** (다). 입력 후보마다 한 행을 쓰고 열은 후보 ID, 기능 후보, 잠정 구분, 판정, 공통 기능 ID, 근거다. 묶음은 단계 가이드 2절에서 판단하는 데 쓰라고만 하고 산출물에 쓰지 않는다. 집계가 입력 후보 수와 합계를 맞춰 누락을 드러낸다(DL-20-008).
- **이유:** (가)는 판정되지 않은 후보를 찾을 수 없다. (나)의 묶음 이름은 영역 구성을 앞서 정하는 값이 되어 영역·모듈 단계와 어긋난다. 후보가 많으면 행이 늘어나지만 칸 수를 줄이려고 묶음 행을 만들지 않는 것이 이 체계의 원칙이다.
- **영향:** 후보가 수백 개인 프로젝트에서는 표가 길어진다. 사용자 확인이 필요한 질문이다: 행 수 부담이 크면 클러스터 대표 판정을 허용할지. 도메인 교체 시험에서 행 수 부담을 본다.
- **상태:** 검토 대기

### DL-20-005 · 판정 값을 공통·고유·혼합으로 하고 질문 순서를 고친다
- **날짜:** 2026-10-08
- **대상:** `templates/20_도메인_공통고유_template.md` 2절 (필드 `판정`), `guides/20_도메인_공통고유_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 판정 기준은 질문 1이 `예`이면 공통으로 끝나, 알림과 이미지처럼 질문 1이 `예`인 기능이 혼합으로 판정된 사례와 맞지 않는다(SA-12). 클러스터 표의 판정은 공통·고유 둘뿐이라 섞인 경우의 근거가 근거 칸 문장에만 남는다(SA-16, SA-20). 08번의 `시스템`은 액터 축의 값으로 도메인 축에 대응이 없다(OM-06).
- **검토한 대안:** (가) 공통·고유 둘로 줄이고 혼합은 후보를 나눠 두 행으로 쓴다 / (나) 샘플의 순서대로 두고 혼합을 질문 3으로 둔다 / (다) 섞임을 먼저 묻고 판정 값에 `혼합`을 둔다
- **결정:** (다). 질문은 섞임, 업무 개념 없이 쓸 수 있는가, 여러 고유 후보가 일반적으로 부르는가의 순서다. 혼합은 정책을 장치에 설정이나 등록으로 넣을 수 있을 때만 쓰고 규칙이 기능의 본질이면 분리하지 않고 고유로 둔다. 공통과 고유 사이에서 갈리면 앞 단계들처럼 `고유`를 고른다.
- **이유:** (가)는 입력 후보 한 행을 둘로 나누게 되어 후보 ID가 유일하지 않고 집계와 입력 후보 수가 어긋난다. (나)는 샘플의 순서 오류를 그대로 둔다. 갈리면 고유로 두는 기준은 앞 단계의 잠정 구분 기준과 같다.
- **영향:** 사용자 확인이 필요한 질문이다: 이 단계에서도 갈릴 때 `고유`를 고르는 것이 맞는가. 뒤에 바로잡을 단계는 표준 카탈로그 대조와 유사 서비스 대조뿐이다.
- **상태:** 검토 대기

### DL-20-006 · 공통 기능 표를 판정 표보다 앞에 두고, 호출 관계를 후보 ID로 쓴다
- **날짜:** 2026-10-08
- **대상:** `templates/20_도메인_공통고유_template.md` 1·2절 (표 `공통기능`, `후보판정`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 공통 기능 목록(COM)이 후보와 이어지지 않아 어느 후보가 어느 공통 기능으로 가는지, 공통 기능이 후보에서 나왔는지 알 수 없다(OM-04, SA-33). 호출하는 쪽은 영역 이름으로 쓰는데 영역은 뒤 단계가 정한다(SA-31). 이 단계의 판정이 공통 기능 ID를 참조해야 해서 정의 표가 앞서야 한다(TP-16, 08번의 DL-08-003과 같다).
- **검토한 대안:** (가) 샘플 순서(판정 → 공통 기능 목록)를 유지하고 판정 표가 공통 기능 ID를 뒤에서 참조한다 / (나) 공통 기능 표에 흡수한 후보 열을 둔다 / (다) 공통 기능 표를 앞에 두고 판정 표의 열이 ID를 참조하게 한다
- **결정:** (다). 호출하는 쪽은 `대표 호출 후보`로 후보 ID(또는 `전체`)를 쓰고 호출 관계 전체는 의존성 단계에 맡긴다. 공통 기능은 가리키는 후보가 한 개 이상 있어야 하며 후보에 없는 범용 기능은 표에 올리지 않는다.
- **이유:** (가)는 TP-16 위반이다. (나)는 후보가 어느 공통 기능으로 가는지를 두 곳에 쓰게 되어 어긋날 수 있다(CM-12).
- **영향:** 후보 판정 표의 `공통 기능 ID`가 공통 기능 표의 ID와 맞는지는 도구가 검사하지 못하고 완료 체크와 가이드의 누락 점검이 맡는다(DL-16-009와 같은 한계).
- **상태:** 검토 대기
