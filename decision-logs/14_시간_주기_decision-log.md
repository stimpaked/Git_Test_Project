### DL-14-001 · 14번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `conversions/14_시간_주기_conversion.md`, `templates/14_시간_주기_template.md`, `guides/14_시간_주기_guide.md` (작업 순서 6단계, 04~10번에 이은 복제)
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 샘플 해부 36행(SA-01~36)과 누락 탐색 20행(OM-01~20)을 앞 단계와 같은 절차로 만들었다. 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 분석서의 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 "도출 질문 → 후보 → 판정 → 목록" 흐름을 따르지 않고 단계의 목적(시간이 계기가 되는 동작을 정리해 사용자가 일으키지 않는 기능을 찾는다)에서 구성을 정했다. 구성은 ① 공통 시간 기준(속성 표) ② 시간 계기 점검(`TQ`) ③ 타이머 목록(`T`) ④ 입력 대응 ⑤ 기능 후보(`TC`)다. 샘플은 앞 단계가 지목한 항목만 타이머 표로 옮겼으므로 입력 밖의 시간 계기를 찾는 점검과, 입력이 타이머로 이어졌는지 남기는 대응 표를 더했다(OM-01, OM-05). 샘플 2절의 매핑은 타이머 정의 뒤에 두어 순서를 지킨다(SA-22). 후보 표는 새 후보와 공통 기반을 가리도록 출처와 관련 후보를 정했다(OM-06, OM-07).
- **이유:** 샘플을 해부하고 누락을 찾은 결과가 템플릿의 모든 변경에 대응한다(정의서 6절 4번, 검사 CV-K04).
- **영향:** 도메인 교체 시험과 변환 분석서 `승인`이 남았다. 11, 13, 16, 20, 22, 24~26, 31, 34번 템플릿이 생기면 인터페이스 표의 잠정 줄을 필드 수준으로 바꾼다.
- **상태:** 유효

### DL-14-002 · 시간 계기 점검을 열한 관점의 속성 표로 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/14_시간_주기_template.md` 2절 (표 키 `시간계기점검`, 정의 ID `TQ`), `guides/14_시간_주기_guide.md` 3.2절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 13번의 시간 전이, 05번의 시간 액터, 07번의 목표에서 이미 지목된 항목을 타이머로 옮길 뿐 입력에 드러나지 않은 시간 계기를 찾는 질문이 없다(OM-01). 점검을 하더라도 타이머가 어느 관점에서 나왔는지 연결할 방법이 없다(OM-02).
- **검토한 대안:** (a) 점검 없이 입력 항목만 옮기는 샘플의 방식 / (b) 05번처럼 후보 정리와 판정까지 잇는 질문 표 / (c) 관점 열한 개의 속성 표를 두고 타이머의 출처 열이 관점을 가리키게 한다
- **결정:** (c). 관점은 유효기간·만료, 갱신·재확인, 알림·리마인드, 대기·방치 처리, 기간 한정 상태, 예약 실행, 정리·보존, 집계·동기화, 감시·경고, 실패 재시도, 개방 질문이다. 질문의 답은 찾은 일의 이름과 하는 일이고 후보 정리나 판정 표는 두지 않는다. 타이머가 곧 후보이기 때문이다.
- **이유:** (a)는 입력에 시간 조건이 안 드러난 일을 놓친다. (b)는 이 단계에서 병합·분리를 판정할 일이 없어 표만 늘린다. (c)는 샘플의 타이머 22건이 모두 열한 관점 중 하나 이상에 속하고, 샘플에 드문 갱신, 감시, 재시도를 놓치지 않게 한다.
- **영향:** 열한 필드는 뒤 단계가 값으로 쓰지 않아 `최종 소비자 없음`이다(DL-14-005). 답이 값인 관점에 타이머가 있는지는 완료 체크로만 확인하고 도구가 확인하지 못한다. 관점 열한 개가 충분한지는 도메인 교체 시험에서 확인한다.
- **상태:** 검토 대기

### DL-14-003 · 타이머 표: 유형 네 값, 시간 조건의 세 칸 분리, 취소 조건 추가
- **날짜:** 2026-10-08
- **대상:** `templates/14_시간_주기_template.md` 3절 (표 키 `타이머`), `guides/14_시간_주기_guide.md` 3.3절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 유형 세 가지(TTL, 주기, 지연)는 서로 겹치고 정해진 날짜와 시각의 일을 담지 못한다(SA-11, SA-15, OM-04). `주기·지연` 열은 기준, 실행 시각, 점검 간격을 섞고(SA-16, OM-03), `정책값(예시)`는 전부 예시 값이다(SA-18). 동작을 없애거나 시계를 다시 시작시키는 조건을 쓸 곳이 없다(OM-17, OM-19). 담당 후보 열은 같은 문서 뒤에서 부여하는 ID를 미리 가리킨다(SA-20).
- **검토한 대안:** (a) 샘플의 세 유형을 유지한다 / (b) 유형을 `경과 후 1회` / `기준 시각 전후 1회` / `지정 시각 1회` / `반복` 넷으로 하고 `주기·지연`을 기준, 시간 조건, 허용 지연 셋으로 나눈다 / (c) 유형을 더 잘게 나눈다(유효기간 만료, 유예 종료, 리마인드를 따로)
- **결정:** (b). 열은 ID, 이름, 대상, 유형, 기준, 시간 조건, 취소 조건, 허용 지연, 동작, 실패 시, 관련 후보, 출처, 근거 13개다. 구현이 점검 방식이어도 유형은 요구의 모양으로 쓰고 점검 간격에서 오는 오차는 허용 지연에 쓴다. 관련 후보는 앞 단계 산출물의 ID만 쓰고, 이 단계의 새 후보는 후보 표가 타이머를 가리킨다(OM-07).
- **이유:** (a)는 예약 실행과 일정 앞 알림을 점검 방식에 가려 버린다. (c)는 같은 모양의 일을 서비스 용어로 나누어 선택지가 도메인에 묶인다. 허용 지연은 뒤 단계의 성능·모니터링 기준이 필요로 하는 값이고 점검 간격과 요구를 구별하게 한다(OM-20). 취소 조건은 이미 끝난 일을 시간이 되어 다시 실행하는 오류를 막는다.
- **영향:** 허용 지연과 취소 조건이 입력에 없으면 `미정`이 많아질 수 있다. 도메인 교체 시험에서 `미정`의 양과 작성자의 부담을 확인한다. 13열의 목록 표는 04번과 비슷한 너비다.
- **상태:** 검토 대기

### DL-14-004 · 입력 대응과 기능 후보 표의 구성
- **날짜:** 2026-10-08
- **대상:** `templates/14_시간_주기_template.md` 4, 5절 (표 키 `입력대응`, `기능후보`, 정의 ID `TC`), `guides/14_시간_주기_guide.md` 3.4, 3.5절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 2절 매핑은 목표만 다루고 전이는 완료 체크로만 확인하며, 목표 열에 ID와 이름을 함께 쓴다(SA-22, SA-23, OM-05). 3절 후보 표는 타이머를 묶은 후보와 타이머 전체의 공통 기반을 섞고 출처를 줄여 쓴다(SA-29, SA-32, OM-06).
- **검토한 대안:** (a) 목표 매핑만 샘플처럼 둔다 / (b) 입력 항목의 종류를 열로 가르는 표 / (c) 입력 항목 ID, 타이머 ID, 근거 세 열의 표로 두고 종류는 ID 접두어와 가이드로 구별한다. 후보 표는 출처에 타이머 ID 또는 `전체`를 쓰고 관련 후보가 있는 타이머는 올리지 않는다
- **결정:** (c). 입력 항목이 시간 계기가 아니면 타이머 칸을 `해당 없음`과 사유로 닫는다(OM-16). 공통 기반 다섯(스케줄 등록, 중복 실행 방지, 재시도, 실행 이력과 수동 재실행, 실패 알림)을 점검하도록 가이드에 두고 후보의 출처를 `전체`로 한다(OM-06). 관련 후보가 `해당 없음`인 타이머가 후보의 출처에 나오는지는 완료 체크로 확인한다.
- **이유:** (b)는 13번 템플릿의 ID 형식을 모르는 상태에서 종류 선택지를 고정해야 한다. (c)는 열이 적고 모든 입력 항목이 타이머로 이어졌는지 한눈에 본다. 이 단계의 가치는 앞 단계 후보에 없던 새 후보를 찾는 것이므로 관련 후보와 후보의 출처를 연결한다(OM-07).
- **영향:** 입력 항목의 종류는 ID 접두어로만 구별되고, 전이의 ID 형식은 13번 세트가 정한다. 입력 대응과 기능 후보의 완전성은 도구가 확인하지 못한다.
- **상태:** 검토 대기

### DL-14-005 · 인터페이스 표: 14번 연결 39줄을 추가하고 05·09번 잠정 줄 3줄을 바꾼다
- **날짜:** 2026-10-08
- **대상:** `tools/data/interfaces.csv` (IF-14-001~039 추가, IF-05-029, IF-05-033, IF-09-011 수정)
- **결정 주체:** 유지보수자 판단
- **배경:** 14번 템플릿 필드 35개는 보내는 필드로 한 줄 이상 나와야 한다(IR-07). 쓰이는 곳은 샘플의 표시(SA-09: 후보 풀 합류, 공통·고유 판정, 성능·모니터링 기준)와 단계 정의로 뒷받침하고, 뒷받침이 없으면 근거에 `추정: 가정`을 썼다. 05번(비사람 액터의 유형, 주고받는 정보)과 09번(목표 매핑의 다룬 곳)이 14번에 보내던 잠정 줄(받는 쪽 `14`)은 14번 필드로 바꿀 수 있게 되었다(IR-10).
- **검토한 대안:** (a) 14번이 받는 입력(07의 목표, 05의 ID, 11의 엔티티, 13의 전이, 10의 추가 질문, 02·03의 기간 근거)도 줄로 더한다 / (b) 14번이 보내는 줄과 05·09번 잠정 줄만 다룬다
- **결정:** (b). 보내는 줄 39개 중 소비자가 있는 줄이 20개(받는 쪽 템플릿이 없어 모두 문서 수준 잠정 값, 환류 1줄 포함)이고 `최종 소비자 없음`이 19개다. 수정한 줄은 IF-05-029(→ `14.입력대응.입력 항목`), IF-05-033(→ `14.타이머.시간 조건`), IF-09-011(→ `14.입력대응.입력 항목`)이다. 근거에 이 항목의 ID를 덧붙였다. 받는 단계 13, 16, 24, 25, 26, 31, 34의 소비자 줄과 22번 일부는 샘플의 표시로 뒷받침되지 않아 근거에 `추정: 가정`을 썼다.
- **이유:** 연결 ID가 보내는 단계 번호로 시작하므로(IR-04) 07, 11, 13 등의 줄은 그 단계 세트가 만들어야 하고, 같은 CSV를 고치는 다른 세트와 ID가 겹치지 않게 한다. 사람·비사람 액터 ID는 목표 목록을 거쳐 받는 것으로 보아 05번 ID에서 14번으로 직접 가는 줄도 만들지 않았다.
- **영향:** 14번 템플릿의 입력(생성 블록)에는 05번과 09번만 나온다. 그룹 병합 때 07(목표 ID·액터), 11(엔티티), 13(시간이 계기인 전이), 10(기다림 질문), 02·03(기간 근거)에서 14번으로 오는 줄을 더해야 한다. 11, 13, 16, 20, 22, 24, 25, 26, 31, 34번 템플릿이 생기면 14번의 잠정 줄을 필드 수준으로 바꾼다.
- **상태:** 검토 대기

### DL-14-006 · 시간 조건의 값은 입력에서만 가져오고 없으면 `미정`으로 닫는다
- **날짜:** 2026-10-08
- **대상:** `guides/14_시간_주기_guide.md` 3.3, 5절, `templates/14_시간_주기_template.md` 3절 (`타이머.시간 조건`, `타이머.허용 지연`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 기간과 횟수는 전부 예시 값이고 `법무 확인 필요`처럼 값이 아닌 말이 값 열에 있다(SA-04, SA-18). 입력에 기간이 없을 때 닫는 방법이 샘플에 없다(OM-09).
- **검토한 대안:** (a) 입력에 없으면 합리적인 값을 쓰고 `가정`으로 표시한다(공통 가이드 3절 2번) / (b) 입력에 없으면 `미정`(확인처·담당·기한)으로 닫는다
- **결정:** (b). 일부만 알면 아는 값 뒤에 `미정`을 이어 쓴다(CM-07). 규제가 정하는 기간은 확인처를 법무 담당으로 쓴다.
- **이유:** 기간은 정책 값이라 틀린 값이 뒤 단계(성능 요구, 규제 매핑, 데이터 생애 정책)로 퍼지면 되돌리기 어렵다. 공통 가이드 3절 3번(가정하기 어렵거나 틀리면 이후 단계가 크게 흔들리면 `미정`)을 이 단계에 적용한 것이고 가장 보수적인 쪽이다.
- **영향:** `미정` 칸이 많아질 수 있다. 도메인 교체 시험에서 확인한다.
- **상태:** 검토 대기

### DL-14-007 · 공통 시간 기준을 속성 표로 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/14_시간_주기_template.md` 1절 (표 키 `시간기준`), `guides/14_시간_주기_guide.md` 3.1절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 `1일(03:00)`, `전일 20시`처럼 시간대 없이 시각을 쓴다(OM-12). 휴일과 말일, 서버와 기기 중 어느 시계로 판정하는지도 정해져 있지 않다(OM-14, OM-18).
- **검토한 대안:** (a) 타이머 표에 시간대 열을 둔다 / (b) 서비스 전체에 하나씩 쓰는 속성 표(기준 시간대, 기준 시계, 달력 규칙)를 앞에 둔다 / (c) 표 없이 가이드에서만 안내한다
- **결정:** (b).
- **이유:** (a)는 대부분의 타이머에서 값이 같아 칸이 반복된다. (c)는 확인이 도구에 잡히지 않고 근거를 남길 곳이 없다. 세 항목은 서비스 전체의 결정이다.
