### DL-19-001 · 19번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `conversions/19_외부연동_conversion.md`, `templates/19_외부연동_template.md`, `guides/19_외부연동_guide.md` (작업 순서 6단계, 04~16번에 이은 복제)
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 샘플 해부 36행(SA-01~36)과 누락 탐색 21행(OM-01~21)을 앞 단계와 같은 절차로 만들었다. 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 구성(도출 질문 → 후보 → 판정 → 목록)을 따르지 않고 이 단계의 목적(외부 시스템 연동에 필요한 설정·장애 대응·재시도·모니터링 기능을 도출한다)에 맞춰 값 표를 셋으로 둔다. 1번 표 `연동정의`는 연동 하나를 행 하나로 하는 목록(정의 ID `IG`), 2번 표 `공통점검`은 여러 연동에 걸치는 연동 기능을 찾는 고정 질문 열 개(정의 ID `IQ`, 속성 표), 3번 표 `기능후보`는 두 표에서 도출한 후보(정의 ID `IC`)다(SA-10, SA-21, SA-26, OM-01, OM-08). 그림이나 표 없는 필수 블록, 선택 블록은 없다.
- **이유:** 이 단계의 본질은 연동 대상마다 다섯 측면(연동 자체, 설정·키 관리, 장애 시 동작, 재시도·한도, 모니터링·비용)을 빠짐없이 정하고 그 결과를 기능 후보로 모으는 것이다. 후보를 찾는 도출 질문이 필요한 곳은 연동 하나의 칸이 아니라 여러 연동에 걸치는 기능뿐이다. 템플릿의 모든 변경이 분석서의 줄에 대응한다(정의서 6절 4번).
- **영향:** 도메인 교체 시험(8번)이 남았다. 인터페이스 표에 19번 보내는 줄 33개를 더하고 잠정 줄 6개를 바꿨다(DL-19-007).
- **상태:** 유효

### DL-19-002 · 연동 정의는 연동 하나를 행 하나로 두고 ID 열을 더하며 담당 후보 열을 지운다
- **날짜:** 2026-10-08
- **대상:** `templates/19_외부연동_template.md` 1절 (필드 `ID`, `액터`, `방향`, `주고받는 정보`, `설정·키 관리`), `guides/19_외부연동_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 외부 액터 하나에 행 하나를 두고(SA-10), 액터 열에 ID와 이름을 한 칸에 묶고(SA-11), `입력 → 출력`으로 방향을 괄호와 화살표로 암시하며(SA-14, SA-20), 설정·키 관리 열이 없고(SA-08), `담당 후보` 열이 3절의 후보 ID를 앞서 참조한다(SA-18). 한 액터에 호출 시점과 정보가 다른 연동이 둘 이상인 경우가 있다(OM-10).
- **검토한 대안:** (a) 샘플처럼 액터 하나에 행 하나를 두고 칸 안에 여러 연동을 적는다 / (b) 연동 하나를 행 하나로 하고 행에 ID를 붙여 후보의 출처가 가리키게 한다 / (c) 연동 정의를 액터 표와 연동 표로 둘로 나눈다
- **결정:** (b). 행마다 `IG-01`부터 ID를 부여하고, 액터 칸은 비사람 액터 목록의 ID 참조로 쓰며, 방향을 비사람 액터 목록과 같은 어휘의 선택지 열로 둔다. `입력 → 출력`은 비사람 액터 목록과 같은 이름 `주고받는 정보`로 바꾸고 보내는 것과 받는 것의 순서를 힌트가 말한다. 설정·키 관리 열을 더하고 담당 후보 열은 지운다. 후보 쪽의 `출처`가 연동 ID를 가리킨다(OM-01, OM-03, OM-06).
- **이유:** (a)는 한 칸에 서로 다른 장애 동작이 섞여 칸을 닫기 어렵다. (c)는 액터 정보를 비사람 액터 목록이 이미 갖고 있어 같은 사실을 두 곳에 쓰게 된다(CM-12). (b)는 다섯 측면을 연동마다 닫으면서 앞 표가 뒤 표의 ID를 참조하는 순서 오류(TP-16)를 없앤다.
- **영향:** 행 수가 액터 수보다 늘 수 있다. 연동 정의와 기능 후보가 서로 맞는지는 도구가 검사하지 못하고 완료 체크가 맡는다(DL-19-010).
- **상태:** 검토 대기

### DL-19-003 · 연동 대상 액터를 외부 시스템·장치·자동 호출 주체로 한정하고 시간이 계기인 호출은 가리키기만 한다
- **날짜:** 2026-10-08
- **대상:** `guides/19_외부연동_guide.md` 1절, 3.1, 6절, `templates/19_외부연동_template.md` (완료 체크)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 외부 시스템 일곱 개만 다룬다. 비사람 액터에는 외부 시스템 말고 장치(서비스로 값을 보내오는 것)와 자동 호출 주체(서비스를 호출하는 프로그램)가 있고, 시간 트리거는 시간이 계기인 기능을 다루는 단계가 따로 있다(OM-05, OM-16). 호출 시점이 시간인 연동은 그 단계와 같은 동작을 두 번 정의할 위험이 있다(OM-17).
- **검토한 대안:** (a) 비사람 액터를 모두 연동 정의의 대상으로 한다 / (b) 외부 시스템만 대상으로 한다(샘플 그대로) / (c) 외부 시스템·장치·자동 호출 주체를 대상으로 하고 시간 트리거는 제외한다
- **결정:** (c). 시간이 계기인 호출은 호출 시점에 시간 기반 기능의 ID를 쓰고 그 기능의 실패 시와 재시도는 되풀이하지 않고 가리킨다. 방향이 `액터→서비스`인 연동은 재시도·한도 칸을 외부의 재전송을 받는 규칙과 서비스가 외부에 허용하는 한도로 읽는다. 장애 시 동작은 진행하는지 막는지를 먼저 쓴다(OM-16, OM-21).
- **이유:** (a)는 시간 트리거를 두 단계가 정의한다. (b)는 장치와 자동 호출 주체의 설정·한도·장애 대응을 빠뜨린다. 판단 기준은 조건이 있는 문장이라 가이드에 쓴다(정의서 4절 판별법 2).
- **영향:** 완료 체크가 시간 트리거 액터가 연동 정의에 없는지 확인한다. 시간 기반 기능의 ID는 인터페이스 표의 입력 줄(DL-19-008)로 이어진다.
- **상태:** 검토 대기

### DL-19-004 · 공통 점검 질문 열 개를 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/19_외부연동_template.md` 2절 (표 `공통점검`), `guides/19_외부연동_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 공통 연동 항목은 세 개이고 값으로 적혀 있다(SA-21, SA-25). 도메인을 대입해 보니 여러 연동에 걸쳐 필요한 연동 기능이 더 있다: 재시도 때 같은 요청을 두 번 처리하지 않게 하는 규칙(OM-14), 한 외부 액터의 장애 격리와 대체 경로 전환(OM-15), 외부가 보내오는 요청의 검증과 중복 걸러내기(OM-13), 외부 변경 대응(OM-20), 시험 환경(OM-12), 외부로 나가는 개인 정보 관리(OM-11).
- **검토한 대안:** (a) 샘플처럼 세 항목만 값으로 둔다 / (b) 세 항목을 질문으로 바꾸고 일곱 질문과 개방 질문을 더한다 / (c) 공통 점검 없이 각 연동 행의 후보로만 도출한다
- **결정:** (b). 열 질문의 답은 필요한 기능과 대상 연동 ID이고, 값으로 닫은 항목은 기능 후보의 출처가 된다. 질문마다 어느 칸을 보고 답하는지는 가이드가 말한다.
- **이유:** (a)는 점검 질문 없이 값으로만 적어 놓친 종류를 확인할 방법이 없다(OM-08). (c)는 여러 연동에 걸치는 기능이 연동마다 중복되거나 빠진다. 질문 수는 시간·주기 단계의 열한 질문보다 하나 적고, 개방 질문으로 나머지를 잡는다.
- **영향:** 질문 열 개가 충분한지는 도메인 교체 시험에서 본다. 열 필드는 뒤 단계가 값으로 쓰지 않아 `최종 소비자 없음`이다(DL-19-007). 법령 매핑과 위협 목록은 규제·정책, 보안·어뷰징 단계의 몫이라 이 단계는 기능만 드러낸다.
- **상태:** 검토 대기

### DL-19-005 · 기능 후보의 구분에 `프로세스`를 더하고 공통·고유(잠정) 이름을 최근 단계에 맞춘다
- **날짜:** 2026-10-08
- **대상:** `templates/19_외부연동_template.md` 3절 (필드 `구분`, `공통·고유(잠정)`), `guides/19_외부연동_guide.md` 3.3
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 기능이 아닌 출시 절차를 문장 속 굵은 표시로 구분한다(SA-31). 시나리오 5유형과 이벤트 단계는 `구분`(기능 후보 / 후속 후보 / 설계 기준)을 쓰는데 `프로세스`는 없다(OM-09). 후보 표의 잠정 구분 열 이름은 단계마다 `공통·고유(잠정)`과 `잠정 도메인 구분`으로 갈려 있다.
- **검토한 대안:** (a) 구분 값에 `프로세스`를 더한다 / (b) 앞 단계와 같은 세 값만 쓰고 프로세스는 설계 기준으로 넣는다 / (c) 프로세스를 후보에서 뺀다
- **결정:** (a). 앞 단계의 세 값은 그대로 두고 `프로세스`를 네 번째로 더한다. 잠정 구분 열은 시나리오 5유형·상태 전이·이벤트 단계가 쓴 `공통·고유(잠정)`과 같은 이름과 같은 선택지를 쓴다(SA-30).
- **이유:** (b)는 구조 기준과 사람이 하는 절차가 섞여 통합 단계가 가려내기 어렵다. (c)는 단계 정의가 말하는 연동 기능 목록에서 샘플이 일부러 표시한 출시 절차의 기록을 잃는다. 같은 값을 두 단계가 다른 어휘로 쓰지 않으려고 이름은 맞췄고, 값의 추가는 이 단계에서만 있는 일이다.
- **영향:** 이후 단계의 구분 값과 어긋날 수 있어 사용자가 구분 어휘를 하나로 정할지 판단해야 한다. 후보 표의 잠정 구분 열 이름을 모든 단계에서 하나로 통일할지도 같이 정한다. 통합·정규화 단계가 `프로세스`를 읽어야 한다(IF-19-031).
- **상태:** 검토 대기

### DL-19-006 · ID 접두어는 연동 정의 `IG`, 공통 점검 `IQ`, 기능 후보 `IC`로 한다
- **날짜:** 2026-10-08
- **대상:** `templates/19_외부연동_template.md` (정의 ID `IG`, `IQ`, `IC`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 후보 ID를 `CF-19-nn`으로 쓴다. 단계 번호를 ID 안에 넣는 형식이다(SA-27). 템플릿 규칙(TP-28)은 접두어가 모든 템플릿에 걸쳐 유일하라고 하고, 이번 호출은 `I`로 시작하는 접두어만 쓰게 했다.
- **검토한 대안:** (a) 샘플의 `CF`를 그대로 쓴다 / (b) `I`로 시작하는 접두어를 쓴다
- **결정:** (b). 연동 정의는 `IG`(Integration), 공통 점검은 `IQ`(Question), 기능 후보는 `IC`(Candidate)로 하고 `01`부터 연번을 매긴다. 공통 점검은 04·05번의 도출 질문 표와 같은 방식의 고정 항목 ID다.
- **이유:** 다른 단계를 만드는 에이전트와 접두어가 겹치는 것을 막는다(TP-K14가 검사한다). 기존 접두어(A, AC, AQ, AR, NC, NQ, X 등)와도 겹치지 않는다.
- **영향:** 분석서 SA-27에 기록했다.
- **상태:** 검토 대기

### DL-19-007 · 인터페이스 표: 19번 보내는 줄 33개를 추가하고 잠정 줄 6개를 필드 수준으로 바꾼다
- **날짜:** 2026-10-08
- **대상:** `tools/data/interfaces.csv` (IF-19-001~033 추가, IF-05-027, IF-05-030, IF-05-032, IF-05-034, IF-09-013, IF-13-017 수정)
- **결정 주체:** 유지보수자 판단
- **배경:** 19번 템플릿 필드 27개는 모두 보내는 필드로 한 줄 이상 나와야 한다(IR-07). 쓰이는 곳의 근거는 샘플의 표시 `후보 풀로 합류 · 22(가용성 요구의 근거) · 33(uses 관계) · 34(외부 액터→기능 검사)`(SA-07)와 단계 정의다. 비사람 액터 목록과 유저 플로우, 상태 전이가 19번에 보내던 잠정 줄(받는 쪽 `19`) 여섯 개는 19번 필드로 바꿀 수 있게 되었다(IR-10).
- **검토한 대안:** (a) 19번이 받는 입력(범위·제약, 시나리오 5유형, 엔티티 등)도 줄로 더한다 / (b) 보내는 줄과 기존 잠정 줄만 다룬다 / (c) 소비자를 샘플이 말하는 것만 주장한다
- **결정:** (b)이고 소비자는 샘플과 단계 정의가 뒷받침하는 만큼만 주장했다. 연동 정의 11개 필드 가운데 장애 시 동작·재시도·한도·모니터링·비용은 22번(샘플의 가용성 근거), 액터는 33번과 34번(샘플의 쓰이는 곳)에 연결했다. 방향·호출 시점·주고받는 정보·설정·키 관리와 장애 시 동작·모니터링의 운영 쪽 연결(22, 23, 24, 26번)은 샘플의 표시가 없어 근거에 `추정: 가정`을 썼다. 연동 목적과 연동 ID, 근거는 `최종 소비자 없음`과 사유를 적었다. 공통 점검의 열 필드 열 개는 점검 과정의 기록이라 모두 `최종 소비자 없음`이다. 기능 후보는 31번(ID, 출처, 기능 후보, 구분), 33번과 34번(ID), 20번(공통·고유(잠정))에 연결했다. 수정한 줄은 IF-05-027(→ `19.연동정의.액터`, 참조), IF-05-030(→ `19.연동정의.액터`, 판단 입력), IF-05-032(→ `19.연동정의.방향`), IF-05-034(→ `19.연동정의.주고받는 정보`), IF-09-013(→ `19.연동정의.연동 목적`), IF-13-017(→ `19.연동정의.호출 시점`)이다. 근거에 이 항목의 ID를 덧붙였다. 환류 줄 IF-19-004(`19.연동정의.액터` → 비사람 액터 목록, 용도)를 추정 소비자로 더했다.
- **이유:** 입력 줄은 보내는 단계 번호로 연결 ID를 매기므로(IR-04) 병렬로 만드는 다른 단계의 작업과 번호가 겹칠 수 있어 새로 만들지 않았다. 환류 선언이 없으면 연동 정의를 쓰다 발견한 누락 액터가 앞 단계로 돌아가는 흐름이 표에 남지 않는다. 20, 22, 23, 24, 26, 31, 33, 34번 템플릿은 아직 없어 받는 쪽은 문서 수준 잠정 값이다.
- **영향:** 사용자가 환류를 인정하지 않으면 IF-19-004를 지우고 가이드 3.1의 액터 문장을 고친다. 해당 템플릿이 생기면 잠정 줄을 필드 수준으로 바꾼다. 19번 템플릿의 입력(생성 블록)에는 비사람 액터 목록, 유저 플로우, 상태 전이만 나온다. 나머지 입력 줄은 DL-19-008에 정리했다.
- **상태:** 검토 대기

### DL-19-008 · 그룹 병합 때 더해야 할 입력 줄의 목록
- **날짜:** 2026-10-08
- **대상:** `tools/data/interfaces.csv` (병합 때 추가할 줄), `guides/19_외부연동_guide.md` 1절
- **결정 주체:** 유지보수자 판단
- **배경:** 단계 가이드 1절은 비사람 액터 목록, 유저 플로우, 시나리오 5유형, 엔티티, CRUD 매트릭스, 상태 전이, 시간·주기, 이벤트, 범위·제약, 근거 수집을 읽으라고 한다. 인터페이스 표의 입력 줄은 연결 ID가 보내는 단계 번호로 시작하므로(IR-04) 병렬 작업 중 다른 세트와 번호가 겹칠 수 있어 앞 단계가 보내는 입력 줄을 새로 만들지 않았다(OM-02). 이미 있던 잠정 줄 여섯 개만 필드 수준으로 바꿨다(DL-19-007). 그래서 지금의 템플릿 입력 블록에는 비사람 액터 목록, 유저 플로우, 상태 전이만 나온다.
- **검토한 대안:** (a) 입력 줄을 이번에 모두 더한다 / (b) 목록으로만 남기고 병합 때 더한다
- **결정:** (b). 병합 때 더할 줄(보내는 필드 → 받는 필드, 방식)은 아래와 같다. 받는 단계는 모두 19, 방향은 순행, 필수는 아니오다.

  - 문서 수준 `03`(근거 수집) → `19.연동정의.재시도·한도`, 근거 인용 / `03` → `19.연동정의.모니터링·비용`, 근거 인용(정해진 기술 제약의 한도와 비용)
  - `05.비사람액터.선정 상태` → `19.연동정의.설정·키 관리`, 판단 입력 / `05.비사람액터.장애 시 영향` → `19.연동정의.장애 시 동작`, 판단 입력 / `05.비사람액터.관련 제약·규제` → `19.연동정의.장애 시 동작`, 판단 입력
  - `09.플로우정의.비사람 액터` → `19.연동정의.호출 시점`, 판단 입력 / `09.질문목록.기능 후보` → `19.연동정의.장애 시 동작`, 판단 입력
  - `10.추가질문.질문` → `19.연동정의.장애 시 동작`, 판단 입력
  - `11.엔티티목록.개인정보` → `19.연동정의.주고받는 정보`, 판단 입력 / `11.엔티티목록.주 소유 액터` → `19.연동정의.액터`, 판단 입력

### DL-19-009 · 가이드에 둔 판단 기준: 방향별 칸 읽기, 장애 시 진행 여부, 모르는 값 닫기
- **날짜:** 2026-10-08
- **대상:** `guides/19_외부연동_guide.md` 3.1, 3.2, 5절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 값에는 해당 없는 칸이 `—`이고(SA-16), 업체 선정 전이거나 상대가 사내 시스템인 경우의 닫는 방법이 없다(OM-18, OM-19). 법이 정한 연동은 장애가 나도 건너뛸 수 없다(OM-21).
- **검토한 대안:** (a) 입력에 없는 한도와 비용은 합리적인 값을 가정해 쓴다 / (b) 입력에 없으면 `미정`(확인처·담당·기한)으로 닫고, 아는 부분을 먼저 쓴다
- **결정:** (b). 한도, 비용, 기간, 횟수는 입력에 없으면 `미정`이다. 선정 전인 업체마다 다른 값은 `미정`이고 확인처는 선정 담당이다. 사내 시스템이라 한도와 비용이 없다는 입력의 문장이 있을 때만 해당 칸을 `해당 없음`으로 닫는다. 장애 시 동작은 진행하는지 막는지를 먼저 쓴다. 선택지 칸(방향)과 ID 칸(액터)도 모르면 `미정`이다.
- **이유:** 한도와 비용은 정책 값이라 틀린 값이 가용성 요구(성능·가용성 단계)로 퍼지면 되돌리기 어렵다. 공통 가이드 3절 3번을 이 단계에 적용한 가장 보수적인 쪽이다.
- **영향:** 입력이 얇으면 `미정`이 많아질 수 있다. 이는 구조의 결함이 아니라 입력 부족이다. 도메인 교체 시험에서 확인한다.
- **상태:** 검토 대기

### DL-19-010 · 제안: 표 사이와 산출물 사이의 정합 검사는 도구가 하지 못한다
- **날짜:** 2026-10-08
- **대상:** `tools/tools-decision-log.md` (알려진 한계), `docs/규칙_템플릿.md`, `docs/규칙_인터페이스표.md`
- **결정 주체:** 유지보수자 판단
- **배경:** 19번 세트를 만들며 도구가 확인하지 못하는 곳 셋을 만났다. (1) 연동 정의의 모든 줄이 기능 후보의 출처에 나오는지, 기능 후보의 출처 `IG-`·`IQ-` ID가 앞 표에 있는지, 값으로 닫은 공통 점검 항목이 후보를 가졌는지는 값을 맞대 보아야 안다(OM-07). 현재 산출물 검사(TP-K13)는 구조만 비교한다. (2) 연동 정의의 액터 칸이 비사람 액터 목록의 ID이고 시간 트리거 액터가 아닌지는 두 산출물을 맞대 보아야 안다. (3) 앞 단계 템플릿이 아직 없는 입력을 받는 연결은 연결 ID가 보내는 단계 번호로 시작해, 병렬로 세트를 만들 때 겹칠 수 있다.
- **검토한 대안:** 해당 없음 — 도구와 규칙 문서는 이번 호출의 수정 대상이 아니다. 제안만 남긴다.
- **결정:** 규칙 문서와 도구는 바꾸지 않는다. 표 사이의 ID 참조 일치와 단계 산출물 사이의 참조 일치를 검사할지, 병렬 병합용 입력 줄의 연결 ID 규칙을 정할지 사용자가 정하게 한다. 그때까지는 완료 체크와 가이드의 누락 점검이 맡는다(DL-14-010, DL-16-009와 같은 종류).
- **이유:** 규칙·도구의 변경은 유지보수자가 단독으로 하지 않는다.
- **영향:** 도입하면 `tools/checks.py`에 검사를 더하고 규칙_템플릿과 규칙_인터페이스표에 대응 규칙을 정한다. 시나리오 5유형, 유저 플로우, 이벤트, 시간·주기에도 같은 구조가 있어 한 번에 도입하는 편이 낫다.
- **상태:** 검토 대기
