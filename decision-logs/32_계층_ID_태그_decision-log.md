# 결정 로그 — 32. 계층·ID·태그

> 32번 세트(템플릿, 단계 가이드, 변환 분석서, 인터페이스 표의 32 관련 연결)의 결정 이력이다. 항목은 추가만 하고 과거 항목은 고치지 않는다(`docs/규칙_결정로그.md`).
> 변환 분석서의 줄 ID(`SA-nn`, `OM-nn`)를 `배경`에 적어 근거를 가린다(CV-13).

### DL-32-001 · 32번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-10
- **대상:** `conversions/32_계층_ID_태그_conversion.md`, `templates/32_계층_ID_태그_template.md`, `guides/32_계층_ID_태그_guide.md` (그룹 I에서 31번, 33번과 병렬로 만든 세트)
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 샘플 해부 57행(SA-01~57)과 누락 탐색 24행(OM-01~24)을 같은 절차로 만들었다. 단계 정의의 목적은 기능에 계층·고유 ID·근거 ID·태그를 붙여 찾고 걸러내고 근거를 따라갈 수 있게 하는 것이고 산출물은 기능 트리(L1~L3), 기능 ID, 근거 ID, 태그다. 샘플은 영역마다 표를 나누고 L2를 열로만 두며(SA-13, SA-32), 최종 ID를 통합 단계가 이미 붙였다고 전제하고(OM-01), 뒤 단계가 되돌려 쓴 이력을 칸으로 섞었으며(SA-29, SA-43), 근거와 근거 등급에 체인을 남기지 않았고(SA-41, SA-42), 후속을 걸러 볼 표시가 없다(SA-45). 샘플의 기능 146행과 영역별 표 16개는 표 단위로 묶었다(CV-06).
- **검토한 대안:** 04·05번처럼 도출 질문 → 후보 → 판정 → 목록의 구성으로 하는 안, 샘플처럼 영역마다 표를 나누는 안, 기능 하나를 한 행으로 두는 기능 트리 한 표에 기능군 표와 결번 표와 집계 표를 더하는 안을 비교했다. 이 단계는 후보를 찾거나 판정하는 단계가 아니라 이미 합쳐진 기능에 위치와 이름표와 태그를 붙이는 단계라서 첫 안은 버렸다. 영역마다 표를 나누면 영역 수가 서비스마다 달라 템플릿을 고정할 수 없고 영역 이름·코드·기능 수를 소제목에 중복해 써서 둘째 안도 버렸다.
- **결정:** 값 표 넷을 둔다. 기능군(L2, 목록 표, 정의 ID `FG`), 기능트리(L3, 목록 표, 정의 ID `FT`), 결번(목록 표, 정의 ID 없음), 집계(속성 표, 정의 ID 없음). 필드는 모두 41개다(기능군 5, 기능트리 16, 결번 4, 집계 16). L1은 영역·모듈 산출물의 영역 목록을 그대로 쓰고 새 표를 만들지 않는다(기능군 표의 영역 칸이 `Z-` ID로 가리킨다). 선택 블록과 표 없는 절은 없다.
- **이유:** 템플릿의 모든 표와 필드가 분석서의 줄에 대응한다(정의서 6절 4번). 접두어 `FG`, `FT`는 호출이 지정한 글자로 시작하고 기존 접두어와 겹치지 않는다(TP-28). 행 하나가 판단 하나가 되도록 기능 한 행에 태그를 열로 붙였다.
- **영향:** 도메인 교체 시험(작업 순서 8번)이 남았다. 인터페이스 표는 DL-32-008, 입력 줄 목록은 DL-32-009, 환류 줄 목록은 DL-32-010에 있다.
- **상태:** 유효

### DL-32-002 · 기능 트리에 행 번호 열 `ID`(FT-nnn)와 최종 기능 ID 열을 둘 다 둔다
- **날짜:** 2026-10-10
- **대상:** `templates/32_계층_ID_태그_template.md` 표 `기능트리`의 `ID`, `기능 ID`
- **결정 주체:** 유지보수자 판단
- **배경:** 호출이 정의 ID 접두어를 `FT`로 지정했고(`FT-001` 같은 ID가 표의 정의 ID가 된다), 사용자가 확정한 설계는 최종 기능 ID를 `F-<영역 코드>-nnn`으로 정한다(DL-05-005 방식). 둘은 접두어가 달라 한 열에 같이 쓸 수 없다(SA-17).
- **검토한 대안:** (a) 최종 기능 ID를 `FT-<영역 코드>-nnn`으로 바꿔 한 열로 쓴다 / (b) 정의 ID를 `F`로 선언하고 `기능 ID`를 첫 열로 둔다 / (c) 두 열을 둘 다 둔다 / (d) 정의 ID를 `없음`으로 하고 기능 ID만 둔다
- **결정:** (c). 첫 열 `ID`는 `FT-001`부터 부여하는 이 표의 행 번호이고, 둘째 열 `기능 ID`가 사용자가 확정한 `F-<영역 코드>-nnn`이다. 뒤 단계는 모두 기능 ID로 기능을 가리키고 `ID`는 `최종 소비자 없음`으로 닫았다(IF-32-007).
- **이유:** (a)는 확정된 형식을 사용자 결정 없이 바꾸는 것이고, (b)는 호출이 지정한 접두어를 어기며, (d)도 지정을 어긴다. (c)가 둘 다 지키지만 한 기능에 이름표가 둘이 되는 군더더기가 있다.
- **영향:** 사용자가 `FT-nnn` 열을 빼기로 하면(정의 ID `없음`, 첫 열 `기능 ID`) 템플릿, 가이드, IF-32-007, 완료 체크를 고친다. 사용자 결정이 필요하다.
- **상태:** 검토 대기

### DL-32-003 · 기능 ID 부여 규칙과 결번 표
- **날짜:** 2026-10-10
- **대상:** `templates/32_계층_ID_태그_template.md` 표 `결번`, `guides/32_계층_ID_태그_guide.md` 3.2, 3.3
- **결정 주체:** 유지보수자 판단
- **배경:** 기능 ID의 번호는 삭제해도 재사용하지 않는다고 확정되었다. 이를 지키려면 삭제한 번호가 기록되어야 하는데 샘플의 트리에는 빠진 번호(`F-ACC-016`, `F-ACC-017`)의 흔적이 없다(SA-33, OM-08). 번호의 순서도 규칙이 없다(SA-33). 영역 코드가 형식에 맞지 않을 때의 처리도 필요하다(OM-22).
- **검토한 대안:** (a) 결번 표를 두지 않고 기능을 삭제하지 않는 규칙을 둔다 / (b) 영역마다 마지막 번호를 칸으로 둔다 / (c) 삭제한 기능을 결번 표에 한 줄씩 남긴다
- **결정:** (c). 번호는 영역 안에서 임시 번호 순서대로 `001`부터 붙이고 행은 영역, 기능군, 기능 ID 순으로 늘어놓는다. 결번 표는 기능 ID, 임시 번호, 사유, 근거를 갖고 삭제한 기능이 없는 첫 작성에서는 한 줄을 `해당 없음`과 사유로 닫는다. 영역 코드가 영문 대문자·숫자 형식에 맞지 않으면 영문자와 숫자만 남겨 대문자로 바꿔 쓰고 원래 코드를 기능군 표의 근거에 남긴다(가이드 3.2).
- **이유:** (a)는 과잉 기능을 가려 지우는 역추적 검증의 일을 막는다. (b)는 삭제된 기능을 알 수 없다. 번호를 임시 번호 순서로 붙이면 같은 입력에서 같은 ID가 나온다.
- **영향:** 34·35번이 기능을 삭제할 때 결번에 줄을 더하고 이 산출물의 버전을 올린다(DL-32-010). 완료 체크가 기능 ID의 유일성과 결번과의 비중복을 확인한다.
- **상태:** 검토 대기

### DL-32-004 · 후속 표시는 기능 트리의 구분 열(기능 / 후속)로 둔다
- **날짜:** 2026-10-10
- **대상:** `templates/32_계층_ID_태그_template.md` `기능트리.구분`, `집계.후속 기능 수`
- **결정 주체:** 유지보수자 판단
- **배경:** 사용자가 확정한 설계(쟁점 2)에서 후속 후보는 기능 목록의 행이 되고 `후속` 표시를 붙이며, 이 표시는 32번 이후로 이어져 걸러 볼 수 있어야 한다. 샘플의 트리에는 이 표시가 없다(SA-45, OM-04). 통합 단계의 구분 열 값이 `기능` / `후속`이라는 호출의 약속에 맞춘다.
- **검토한 대안:** (a) 후속 기능을 별도 표로 나눈다 / (b) 구분 열을 둔다 / (c) 이력 열의 값으로 쓴다
- **결정:** (b). 열 이름과 선택지를 통합 단계와 같게 `구분`, `기능 / 후속`으로 둔다. 후속이어도 행을 지우지 않으며 집계가 후속 기능 수를 센다.
- **이유:** 같은 값을 두 단계가 다른 어휘로 쓰지 않는다. 별도 표는 기능 하나를 두 곳에 두게 하고, 이력 열은 두지 않기로 했다(DL-32-005).
- **영향:** 36번이 구분 열을 읽어 후속 기능의 릴리스를 Later로 정한다(IF-32-018). 통합 단계의 구분 열 선택지가 다르면 병합 때 이 열을 맞춘다.
- **상태:** 검토 대기

### DL-32-005 · 이력 칸은 필드로 두지 않고 임시 번호·결번·환류로 남긴다
- **날짜:** 2026-10-10
- **대상:** `templates/32_계층_ID_태그_template.md` (이력 열을 두지 않음), `tools/data/interfaces.csv` (환류 줄은 DL-32-010)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 `이력` 열은 34·35번이 기능을 추가·수정한 표시를 받는 칸이다(SA-29, SA-43, SA-52, SA-57). 뒤 단계가 되돌려 쓰는 칸을 필드로 둘지 환류 줄로 둘지 정해야 한다(OM-09).
- **검토한 대안:** (a) 이력 열을 필드로 둔다 / (b) 열을 두지 않고 환류 줄로만 연결한다
- **결정:** (b). 환류로 더한 기능은 임시 번호가 `해당 없음`인 행으로 구별하고 집계의 후 단계 추가 수가 센다. 환류로 지운 기능은 결번 표에 남긴다. 기능의 수정 내용은 34·35번의 산출물과 이 산출물의 버전과 결정 로그가 갖는다. 환류 줄의 목록은 DL-32-010에 있다.
- **이유:** (a)는 변경이 없는 대부분의 행이 `해당 없음`으로 닫혀 행마다 판단이 없는 열이 되고, 수정 내용은 뒤 단계의 산출물이 더 정확히 가진다. 같은 사실을 두 곳에 쓰지 않는다(정의서 4절).
- **영향:** 뒤 단계 산출물이 기능을 고칠 때 이 산출물의 버전을 올리고 결정 로그에 기록한다(정의서 10절). 수정이 이 산출물에서 어느 행이었는지는 34·35번의 갭 로그가 기능 ID로 가리킨다.
- **상태:** 검토 대기

### DL-32-006 · 근거 ID는 앞 단계 항목의 ID로 하고 근거 등급은 체인으로 가르며 품질 태그 열은 두지 않는다
- **날짜:** 2026-10-10
- **대상:** `templates/32_계층_ID_태그_template.md` `기능트리.근거 ID`, `기능트리.근거 등급`, `guides/32_계층_ID_태그_guide.md` 3.2, `tools/data/interfaces.csv` (IF-22-003, IF-24-033, IF-26-027)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 근거 ID는 다섯 종류에 고정되고(SA-24) 근거 체인을 남기지 않은 채 146행이 모두 `미검증`이다(SA-42). 앞 단계가 남긴 잠정 줄은 후보 ID를 근거 ID로 붙인다고 하고(IF-24-033, IF-26-027), 비기능 요구의 특성을 품질 태그로 붙인다고 한다(IF-22-003). 단계 정의의 목적은 근거를 따라갈 수 있게 하는 것이다(OM-05, OM-06, OM-11, OM-12).
- **검토한 대안:** 근거 ID에 후보 ID를 쓰는 안, 후보 ID를 별도 열로 복사하는 안, 근거 ID는 앞 단계 항목의 ID만 쓰고 후보는 임시 번호로 통합 단계에서 찾는 안, 품질 태그 열을 두는 안을 비교했다.
- **결정:** 근거 ID는 기능이 있어야 하는 이유를 보여 주는 앞 단계 산출물 항목의 ID(가장 가까운 출처 행과 그 행이 인용한 뿌리 항목)이고 후보 ID와 임시 번호는 쓰지 않는다. 후보는 임시 번호로 통합 단계의 병합 후보 칸에서 찾는다. 근거 등급은 근거 ID의 항목에서 근거 칸을 처음까지 올라간 체인으로 `조사:`/`내부 자료:`가 있으면 검증, `일반 지식(미검증):`/`가정:`뿐이면 미검증, 체인을 읽을 수 없으면 `미정`이다(공통 규칙 CM-11). 품질 태그 열은 두지 않는다. 잠정 줄 IF-22-003, IF-24-033, IF-26-027은 받는 쪽을 `32.기능트리.근거 ID`로 바꾸고 설명을 근거 ID를 붙이는 일에 맞게 고쳤다(DL-32-008).
- **이유:** 후보 ID를 근거 ID에 쓰면 통합 단계의 병합 후보와 같은 사실이 두 곳에 있다. 품질 태그는 단계 정의와 샘플에 없고 요구 행의 ID가 근거 ID이면 특성은 그 단계에서 읽는다.
- **영향:** 사용자가 품질 태그를 따로 원하면 기능 트리에 열을 더하고 IF-22-003을 그 열로 옮긴다. 근거 등급의 체인 추적은 도구가 못 하고(DL-32-012) 가이드와 완료 체크가 맡는다.
- **상태:** 검토 대기

### DL-32-007 · 운영 기능 열을 둔다
- **날짜:** 2026-10-10
- **대상:** `templates/32_계층_ID_태그_template.md` `기능트리.운영 기능`, `집계.운영 기능 수`
- **결정 주체:** 유지보수자 판단
- **배경:** 영역·모듈 산출물의 배치 방침은 운영 기능을 "소속 영역 안에 두고 태그로 표시"할 수 있고 그 경우 트리가 태그를 달아야 한다(IF-21-002). 샘플의 트리에는 이 태그가 없고 플랫폼 이름으로 짐작하게 하지만 관리자가 설정하는 기능이 플랫폼은 백엔드인 경우가 있다(OM-10).
- **검토한 대안:** (a) 열을 두지 않고 액터와 플랫폼으로 미룬다 / (b) 방침이 소속 영역 안에 두는 경우에만 채우는 조건 열로 둔다 / (c) 방침에 상관없이 항상 같은 기준으로 채우는 열로 둔다
- **결정:** (c). 선택지는 `예` / `아니오`이고 액터가 모두 서비스를 운영하는 역할이면 `예`다.

### DL-32-012 · 제안: 표 사이의 정합 검사와 근거 체인 검사는 도구가 하지 못한다
- **날짜:** 2026-10-10
- **대상:** `tools/tools-decision-log.md` (알려진 한계), `docs/규칙_공통.md` CM-K05, `docs/규칙_템플릿.md`
- **결정 주체:** 유지보수자 판단
- **배경:** 이 단계는 값을 맞대 보아야 아는 정합이 많다: 31번의 `FN-`가 트리의 임시 번호나 결번에 정확히 한 번 나오는지, 기능 ID의 영역 코드가 기능군의 영역과 같은지, 기능 ID가 겹치지 않는지, 공통 영역에 고유 기능이 없는지, 집계의 합 관계, 근거 등급이 체인과 맞는지. 현재 산출물 검사(TP-K13)는 구조만 비교하고, CM-K05(근거 등급 일치)는 근거 등급을 표시하는 문서가 없어 구현하지 않았는데 이 템플릿이 그 첫 문서다. `tools/check_chain.py`는 `접두어-숫자` 모양만 ID로 보아 `F-<영역 코드>-nnn` 모양의 기능 ID 참조를 검사하지 못한다.
- **검토한 대안:** 해당 없음 — 도구와 규칙 문서는 이번 호출의 수정 대상이 아니다. 제안만 남긴다.
- **결정:** 규칙 문서와 도구는 바꾸지 않는다. 사용자가 정할 것: (1) 위 정합 검사를 도입할지(31번 전수 소진 검사와 함께), (2) CM-K05를 이 템플릿으로 구현할지(근거 칸의 출처 유형을 참조를 따라 올라가며 읽는 검사), (3) `check_chain.py`가 영역 코드가 낀 ID를 읽게 할지. 그때까지는 완료 체크와 가이드의 누락 점검이 맡는다.

- **영향:** 도입하면 `tools/checks.py`와 `tools/check_chain.py`에 검사를 더하고 규칙_템플릿에 대응 규칙을 정한다. 31·33번의 정합 검사와 한 번에 도입하는 편이 낫다.
- **상태:** 검토 대기

### DL-32-014 · 그룹 I 병합: 입력 줄을 더하고 그룹 안 잠정 줄을 필드 키로 바꾼다

- **배경:** 31·32·33번 세트를 병렬로 만든 뒤 병합했다(그룹 I). 각 세트가 남긴 "병합 때 더할 입력 줄" 목록(DL-31-003, DL-32-009, DL-33-008)과 같은 그룹 안의 문서 수준 잠정 줄이 남아 있었다.
