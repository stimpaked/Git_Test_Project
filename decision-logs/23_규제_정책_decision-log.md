# 결정 로그 — 23. 규제·정책

> 23번 세트(템플릿, 단계 가이드, 변환 분석서, 인터페이스 표의 23 관련 연결)의 결정 이력이다. 항목은 추가만 하고 과거 항목은 고치지 않는다(`docs/규칙_결정로그.md`).
> 변환 분석서의 줄 ID(`SA-nn`, `OM-nn`)를 `배경`에 적어 근거를 가리킨다(CV-13).

### DL-23-001 · 23번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-09
- **대상:** `conversions/23_규제_정책_conversion.md`, `templates/23_규제_정책_template.md`, `guides/23_규제_정책_guide.md` (그룹 F, 22~25번 병렬 작성의 하나)
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 샘플 해부 41행(SA-01~41)과 누락 탐색 22행(OM-01~22)을 앞 단계와 같은 절차로 만들었다. 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 구성(도출 질문 → 후보 → 판정 → 목록)을 따르지 않고 이 단계의 목적(법령과 플랫폼 정책이 요구하는 것을 기능·프로세스로 옮겨 필수 항목을 놓치지 않게 한다)에 맞춰 값 표를 다섯으로 둔다. 1번 `규제매핑`은 대응 하나를 행으로 하는 목록(정의 ID `RM`), 2번 `규제점검`은 규제 항목에 직접 적히지 않는 필수 기능을 찾는 고정 질문 열두 개(정의 ID `RQ`, 속성 표), 3번 `설계결정`은 규제 때문에 정한 방침의 목록(정의 ID `RD`), 4번 `기능후보`는 앞 표에서 도출한 후보(정의 ID `RC`), 5번 `집계`는 입력과 매핑의 수를 맞대는 속성 표다(SA-10, SA-24, SA-25, SA-30, OM-04, OM-05). 그림이나 표 없는 필수 블록, 선택 블록은 없다.
- **이유:** 이 단계의 본질은 입력 규제 항목을 하나도 빠뜨리지 않고 기능·프로세스·정책으로 옮겨 출시 게이트로 쓸 수 있게 하는 것이다. 도출 질문이 필요한 곳은 매핑 행 하나의 칸이 아니라 규제 항목에 직접 적히지 않는 부수 기능이다. 템플릿의 모든 변경이 분석서의 줄에 대응한다(정의서 6절 4번).
- **영향:** 도메인 교체 시험(8번)이 남았다. 인터페이스 표에 23번 보내는 줄 47개와 외부 입력 2개를 더하고 잠정 줄 17개를 바꿨다(DL-23-008).
- **상태:** 유효

### DL-23-002 · 규제 매핑은 대응 하나를 행 하나로 두고 요건 열을 지우며 대응 후보 열을 지운다
- **날짜:** 2026-10-09
- **대상:** `templates/23_규제_정책_template.md` 1절 (필드 `ID`, `규제 항목`, `대응 유형`, `대응 내용`, `책임`), `guides/23_규제_정책_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 규제 항목마다 한 행을 두고 유형 칸에 `기능 + 프로세스`처럼 값을 묶으며(SA-10, SA-14, SA-20), `요건(요지)` 열이 근거 수집의 요건 문장을 되풀이하고(SA-13), `대응 후보` 열이 3절에서 처음 부여되는 ID와 다른 단계의 후보 ID를 앞서 참조한다(SA-15). 한 규제 항목에 기능 대응과 프로세스 대응이 함께 있는 경우가 많다(OM-01).
- **검토한 대안:** (a) 샘플처럼 규제 항목 하나에 행 하나를 두고 유형을 묶어 쓴다 / (b) 대응 하나를 행 하나로 하고 규제 항목은 ID 참조 열로 둔다 / (c) 규제 항목 표와 대응 표를 둘로 나눈다
- **결정:** (b). 행마다 `RM-01`부터 ID를 부여하고, 규제 항목 칸은 근거 수집의 `MR-` ID 참조로 쓰며, 요건 문장은 쓰지 않는다. `대응 후보` 열은 지우고 후보 쪽의 `출처`가 매핑 행을 가리킨다.
- **이유:** (a)는 한 칸에 책임과 게이트가 다른 두 대응이 섞여 칸을 닫기 어렵고 프로세스 대응이 후보로 이어지는지 따라갈 수 없다. (c)는 규제 항목의 정보를 근거 수집이 이미 갖고 있어 같은 사실을 두 곳에 쓰게 된다(CM-12). (b)는 대응마다 칸을 닫으면서 앞 표가 뒤 표의 ID를 참조하는 순서 오류(TP-16)를 없앤다.
- **영향:** 행 수가 규제 항목 수보다 늘 수 있다. 입력의 모든 규제 항목이 매핑에 나오는지는 도구가 검사하지 못하고 완료 체크와 집계가 맡는다(DL-23-012).
- **상태:** 검토 대기

### DL-23-003 · 대응 유형에 `대응 불필요`를 더하고 출시 게이트를 세 값과 조건 열로 가른다
- **날짜:** 2026-10-09
- **대상:** `templates/23_규제_정책_template.md` 1절 (필드 `대응 유형`, `출시 게이트`, `게이트 조건`), `guides/23_규제_정책_guide.md` 3.1, 5절
- **결정 주체:** 사용자 결정
- **배경:** 샘플의 게이트 칸에는 기호 ●와 조건(`광고성 푸시 발송 시`)과 사유(`스토어 심사`)와 `권고`가 섞여 있다(SA-17). 근거 수집의 적용 여부에는 적용 후보와 적용 제외가 있는데 샘플에는 처리 방법이 없다(OM-03). 법적 의무인지 모호한 기준이 있다(SA-21, OM-18).
- **검토한 대안:** (a) 샘플처럼 기호와 조건을 한 칸에 둔다 / (b) 게이트를 선택지(출시 필수 / 조건부 필수 / 권고)로 하고 조건을 별도 열로 둔다 / (c) 적용 제외 항목은 매핑에서 뺀다
- **결정:** (b)와 적용 제외 항목은 `대응 불필요` 행으로 남긴다. 적용 후보는 적용된다고 보고 대응을 정하며 게이트는 가이드가 정한 기준(적용 확정은 출시 필수, 적용 후보나 특정 기능을 낼 때만 걸리는 요건은 조건부 필수, 의무 여부가 확인되지 않은 기준은 권고)으로 고른다. 판단이 갈리면 센 쪽을 고른다.
- **이유:** (a)는 한 칸을 선택지로 검사할 수 없다. (c)는 입력의 규제 항목이 매핑에서 사라져 누락과 의도적 제외를 가를 수 없다(34번의 의도적 제외 목록). 필수 항목을 낮춰 놓치는 위험이 게이트를 높여 두는 비용보다 크므로 보수적으로 센 쪽을 고른다.
- **영향:** `대응 불필요`와 `해당 없음`(게이트, 게이트 조건)이 한 행에 함께 나온다. 이는 닫는 말이 아니라 개념이 없을 때의 `해당 없음`이다. 사용자가 게이트 어휘를 다르게 정하면 선택지를 바꾼다.
- **상태:** 유효

### DL-23-004 · 규제 점검 질문 열두 개를 둔다
- **날짜:** 2026-10-09
- **대상:** `templates/23_규제_정책_template.md` 2절 (표 `규제점검`), `guides/23_규제_정책_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 규제 항목마다 직접 대응만 올린다. 도메인을 대입해 보니 규제 항목에 직접 적히지 않아도 필요한 부수 기능이 있다: 동의 증빙(OM-11), 규제 변경 대응(OM-12), 법정 보관 기록과 삭제 요구의 충돌(OM-13), 고지의 시점과 화면(OM-14), 연령·자격 확인과 위탁 고지(OM-15), 신고 사실의 표시(OM-19), 기록 제출(OM-20), 플랫폼 심사 요건(OM-21). 질문 수는 외부 연동 단계의 공통 점검(열 개)처럼 개방 질문을 마지막에 두고 위 종류를 하나씩 담아 열두 개가 되었다.
- **검토한 대안:** (a) 점검 없이 규제 항목의 직접 대응만 올린다(샘플) / (b) 고정 질문 열두 개와 개방 질문을 둔다 / (c) 규제 분야별(개인정보, 광고, 결제 등) 점검표를 둔다
- **결정:** (b). 질문은 법령 분야가 아니라 기능의 종류로 쓴다. 답은 필요한 기능과 관련 `RM-` ID이고, 값으로 닫은 항목은 후보의 출처가 된다.
- **이유:** (a)는 놓친 종류를 확인할 방법이 없다(OM-05). (c)는 분야 이름이 법령이나 업종을 전제해 템플릿이 도메인에 묶이고(TP-02), 입력에 없는 법령을 불러들일 위험이 있다. 질문을 기능 종류로 쓰면 어떤 법령이 적용되는지는 정하지 않고 필요한 기능만 드러낸다.
- **영향:** 질문 열두 개가 충분한지는 도메인 교체 시험에서 본다. 열두 필드는 뒤 단계가 값으로 쓰지 않아 `최종 소비자 없음`이다(DL-23-008). 보관 기간은 데이터 생애 단계가 정하므로 RQ-05는 기능의 필요만 묻는다.
- **상태:** 검토 대기

### DL-23-005 · 설계 결정 표에 확정 상태를 두고 후보와 연결한다
- **날짜:** 2026-10-09
- **대상:** `templates/23_규제_정책_template.md` 3절 (표 `설계결정`), `guides/23_규제_정책_guide.md` 3.3
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 설계 결정은 이름·내용·근거 세 열이고 근거 칸이 샘플의 규제 ID와 범위 항목을 그대로 적는다(SA-26~SA-28). 법무 확인 전의 방침을 확정처럼 쓰면 이후 단계가 틀린 전제 위에 선다(OM-07). 회피로 푼 방침과 규제 대응의 연결도 없다(OM-08).
- **검토한 대안:** (a) 샘플처럼 세 열만 둔다 / (b) ID, 관련 규제(`RM-`), 확정 상태를 더한다 / (c) 설계 결정을 따로 두지 않고 기능 후보의 설계 기준으로만 둔다
- **결정:** (b). 확정 상태는 `확정` / `확인 대기` 둘이다. 설계 기준 후보는 방침이 기능에 규칙을 요구할 때 후보 표에서 이 표를 출처로 가리킨다.
- **이유:** (c)는 선택이 있었던 방침의 이력이 후보 문장 속에 묻힌다. 확인 대기는 `미정`과 달리 값이 있으나 확인 전이라는 뜻이어서 둘이 겹치지 않는다. 선택지 값에 닫는 말을 쓰지 않는 규칙(템플릿 힌트)을 지켰다.
- **영향:** 36번이 확인 대기 방침을 게이트 점검의 열린 항목으로 읽는다(IF-23-030). 확정 상태의 어휘를 `검토 대기` 같은 결정 로그의 어휘와 맞출지는 사용자가 정할 수 있다.
- **상태:** 검토 대기

### DL-23-006 · 기능 후보 표는 통일 열을 따르고 규제 항목 열을 더하며 구분 어휘를 앞 단계에 맞춘다
- **날짜:** 2026-10-09
- **대상:** `templates/23_규제_정책_template.md` 4절 (표 `기능후보`), `guides/23_규제_정책_guide.md` 3.4
- **결정 주체:** 유지보수자 판단
- **배경:** 그룹 F 지시(수정목록 G13의 사용자 결정)가 후보 표의 열을 `ID | 후보 문장 | 구분 | 공통·고유(잠정) | 출처 | (단계 고유 열) | 근거`로 통일하라고 했다. 샘플의 후보 표는 이 순서와 달라(SA-31~SA-34) 규제에서 후보로 이어지는 추적 열도 없다(OM-09). 후보 중에 기능이 아닌 항목이 섞인다(SA-36).
- **검토한 대안:** (a) 샘플의 열 순서를 유지한다 / (b) 통일 열을 따르고 단계 고유 열로 `규제 항목`(`MR-`)을 둔다 / (c) 규제 항목을 출처 열에 섞어 쓴다
- **결정:** (b). 구분은 18번과 19번 템플릿의 어휘 네 값(기능 후보 / 후속 후보 / 설계 기준 / 프로세스)을 쓴다. 문서와 운영 규칙으로만 끝나는 정책은 `프로세스`, 기능이 따르는 정책은 `설계 기준`으로 가른다.
- **이유:** (c)는 출처의 형식이 섞여 검사하기 어렵다. 34번의 규제→기능 검사는 규제 ID에서 후보로 바로 가야 하므로 별도 열이 낫다. 같은 값을 두 단계가 다른 어휘로 쓰지 않으려고 구분 값을 맞췄다.
- **영향:** 31번이 구분의 `프로세스`와 `설계 기준`을 읽는다(IF-23-035). 22, 24, 25번의 후보 표도 같은 열을 따르면 31번이 한 모양으로 읽는다.
- **상태:** 검토 대기

### DL-23-007 · ID 접두어는 규제 매핑 `RM`, 규제 점검 `RQ`, 설계 결정 `RD`, 기능 후보 `RC`로 한다
- **날짜:** 2026-10-09
- **대상:** `templates/23_규제_정책_template.md` (정의 ID `RM`, `RQ`, `RD`, `RC`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 후보 ID를 `CF-23-nn`으로 쓴다. 단계 번호를 ID 안에 넣는 형식이다(SA-31). 템플릿 규칙(TP-28)은 접두어가 모든 템플릿에 걸쳐 유일하라고 하고, 이번 호출은 `R`로 시작하는 접두어만 쓰게 했다.
- **검토한 대안:** (a) 샘플의 `CF`를 그대로 쓴다 / (b) `R`로 시작하는 접두어를 쓴다
- **결정:** (b). 규제 매핑은 `RM`(Mapping), 규제 점검은 `RQ`(Question), 설계 결정은 `RD`(Decision), 기능 후보는 `RC`(Candidate)로 하고 `01`부터 연번을 매긴다. 규제 점검은 외부 연동 단계의 공통 점검과 같은 방식의 고정 항목 ID다.
- **이유:** 다른 단계를 만드는 에이전트와 접두어가 겹치는 것을 막는다(TP-K14가 검사한다). 기존 접두어 전부(A, AC, AQ, AR, BG ... Z)와도 겹치지 않는다.
