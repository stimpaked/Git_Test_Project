### DL-24-001 · 24번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-09
- **대상:** `conversions/24_보안_어뷰징_conversion.md`, `templates/24_보안_어뷰징_template.md`, `guides/24_보안_어뷰징_guide.md` (작업 순서 6단계, 그룹 F의 복제)
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 샘플 해부 34행(SA-01~34)과 누락 탐색 22행(OM-01~22)을 앞 단계와 같은 절차로 만들었다. 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 구성(도출 질문 → 후보 → 판정 → 목록)을 따르지 않고 이 단계의 목적(서비스에 가해질 수 있는 위협과 오남용을 나열하고 방어 기능을 정한다)에 맞춰 값 표를 넷으로 둔다. 1번 표 `보호대상`은 위협이 닿는 대상을 입력에서 가져와 정하는 목록 표(정의 ID `WA`), 2번 표 `점검관점`은 공격하는 쪽의 길로 나눈 고정 질문 열두 개(정의 ID `WQ`, 속성 표), 3번 표 `위협목록`은 위협 하나를 행 하나로 하는 목록 표(정의 ID `WT`), 4번 표 `방어후보`는 통일한 후보 표 열을 따르는 목록 표(정의 ID `WD`)다.
- **이유:** 이 단계의 본질은 위협을 목록에서 고르는 것이 아니라 입력(액터, 소유·권한, 외부 연동, 엔티티, 시간 기준)에서 위협이 나오게 하는 구조를 만드는 것이다. 샘플은 위협 열여덟 개를 자체 목록으로 들고 있어 입력과 이어지지 않는다(OM-01, OM-05). 템플릿의 모든 변경이 분석서의 줄에 대응한다(정의서 6절 4번).
- **영향:** 도메인 교체 시험(8번)이 남았다. 인터페이스 표에 24번 보내는 줄 44개와 외부 입력 줄 4개를 더하고 잠정 줄 13개를 바꿨다(DL-24-006).
- **상태:** 유효

### DL-24-002 · 보호 대상 표를 두고 위협 표와 분리한다
- **날짜:** 2026-10-09
- **대상:** `templates/24_보안_어뷰징_template.md` 1절 (표 `보호대상`), `guides/24_보안_어뷰징_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 자산 다섯 가지를 방법 문단에만 쓰고 위협 표가 곧바로 시나리오로 시작한다(SA-08). 어떤 입력의 어떤 대상을 보호 대상으로 올렸고 무엇을 제외했는지, 어떤 목표(기밀성 같은)를 지키려는지가 남지 않는다(OM-04). 위협이 외부 연동이나 시간 기준을 표적으로 하는 경우가 있다(OM-13, OM-16).
- **검토한 대안:** (a) 샘플처럼 보호 대상 표 없이 위협 표만 둔다 / (b) 보호 대상 표를 두고 위협 행이 `WA-` ID로 가리키게 한다 / (c) 보호 대상 × 위협 유형 매트릭스를 둔다
- **결정:** (b). 행 하나가 판단 하나인 목록 표로 두고 종류는 입력 산출물의 표(엔티티, 규칙·행위, 연동, 타이머)에 맞춰 `데이터 / 접근 규칙 / 외부 연동 / 시간 기준 / 그 밖`으로 한다. 보호 목표는 `기밀성 / 무결성 / 가용성 / 추적성`이다. 한 대상의 목표가 둘이면 행을 나눈다.
- **이유:** (a)는 입력에서 올리지 않은 대상이 누락되어도 알 수 없다(OM-04). (c)는 대상 수 × 유형 수의 칸이 되어 행 하나가 판단 하나라는 원칙에 어긋난다. 위협 유형은 위협 행의 선택지로 담는다. 보호 목표 어휘는 일반 지식(미검증)이며 사용자가 확인한 용어가 아니다.
- **영향:** 보호 대상의 종류 선택지가 입력 산출물의 표 종류에 묶여 있어 새 종류의 입력이 생기면 템플릿을 갱신한다. `그 밖`으로 둔 대상이 많이 나오면 도메인 교체 시험에서 선택지를 다시 본다(OM-22).
- **상태:** 검토 대기

### DL-24-003 · 점검 관점 열두 질문을 둔다
- **날짜:** 2026-10-09
- **대상:** `templates/24_보안_어뷰징_template.md` 2절 (표 `점검관점`), `guides/24_보안_어뷰징_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 점검 관점 없이 위협 열여덟 개를 자유롭게 적었고(OM-05), 서로 다른 세 행이 같은 관점(반복 호출과 대량 수집)이었다(SA-21, SA-22). 도메인을 대입하니 사람이 아닌 장치의 위장(OM-15), 시간 기준 조작(OM-16), 외부 통지의 위조(OM-13), 서비스 자신이 입는 피해(OM-14), 운영하는 사람이 주체인 위협(OM-11)이 샘플의 구조에 담기지 않는다.
- **검토한 대안:** (a) 위협 유형 여섯 가지(위장·변조·부인·정보 노출·서비스 거부·권한 상승)와 남용만을 점검 질문으로 쓴다 / (b) 유형과 별개로 공격하는 쪽의 길(신원, 권한, 변조, 노출, 대량 이용, 제재 회피, 외부 입구, 시간·환경, 운영 권한, 정상 기능 남용, 책임 추적)로 열한 질문과 개방 질문을 둔다 / (c) 점검 질문 없이 입력의 항목마다 위협을 도출한다
- **결정:** (b). 위협 유형은 위협 행의 선택지(위장 / 변조 / 부인 / 정보 노출 / 서비스 거부 / 권한 상승 / 남용)로 두고, 점검 관점은 그 유형들이 입력의 어느 곳에서 나오는지를 가리킨다. 질문의 답은 위협이 드러나는 `WA-` ID와 요지이고, 값으로 닫은 항목은 위협 목록의 출처에 나온다. 질문 열두 개는 인터페이스 표에서 `최종 소비자 없음`이다(DL-24-006).
- **이유:** (a)는 유형만으로는 입력의 어느 표를 읽어야 하는지가 드러나지 않고 제재 회피와 외부 입구 같은 서비스 구조에서 나오는 길이 빠진다. (c)는 입력이 얇을 때 놓친 길을 확인할 방법이 없다(OM-05). 위협 유형 어휘와 점검 관점의 구성은 일반 지식(미검증)이며 이 프로젝트에서 도출한 것이다. 질문 수가 충분한지는 도메인 교체 시험에서 본다.
- **영향:** 점검 관점 열두 개가 모든 서비스에 적용되는 것은 아니다. 해당하지 않는 관점은 `해당 없음`(사유)으로 닫는 기준을 가이드 5절에 썼다(OM-17).
- **상태:** 검토 대기

### DL-24-004 · 위협 행에 위협 주체, 관련 액터, 대응 방침, 기존 방어 후보 열을 둔다
- **날짜:** 2026-10-09
- **대상:** `templates/24_보안_어뷰징_template.md` 3절 (필드 `위협 주체`, `관련 액터`, `대응 방침`, `기존 방어 후보`, `출처`, `가능성`, `영향`), `guides/24_보안_어뷰징_guide.md` 3.3
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 주체를 문장에 암시하고(OM-03), 모든 위협에 방어를 붙이고(OM-06, SA-16), 후보 열에 다른 단계의 후보 ID를 섞고(SA-17, OM-08), 위협의 출처가 없고(OM-02), 가능성과 영향이 근거 없는 H/M/L이다(SA-14, SA-15, OM-09).
- **검토한 대안:** (a) 위협 주체를 액터 ID 하나로만 쓴다 / (b) 선택지 4종(이용 액터 / 운영 액터 / 계정 없는 외부인 / 외부 시스템)과 액터 ID를 둘 다 둔다 / (c) 대응 방침 없이 모든 위협을 방어로 본다
- **결정:** (b)와 대응 방침 열 `방어 / 수용 / 후속`을 둔다. `계정 없는 외부인`은 액터 목록에 그 역할이 없을 수 있어 관련 액터 칸을 `미정`으로 닫는 기준을 가이드에 쓴다(액터를 만들어 내지 않는다). 가능성과 영향은 `높음 / 중간 / 낮음` 선택지이고 근거가 없으면 `미정`이다. 대응 방침은 판단이 갈리면 가장 보수적인 `방어`를 고른다. 출처에는 점검 관점과 입력 산출물의 ID를 쉼표로 구분해 쓴다. 기존 방어 후보는 입력 산출물이 이미 낸 후보 ID를 가리킨다.
- **이유:** (a)는 액터 목록에 없는 외부인과 운영 권한 오용을 구분하지 못한다. (c)는 위험 수용이나 범위 밖의 위협을 방어 기능으로 만들어 과잉 설계가 된다(OM-06). 가능성·영향을 근거 없이 쓰면 추측이 되므로(CM-09) `미정`으로 닫는 기준이 필요하다.
- **영향:** `수용`과 `후속`의 근거는 입력 문장(위험 수용 기준, 후속 목록)이어야 한다고 가이드 5절에 썼다. 외부인 역할이 액터 목록에 없는 경우는 사람 액터 목록 단계에 환류가 필요할 수 있다(보고의 질문 참조).
- **상태:** 검토 대기

### DL-24-005 · 방어 후보 표는 통일한 후보 표 열에 방어 단계를 더해 쓴다
- **날짜:** 2026-10-09
- **대상:** `templates/24_보안_어뷰징_template.md` 4절 (표 `방어후보`), `guides/24_보안_어뷰징_guide.md` 3.4
- **결정 주체:** 유지보수자 판단
- **배경:** 그룹 F의 후보 표 열은 `ID | 후보 문장 | 구분 | 공통·고유(잠정) | 출처 | (이 단계에서만 필요한 열) | 근거`로 통일하도록 사용자가 정했다(수정목록 G13, DL-20-013). 샘플의 후보 표는 열이 `후보 ID | 출처 | 기능 후보 | 도메인 구분(잠정)`이다(SA-24~SA-27). 샘플에는 방어가 어느 단계에 있는지(OM-07)와 구분(OM-10, SA-28)이 없다.
- **검토한 대안:** (a) 17~21번의 후보 표 열 순서를 그대로 쓴다 / (b) 통일 규칙의 열 순서를 쓰고 이 단계에서만 필요한 열로 `방어 단계`를 더한다
- **결정:** (b). 구분 선택지는 18·19번과 같은 어휘 `기능 후보 / 후속 후보 / 설계 기준 / 프로세스`다. 방어 단계는 `예방 / 탐지 / 대응 / 복구`다.
- **이유:** 사용자 결정(통일)이 17~21번의 모양보다 우선한다고 지시를 받았다. 방어 단계는 예방만 나열하는 편향을 점검하려는 열이고 위협 하나에 단계 여럿의 후보가 필요한지는 가이드 4절이 묻는다.
- **영향:** 17~21번의 열 이름(`기능 후보`, `잠정 도메인 구분` 등)이 24번과 다르다. 통일은 그룹 F 이후 한꺼번에 하기로 했으므로(G13) 이 세트는 통일한 모양으로 먼저 만들었다. 31번이 후보 표를 읽을 때 열 이름 차이를 병합 때 맞춘다.
- **상태:** 검토 대기

### DL-24-006 · 인터페이스 표: 24번 보내는 줄 44개와 외부 입력 줄 4개를 추가하고 잠정 줄 13개를 필드 수준으로 바꾼다
- **날짜:** 2026-10-09
- **대상:** `tools/data/interfaces.csv` (IF-24-001~044, IF-EX-24-001~004 추가, IF-01-056, IF-10-004, IF-10-006, IF-11-015, IF-11-017, IF-14-002, IF-15-003, IF-15-007, IF-15-011, IF-15-018, IF-15-020, IF-19-006, IF-19-009 수정)
- **결정 주체:** 유지보수자 판단
- **배경:** 24번 템플릿 필드 38개는 모두 보내는 필드로 한 줄 이상 나와야 한다(IR-07). 쓰이는 곳의 근거는 샘플의 표시 `후보 풀로 합류 · 22(보안 NFR 근거) · 26(모더레이션·제재 도구)`(SA-07)와 단계 정의다. 받는 쪽이 `24`인 잠정 줄 13개는 24번 필드로 바꿀 수 있게 되었다(IR-10).
