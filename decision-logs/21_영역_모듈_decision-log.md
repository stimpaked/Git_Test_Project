> 21번 세트(템플릿, 단계 가이드, 변환 분석서, 인터페이스 표의 21 관련 연결)의 결정 이력이다. 항목은 추가만 하고 과거 항목은 고치지 않는다(`docs/규칙_결정로그.md`).
> 변환 분석서의 줄 ID(`SA-nn`, `OM-nn`, `DT-nn`)를 `배경`에 적어 근거를 가리킨다(CV-13).

### DL-21-001 · 21번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `conversions/21_영역_모듈_conversion.md`, `templates/21_영역_모듈_template.md`, `guides/21_영역_모듈_guide.md`
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 04번에서 16번까지에 이어 21번 세트를 만든다. 샘플 해부 36행(SA-01~36)과 누락 탐색 17행(OM-01~17)을 같은 절차로 만들었다. 샘플의 영역 16개, 엔티티 27개, 목표 67개는 표 단위로 묶었다(CV-06). 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 세트 파일을 만든다. 정의 ID 접두어는 호출에서 지정한 `Z`로 시작하는 `Z`(영역) 하나를 쓴다. 다른 표는 새 ID를 부여하지 않아 `정의 ID: 없음`이다.
- **이유:** 샘플을 해부하고 누락을 찾은 결과가 템플릿의 모든 변경에 대응한다(정의서 6절 4번). `Z`는 기존 접두어(A, AC, AQ, AR, NC, NQ, X 등)와 겹치지 않는다(TP-28).
- **영향:** 도메인 교체 시험(8번)이 남았다. 인터페이스 표에 21번 보내는 줄 19개를 더하고 앞 단계가 받는 쪽 잠정 줄 4개를 필드 키로 바꿨다(DL-21-009).
- **상태:** 유효

### DL-21-002 · 구성: 배치 방침 → 영역 목록 → 엔티티 배정 → 목표 배정
- **날짜:** 2026-10-08
- **대상:** `templates/21_영역_모듈_template.md` 전체
- **결정 주체:** 유지보수자 판단
- **배경:** 이 단계의 목적은 기능을 담을 상위 영역을 정해 병합과 분류의 틀을 만드는 것이고 산출물은 영역 코드, 책임 엔티티, 포함 목표이다. 샘플은 영역 목록, 엔티티 배정 검사, 목표 배정, 호출 방향 그림 순으로 쓰며 영역을 정하는 방침(운영 기능 배치, 호출 방향)이 영역 목록 앞의 규칙 문장과 맨 뒤 그림에 흩어져 있다(SA-11, SA-28, SA-30). 04·05번의 도출 질문 → 후보 → 판정 → 목록 구성은 후보를 도출하는 단계가 아닌 이 단계에 맞지 않는다.
- **검토한 대안:** (a) 샘플의 순서(영역 목록, 엔티티 배정, 목표 배정, 호출 방향)를 그대로 쓴다 / (b) 영역 후보를 먼저 나열하고 판정하는 후보 정리 표를 둔다 / (c) 영역을 정하는 방침, 영역 목록, 엔티티 배정, 목표 배정의 네 부분으로 나눈다 / (d) 배정 표를 두지 않고 영역 목록에 책임 엔티티와 포함 목표 열을 둔다
- **결정:** (c). 배치 방침 표(속성 표), 영역 목록(정의 ID `Z`), 엔티티 배정, 목표 배정 순으로 둔다. 후속 점검 표는 두지 않고 완료 체크가 맡는다.
- **이유:** (a)는 방침이 영역을 정한 뒤에 나와 영역 목록을 쓰는 순서와 어긋난다(TP-16). (b)는 이 단계의 입력이 이미 엔티티와 목표로 정해져 있어 영역 후보의 출처 구분이 필요하지 않고 단계 정의의 산출물에 후보가 없다. (d)는 DL-21-003에서 다룬다.
- **영향:** 영역 목록이 영역 ID를 부여하고 배정 표 둘이 이를 참조하므로 작성 순서가 곧 표 순서이다. 표 사이의 ID 참조 일치는 도구가 검사하지 못하고 완료 체크와 가이드의 누락 점검이 맡는다(DL-21-011).
- **상태:** 검토 대기

### DL-21-003 · 책임 엔티티와 포함 목표는 영역 열이 아니라 항목별 배정 표로 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/21_영역_모듈_template.md` 3·4절 (필드 `21.엔티티배정.엔티티`, `21.엔티티배정.영역`, `21.목표배정.목표`, `21.목표배정.영역`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 같은 엔티티 배정을 영역 표의 `책임 엔티티` 열과 2절의 배정 표 두 곳에 쓰고(SA-15, SA-20), 목표는 영역마다 `UG-003, 004`처럼 줄여 적는다(SA-24). 엔티티나 목표 하나가 두 영역에 올라도 눈에 띄지 않는다. 단계 정의의 산출물은 영역 코드, 책임 엔티티, 포함 목표이다.
- **검토한 대안:** (a) 영역 표의 열로 책임 엔티티와 포함 목표를 쉼표로 구분해 쓴다 / (b) 영역 표에 열을 두고 배정 표도 별도로 둔다(샘플 방식) / (c) 엔티티와 목표마다 한 행인 배정 표만 두고 영역 표에는 두지 않는다
- **결정:** (c). 배정 표 둘의 행은 입력 목록의 엔티티와 목표이고 영역 칸이 영역 ID를 가리킨다.
- **이유:** (a)와 (b)는 같은 사실이 두 곳에 있거나 한 칸에 여럿이라 정확히 한 영역이라는 요구를 구조로 보장하지 못한다(CM-12). (c)는 행 하나가 영역 하나이므로 정확히 한 영역이 구조로 보이고 영역 배정 검사가 행 단위로 쉽다. 영역에서 보는 책임 엔티티 목록은 이 표를 영역 ID로 거르면 얻는다.
- **영향:** 영역별 책임 엔티티를 한눈에 보려면 배정 표를 거른다. 영역이 비어 있지 않은지는 완료 체크가 확인한다(SA-16).
- **상태:** 검토 대기

### DL-21-004 · 영역 ID `Z-nn`과 영역 코드를 따로 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/21_영역_모듈_template.md` (정의 ID `Z`, 필드 `21.영역목록.ID`, `21.영역목록.영역 코드`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 영문 세 자 코드(`ACC` 등)를 영역의 키로 쓴다(SA-13). 단계 정의의 산출물이 영역 코드를 요구한다. 템플릿 규칙은 새로 부여하는 ID의 접두어를 알파벳 대문자 1~3자로 모든 템플릿에 걸쳐 유일하게 하라고 하고(TP-28), 이번 호출은 `Z`로 시작하는 접두어만 쓰게 했다. 영역 코드의 글자는 프로젝트가 정하는 값이라 템플릿이 정해 둘 수 없다.
- **검토한 대안:** (a) 영역 코드를 영역의 ID로 쓰고 정의 ID를 `없음`으로 둔다 / (b) 정의 ID `Z`로 `Z-01`을 부여하고 영역 코드는 별도 열에 값으로 쓴다
- **결정:** (b). 배정 표는 영역을 `Z-` ID로 가리키고 영역 코드는 영역을 짧게 부르는 이름으로 쓴다.
- **이유:** (a)는 코드의 글자가 프로젝트마다 달라 ID 형식을 힌트로 밝힐 수 없고 코드가 바뀌면 모든 참조가 바뀐다. (b)는 참조를 안정된 ID로 하고 코드를 바꿔도 참조가 유지된다. 대신 열이 하나 늘고 영역 코드가 겹치지 않는지는 사람이 확인해야 한다.
- **영향:** 뒤 단계가 영역을 가리킬 때 `Z-` ID와 영역 코드 가운데 무엇을 쓸지는 뒤 단계가 정한다(IF-21-005, IF-21-006).
- **상태:** 검토 대기

### DL-21-005 · 운영 기능 배치를 방침 표의 선택지 항목으로 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/21_영역_모듈_template.md` 1절 (필드 `21.배치방침.운영 기능 배치`), `guides/21_영역_모듈_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 규칙 4는 관리자 기능을 별도 영역으로 빼지 않고 해당 영역 안에 두며 태그를 붙이고 백오피스 공통 기능만 따로 둔다고 정했다(SA-11). 병원 예약 서비스처럼 운영 기능이 같은 엔티티를 다루는 서비스가 있고(OM-12), 운영 기능이 아예 없는 서비스도 있다.
- **검토한 대안:** (a) 샘플의 규칙을 가이드의 고정 기준으로 쓰고 템플릿에는 두지 않는다 / (b) 세 가지 선택지로 방침 표의 항목에 둔다 / (c) 선택지 없이 자유 서술로 둔다
- **결정:** (b). 선택지는 `소속 영역 안에 두고 태그로 표시` / `별도 영역으로 분리` / `영역 공통의 운영 기능만 별도 영역으로 분리`이고 기본값을 가이드에 두지 않는다. 입력으로 정할 수 없으면 `미정`, 운영 기능이 없으면 `해당 없음`과 사유이다.
- **이유:** (a)는 한 서비스의 판단을 모든 서비스에 못 박는다. (c)는 뒤 단계가 기계적으로 읽을 수 없다. 기본값을 두지 않는 것이 입력에 없는 사실을 만들지 않는 보수적인 쪽이다.
- **영향:** 운영 기능을 태그로 표시한다는 방침은 계층·ID·태그 단계가 태그 어휘로 받아야 한다(IF-21-002). 운영·백오피스 단계가 다루는 운영 업무와의 경계는 그 단계 세트에서 정한다.
- **상태:** 검토 대기

### DL-21-006 · 호출 방향은 그림이 아니라 방침 한 칸으로 두고 정책 값 주입은 의존성 단계에 넘긴다
- **날짜:** 2026-10-08
- **대상:** `templates/21_영역_모듈_template.md` 1절 (필드 `21.배치방침.호출 방향 원칙`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 영역 16개를 노드로 옮긴 그림과 두 문장의 원칙을 쓴다(SA-28~31). 그림의 간선은 하나이고 노드는 영역 목록의 반복이다(OM-06). 단계 정의의 산출물에는 그림이 없다. 정책 값을 설정이나 템플릿으로 주입한다는 둘째 문장은 영역 사이에 값이 오가는 방식으로 호출 관계의 설계이다(SA-31).
- **검토한 대안:** (a) 샘플처럼 그림을 표 없는 필수 블록으로 둔다(TP-29) / (b) 호출 방향 원칙을 방침 표의 한 칸으로 두고 그림은 두지 않는다 / (c) 호출 방향 표를 영역 쌍마다 만든다
- **결정:** (b). 정책 값 주입은 템플릿에 두지 않고 의존성 단계의 몫으로 남긴다. 원칙을 모르면 `미정`, 공통과 고유의 구분이 없는 서비스는 `해당 없음`과 사유로 닫는다(OM-11).
- **이유:** (a)는 영역 목록과 같은 사실을 그림으로 한 번 더 쓰고 그림과 표의 일치를 도구가 검사하지 못한다(DL-21-011). (c)는 영역이 늘수록 행이 제곱으로 늘어난다. 영역 쌍의 호출 관계는 의존성 단계의 산출물이다.
- **영향:** 호출 방향 원칙은 의존성 단계가 제약으로 받는다(IF-21-003). 원칙이 영역 목록의 구분과 어긋나지 않는지는 완료 체크가 확인한다.
- **상태:** 검토 대기

### DL-21-007 · 영역 밖 목표는 열을 더하지 않고 영역 칸을 `해당 없음`(사유)로 닫는다
- **날짜:** 2026-10-08
- **대상:** `templates/21_영역_모듈_template.md` 4절 (필드 `21.목표배정.영역`), `guides/21_영역_모듈_guide.md` 3.4, 5절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 기능이 아니라 출시 프로세스인 목표를 `(영역 없음)` 행으로 따로 적었다(SA-25). 병원 예약 서비스처럼 서비스 밖 업무가 목표에 올라오는 경우가 있다(OM-10). 영역 칸을 비우면 공통 규칙에 어긋난다(CM-04).
- **검토한 대안:** (a) 영역 목록에 "영역 없음"을 뜻하는 영역을 하나 둔다 / (b) 목표 배정에 구분 열(영역 / 영역 밖)을 더한다 / (c) 영역 칸을 `해당 없음`과 사유로 닫는다
- **결정:** (c). 사유에 기능이 아닌 이유와 그 일을 맡는 곳을 쓰게 한다.
- **이유:** (a)는 모든 영역 점검에 예외를 만든다. (b)는 거의 모든 행이 같은 값인 열을 더한다. (c)는 공통 규칙의 닫는 말을 그대로 쓰고 칸 수가 늘지 않는다. ID 칸에 `해당 없음`이 오는 것은 공통 규칙이 허용하는 닫는 말이고 사유가 있는지는 검사 CM-K02가 확인한다.
- **영향:** 영역 밖 목표가 다른 단계에서 누락되지 않도록 그 일을 맡는 곳을 사유에 쓰게 했다. 뒤 단계가 목표 배정의 영역을 읽을 때 `해당 없음` 행을 건너뛴다.
- **상태:** 검토 대기

### DL-21-008 · 기능을 영역에 두는 규칙은 이 단계가 검사하지 않고 엔티티와 목표의 배정으로 틀을 만든다
- **날짜:** 2026-10-08
- **대상:** `templates/21_영역_모듈_template.md` (완료 체크), `conversions/21_영역_모듈_conversion.md` SA-08
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 규칙 1은 한 기능이 정확히 한 영역에 속한다고 하지만 이 단계의 산출물에는 기능이 없다(SA-08, OM-07). 기능은 병합 이후에 생긴다.
- **검토한 대안:** (a) 이 단계에서 앞 단계 기능 후보도 영역에 배정한다 / (b) 기능의 영역 배정은 병합·계층 단계에 두고 이 단계는 엔티티와 목표의 배정만 한다

### DL-21-010 · 병합 때 더해야 할 입력 줄과 환류 줄의 목록
- **날짜:** 2026-10-08
- **대상:** `tools/data/interfaces.csv` (병합할 때 더할 줄), `guides/21_영역_모듈_guide.md` 1절
- **결정 주체:** 유지보수자 판단
- **배경:** 가이드 1절이 읽으라고 하는 입력은 엔티티 목록·엔티티 관계·목표 목록·공통·고유 판정이다(OM-02). 이 가운데 인터페이스 표에서 21번으로 오는 줄은 `07.목표목록.ID`, `11.엔티티목록.ID`, `11.엔티티관계.출발 엔티티`, `11.엔티티관계.대상 엔티티` 넷뿐이다(DL-21-009). 연결 ID는 보내는 단계 번호로 시작하므로 앞 단계가 보내는 줄을 이 세트에서 새로 만들면 같은 번호를 다른 세트가 쓸 때 겹친다.
- **검토한 대안:** (a) 이번 호출에서 앞 단계가 보내는 줄을 직접 더한다 / (b) 병합할 때 더할 줄의 목록만 남긴다
- **결정:** (b). 병합할 때 아래 줄을 더한다. (1) `11.엔티티목록.엔티티` → `21.엔티티배정.영역`, 판단 입력(이름으로 책임 영역을 가린다). (2) `11.엔티티목록.설명` → `21.엔티티배정.영역`, 판단 입력(엔티티가 무엇인지 보고 책임 영역을 가린다). (3) `07.목표목록.목표` → `21.목표배정.영역`, 판단 입력(목표의 결과가 나오는 영역을 가린다). (4) 도메인 공통·고유 단계의 공통·고유 판정 → `21.영역목록.공통·고유`, 판단 입력(필드 키는 해당 템플릿이 생기면 정한다). (5) 같은 단계의 공통 기능 목록 초안 → `21.영역목록.영역`, 판단 입력(공통 영역을 둘지 정하는 단서). 별도 제안: (6) 통합·정규화 또는 계층·ID·태그 단계에서 영역을 추가하거나 나눠야 할 때 `21.영역목록.영역`으로 오는 환류 줄을 둘지 사용자가 정한다(OM-08).
- **이유:** 줄을 새로 만들지 않고 목록으로 남기면 번호 충돌 없이 병합자가 한 번에 정리할 수 있다. 환류는 다른 단계의 산출물을 고치는 흐름이라 사용자 결정이 필요하다.
- **영향:** 병합 뒤 21번 템플릿의 문서 정보 블록 입력에 11번의 필드 `엔티티, 설명`, 07번의 `목표`, 도메인 공통·고유 단계가 나타난다. 환류를 두면 앞 단계 문서의 버전을 올리고 결정 로그에 기록한다(정의서 8절).
- **상태:** 검토 대기
