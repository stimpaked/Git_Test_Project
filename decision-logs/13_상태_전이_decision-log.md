# 결정 로그 — 13. 상태 전이

> 13번 세트(템플릿, 단계 가이드, 변환 분석서, 인터페이스 표의 13 관련 연결)의 결정 이력이다. 항목은 추가만 하고 과거 항목은 고치지 않는다(`docs/규칙_결정로그.md`).
> 변환 분석서의 줄 ID(`SA-nn`, `OM-nn`, `DT-nn`)를 `배경`에 적어 근거를 가리킨다(CV-13).

### DL-13-001 · 13번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `conversions/13_상태_전이_conversion.md`, `templates/13_상태_전이_template.md`, `guides/13_상태_전이_guide.md`
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 04번에서 10번까지에 이어 13번 세트를 만든다. 샘플 해부 40행(SA-01~40)과 누락 탐색 17행(OM-01~17)을 같은 절차로 만들었다. 샘플이 커서 전이표 예순다섯 행과 후보 열네 행은 표 단위로 묶었다(CV-06). 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 세트 파일을 만든다. 정의 ID 접두어는 호출에서 지정한 `S`로 시작하는 `S`(상태), `ST`(전이), `SQ`(후보)를 쓴다.
- **이유:** 샘플을 해부하고 누락을 찾은 결과가 템플릿의 모든 변경에 대응한다(정의서 6절 4번).
- **영향:** 도메인 교체 시험(8번)이 남았다. 인터페이스 표에 13번 보내는 줄 36개와 앞 단계가 받는 쪽 줄의 수정·추가를 더했다(DL-13-009).
- **상태:** 유효

### DL-13-002 · 구성: 대상 엔티티 → 상태 목록 → 전이표 → 상태도 → 상태 점검 → 후보 목록
- **날짜:** 2026-10-08
- **대상:** `templates/13_상태_전이_template.md` 전체
- **결정 주체:** 유지보수자 판단
- **배경:** 이 단계의 목적은 엔티티의 상태와 계기를 정리해 계기 없는 전이와 막다른 상태를 찾는 것이다. 샘플은 상태도(그림)를 앞에 두고 전이표를 뒤에 두며 상태가 있는 엔티티가 어느 것인지, 상태가 무엇을 뜻하는지, 끝 상태인지를 담는 곳이 없다(SA-10, SA-14, SA-17, OM-01~03, OM-09). 04·05번의 도출 질문 → 후보 → 판정 → 목록 구성은 이 단계에 맞지 않는다.
- **검토한 대안:** (a) 샘플의 순서(상태도, 전이표, 후보)를 그대로 쓴다 / (b) 상태 목록 없이 전이표의 시작·종료 상태를 이름으로 쓴다 / (c) 대상 판정, 상태 정의, 전이, 그림, 점검, 후보의 여섯 부분으로 나눈다 / (d) 점검을 별도 표로 두지 않고 완료 체크로만 확인한다
- **결정:** (c). 대상 엔티티 표(판정), 상태 목록(정의 ID `S`), 전이표(`ST`), 상태도(표 없는 필수 블록, TP-29), 상태 점검 표, 후보 목록(`SQ`) 순서로 둔다.
- **이유:** (a)는 같은 전이를 그림과 표에 따로 쓰게 해 어긋난다(SA-15). (b)는 상태 이름의 불일치(SA-17의 `발급 가능`)를 막지 못하고 끝 상태를 표시할 곳이 없다. (d)는 점검을 했다는 증거가 남지 않는다(OM-09). 앞 단계가 점검 표를 두는 선례(유저 플로우의 플로우 점검)와도 맞다.
- **영향:** 전이표가 상태 ID를 참조하고 후보 목록이 전이·상태 ID를 참조하므로 작성 순서가 곧 표 순서이다(TP-16). 상태도와 표의 일치는 도구가 검사하지 못하고 완료 체크와 가이드가 맡는다(DL-13-010).
- **상태:** 검토 대기

### DL-13-003 · 엔티티는 ID가 아니라 이름으로 가리킨다
- **날짜:** 2026-10-08
- **대상:** `templates/13_상태_전이_template.md` (필드 `13.대상엔티티.엔티티`, `13.상태목록.엔티티`, `13.전이표.엔티티`, `13.상태점검.엔티티`), 상태도의 소제목
- **결정 주체:** 유지보수자 판단
- **배경:** 입력인 엔티티 목록(11번)의 템플릿은 아직 없어 엔티티 ID의 형식을 알 수 없다. 샘플의 소제목과 전이표는 이름을 쓰고 소제목에는 샘플 11번의 ID(`E-`)를 덧붙였다(SA-10, SA-21).
- **검토한 대안:** (a) 샘플 체계의 엔티티 ID 접두어를 가정해 ID 참조로 쓴다 / (b) 이 단계가 엔티티의 별칭 ID를 새로 만든다 / (c) 엔티티 목록의 이름을 그대로 쓴다
- **결정:** (c). 힌트는 "엔티티 목록에 쓴 엔티티의 이름 그대로"이다. 상태도의 소제목도 엔티티 이름이다.
- **이유:** (a)는 없는 사실을 만든다. (b)는 같은 엔티티에 ID가 둘이 되어 어긋나기 쉽다. 이름은 11번 템플릿이 어떤 형식이든 지금 쓸 수 있다.
- **영향:** 11번 템플릿이 생겨 엔티티 ID가 정해지면 이 필드들을 ID 참조로 바꿀지 정하고 가이드 1절·3절을 고친다. TP-29의 소제목 예는 표가 부여한 ID이지만 이 단계의 상태도는 엔티티 이름을 쓴다(DL-13-010).
- **상태:** 검토 대기

### DL-13-004 · 전이의 양 끝은 상태 ID 하나로 쓰고 `(생성 전)`·`(소멸)`만 예외로 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/13_상태_전이_template.md` (필드 `13.전이표.시작 상태`, `13.전이표.종료 상태`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 시작 상태에 `(없음)`, `활성·일시정지`, `임의`를, 종료 상태에 `(폐기)`, `이전 상태`, `(SLA 경고)`, 목록에 없는 상태를 섞어 쓴다(SA-22, SA-23, SA-13). 양 끝이 흐리면 막다른 상태와 도달 못 하는 상태를 찾을 수 없다(OM-08).
- **검토한 대안:** (a) 샘플의 값 표기를 그대로 둔다 / (b) 여러 상태를 한 칸에 쓰는 것을 허용하고 `임의`만 금지한다 / (c) 한 행에 시작 상태 하나, 종료 상태 하나만 쓰고 이전 상태로 돌아가는 전이는 상태마다 행을 나눈다
- **결정:** (c). 생성 전과 소멸만 상태 ID 대신 `(생성 전)`, `(소멸)`을 쓴다. 알림처럼 상태가 아닌 값은 후보로 올린다.
- **이유:** (b)는 점검이 행 단위로 기계적이지 않다. (c)는 행이 늘지만 상태도의 선과 표의 행이 일대일이 되어 정합 확인이 쉽다.
- **영향:** 이전 상태로 복원하는 전이가 많은 서비스는 행이 늘어난다. 도메인 교체 시험에서 부담이 과한지 본다.
- **상태:** 검토 대기

### DL-13-005 · 앞 단계 후보는 `기존 후보`로, 새 후보는 후보 목록의 출처로 잇는다
- **날짜:** 2026-10-08
- **대상:** `templates/13_상태_전이_template.md` (필드 `13.전이표.기존 후보`, `13.후보목록.출처`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 전이표 `담당 후보` 칸은 앞 단계의 질문 ID, 12번의 후보 ID, 이 문서 3절의 후보 ID를 한 칸에 섞어 앞 표가 뒤 표의 ID를 참조한다(SA-27, OM-05). 검사 TP-K07도 뒤 표의 접두어를 앞 표가 쓰면 실패로 본다.
- **검토한 대안:** (a) 후보 목록을 전이표보다 앞에 두고 전이표가 새 후보도 참조하게 한다 / (b) 전이표에서 담당 후보 칸을 없애고 후보 목록의 출처만 둔다 / (c) 전이표에는 앞 단계 후보만 쓰고 새 후보는 후보 목록의 출처가 전이를 가리키게 한다
- **결정:** (c). 앞 단계 후보가 없는 전이는 기존 후보 칸을 `해당 없음`과 사유로 닫고 후보 목록의 출처에 쓴다. 전이에서 기능으로의 추적은 두 표에 나뉘고 완료 체크가 모든 전이가 둘 중 한 곳에 있는지 확인한다.
- **이유:** (a)는 후보가 전이에서 나오는 흐름과 거꾸로다(후보의 출처가 순환한다). (b)는 전이와 기능의 연결(샘플의 쓰이는 곳 `34(전이→기능 검사)`)을 앞 단계 후보에 대해서는 잃는다. (c)는 TP-16을 지키고 연결을 모두 남긴다.
- **영향:** 후보 목록에서 전이로의 역방향은 파생이라 전이표에 쓰지 않는다. `해당 없음`의 사유를 전이마다 쓰는 부담이 있다.
- **상태:** 검토 대기

### DL-13-006 · 계기 유형은 다섯 가지이고 계기 주체는 액터 ID로 쓴다
- **날짜:** 2026-10-08
- **대상:** `templates/13_상태_전이_template.md` (필드 `13.전이표.계기 유형`, `13.전이표.계기 주체`), `guides/13_상태_전이_guide.md` 3.3
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 트리거 유형은 사용자·시스템·시간·운영 넷이고 트리거 주체 열에 액터 ID, 호칭, 승인 조건, `시스템`, 목록에 없는 `TTL(3분)`이 섞여 있다(SA-19, SA-24, SA-25). 서비스 밖의 센서나 외부 시스템이 일으키는 계기를 담을 유형이 없다(OM-12).
- **검토한 대안:** (a) 네 유형을 유지하고 외부 계기를 `시스템`에 넣는다 / (b) `외부 호출`을 더해 다섯 유형으로 한다 / (c) 유형 칸 없이 계기 주체의 액터 유형(04·05번)으로만 구분한다
- **결정:** (b). 사용자·운영은 사람 액터, 시간·외부 호출은 비사람 액터, 시스템은 서비스 자신의 판단이라 `해당 없음`과 사유로 닫는다. 열 이름은 단계 정의의 말에 맞춰 `계기`로 한다.
- **이유:** (a)는 서비스 자신의 판단과 서비스 밖 주체를 구분하지 못한다. (c)는 14번(시간)과 26번(운영)이 유형만 보고 전이를 고르는 쓰임을 잃는다. 서비스 안의 구성요소는 액터가 아니라는 앞 단계의 기준(액터 목록의 판단)을 따랐다.
- **영향:** `외부 호출`을 19번(외부 연동)이 받는다는 주장은 근거가 `추정: 가정`이다(DL-13-009). 맞는 시간 트리거 액터가 비사람 액터 목록에 없을 때는 앞 단계 보완이 필요하며 이 단계는 `미정`으로 닫는다(OM-15). 환류 연결은 만들지 않았다.
- **상태:** 검토 대기

### DL-13-007 · 끝 상태 표시와 상태 점검 표를 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/13_상태_전이_template.md` (필드 `13.상태목록.끝 상태`, 표 `상태점검`), `guides/13_상태_전이_guide.md` 3.2, 3.5
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 약속 상태도는 나가는 선이 없는 상태 다섯 개가 의도한 끝인지 알 수 없다(SA-14, OM-03). 들어오는 전이가 없는 상태를 찾는 절차도 없다(OM-04). 점검했다는 증거가 없다(OM-09).
- **검토한 대안:** (a) 끝 상태를 상태도의 `[*]` 선으로만 표시한다 / (b) 상태 목록에 끝 상태 선택지를 둔다 / (c) 점검 표를 엔티티의 판정 표(대상 엔티티)에 합친다
- **결정:** (b)와 별도 점검 표. 끝 상태가 입력으로 확인되지 않으면 `미정`으로 닫고 막다른 상태로 센다. 점검 표는 도달 못 하는 상태, 막다른 상태, 계기 없는 전이를 엔티티마다 `없음`/`있음`으로 쓴다(유저 플로우의 플로우 점검과 같은 어휘).
- **이유:** (a)는 그림을 그린 사람의 주장이라 표와 검사가 쓸 수 없다. (c)는 상태 없음 엔티티가 세 칸을 모두 닫아야 하고 점검을 마지막에 채우게 된다.
- **영향:** 도달 못 하는 상태는 단계 정의의 목적(계기 없는 전이와 막다른 상태)을 넘는 점검이다. 사용자가 범위 밖이라 판단하면 열 하나를 빼면 된다.
- **상태:** 검토 대기

### DL-13-008 · 상태가 있는 엔티티는 모두 상태도를 그린다
- **날짜:** 2026-10-08
- **대상:** `templates/13_상태_전이_template.md` 4절(상태도), `guides/13_상태_전이_guide.md` 3.4
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 엔티티 셋을 `표로만 정의`하고 상태도를 그리지 않았으며 상태 목록이 없어 표 안의 상태 이름이 어긋났다(SA-17). 단계 정의의 산출물은 엔티티별 상태도이다. 상태도는 값 표가 아니라 그림이라 표 없는 필수 블록이다(TP-29).
- **검토한 대안:** (a) 상태가 둘뿐인 엔티티는 상태도를 생략해도 된다 / (b) 모든 상태 있음 엔티티에 필수로 한다 / (c) 선택 블록으로 둔다
- **결정:** (b). 선의 레이블에 전이 ID를 쓰고 표가 원본이며 그림은 표에서 그린다. 해설 주석은 달지 않고 가이드에 소제목만 둔다(GD-11).
- **이유:** 생략을 허용하면 샘플처럼 표만으로 정의된 엔티티에서 막다른 상태를 놓친다. 선택 블록은 표 없는 필수 블록의 취지(단계 정의가 산출물로 요구)와 맞지 않다.
- **영향:** 엔티티가 많은 서비스는 그림이 많아진다. 그림과 표의 일치는 도구가 검사하지 못한다(DL-13-010).
- **상태:** 검토 대기

### DL-13-009 · 인터페이스 표: 앞 단계의 잠정 줄을 필드 수준으로 바꾸고 13번 연결을 추가한다
- **날짜:** 2026-10-08
- **대상:** `tools/data/interfaces.csv` (IF-09-037, 038, 039, 044 / IF-10-003, 005, 018 / IF-13-001~036)
- **결정 주체:** 유지보수자 판단
- **배경:** 13번 템플릿이 생겨 09·10번이 13번에 보내는 문서 수준 잠정 줄 다섯 개를 필드 수준으로 바꿀 수 있게 되었다(IR-10). 템플릿 필드 29개가 모두 보내는 필드로 나와야 한다(IR-07). 쓰이는 곳의 근거는 샘플의 표시 `후보 풀, 14, 16, 26, 34`(SA-07)와 단계 정의다.
- **검토한 대안:** (a) 쓰이는 곳을 샘플 표시에 있는 것만 연결한다 / (b) 샘플 표시와 단계 정의에서 합리적으로 읽히는 소비자를 `추정: 가정`으로 더한다
- **결정:** 수정한 줄은 IF-09-037(→ `13.대상엔티티.상태 유무`), IF-09-038(→ `13.상태목록.상태`), IF-09-039(→ `13.상태목록.근거`), IF-10-003·IF-10-005(→ `13.전이표.계기`)이다. 이 단계가 받는 줄로 09·10번의 질문 ID가 기존 후보로 쓰이는 연결 IF-09-044, IF-10-018을 더했다(샘플 전이표가 두 단계의 질문 ID를 인용하는 사실이 근거이며 샘플이 입력으로 밝히지 않아 `추정: 가정`을 함께 썼다, SA-27). 13번 보내는 줄 36개는 샘플 표시에 있는 14·16·26·31·34번은 근거를 SA-07로, 표시에 없는 15·19·22번과 일부 판단 입력은 `추정: 가정`으로 썼다. 22번은 샘플의 정책 값 문장(SA-09)이 근거다. 대상 엔티티의 세 칸, 상태 점검의 칸, 각 표의 근거 칸, 상태 목록의 설명·끝 상태는 `최종 소비자 없음`과 사유로 닫았다. 모든 13번 줄의 받는 쪽은 뒤 단계 템플릿이 없어 `NN` 잠정 값이다.
- **이유:** 샘플과 단계 정의가 뒷받침하는 만큼만 주장하고 나머지는 가정으로 표시했다.
- **영향:** 입력인 11번(엔티티 목록)의 보내는 줄은 11번 템플릿이 없어 만들지 않았다. 그래서 생성 블록의 입력에 11번이 나오지 않는다. 11번 세트에서 `13.대상엔티티.엔티티`로 보내는 줄을 더해야 한다. IF-09-044와 IF-10-018은 같은 번호를 다른 세트가 쓸 수 있어 합칠 때 확인한다. 11, 12, 14~16, 19, 20, 22, 26, 31, 34번 템플릿이 생기면 해당 잠정 줄을 필드 수준으로 바꾼다.

### DL-13-010 · 제안: 표 사이와 표·그림 사이의 정합 검사가 도구에 없다
- **날짜:** 2026-10-08
- **대상:** `tools/tools-decision-log.md` (알려진 한계), `docs/규칙_템플릿.md` (TP-29)
- **결정 주체:** 유지보수자 판단
- **배경:** 전이표의 시작·종료 상태가 상태 목록의 같은 엔티티 상태인지, 상태도의 노드와 선이 표와 같은지, 후보 목록의 출처가 실제 전이·상태 ID인지는 두 표 또는 표와 그림을 맞대 보아야 안다. 현재 산출물 검사(TP-K13)는 구조(표 키, 열 이름)만 비교한다(DL-10-008과 같은 한계). 또 TP-29는 그림 소제목에 표가 부여한 ID를 쓰는 예만 들고 있는데 이 단계의 소제목은 엔티티 이름이다(DL-13-003).

- **결정:** 규칙 문서와 도구는 바꾸지 않는다. (a) 표 사이의 ID 참조 일치 검사, (b) 상태도(mermaid)의 선 레이블 ID가 전이표와 일치하는지 검사, (c) TP-29의 소제목이 ID가 아닌 이름일 수 있는지 명시하는 것의 도입 여부를 사용자가 정하게 한다. 그때까지는 완료 체크와 가이드의 누락 점검이 맡는다.
- **이유:** 규칙·도구의 변경은 유지보수자가 단독으로 하지 않는다.
- **영향:** 도입하면 `tools/checks.py`에 검사를 더하고 규칙_템플릿에 대응 규칙을 정한다.
- **상태:** 검토 대기
