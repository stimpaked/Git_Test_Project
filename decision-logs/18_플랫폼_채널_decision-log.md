# 결정 로그 — 18. 플랫폼·채널

> 18번 세트(템플릿, 단계 가이드, 변환 분석서, 인터페이스 표의 18 관련 연결)의 결정 이력이다. 항목은 추가만 하고 과거 항목은 고치지 않는다(`docs/규칙_결정로그.md`).
> 변환 분석서의 줄 ID(`SA-nn`, `OM-nn`)를 `배경`에 적어 근거를 가리킨다(CV-13).

### DL-18-001 · 18번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `conversions/18_플랫폼_채널_conversion.md`, `templates/18_플랫폼_채널_template.md`, `guides/18_플랫폼_채널_guide.md`
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 04~16번에 이어 18번 세트를 만든다. 샘플 해부 52행(SA-01~52)과 누락 탐색 25행(OM-01~25)을 같은 절차로 만들었다. 샘플의 주제 16행과 후보 13행은 같은 틀을 되풀이해 칸 값을 표 단위로 묶었다(CV-06). 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 구성(도출 질문 → 후보 → 판정 → 목록)을 따르지 않고 이 단계의 목적(플랫폼·채널마다 달라지는 기능과 제약을 정리한다)에 맞춰 값 표를 넷으로 한다. 1번 표 `플랫폼목록`은 점검 대상 플랫폼과 채널(정의 ID `LP`), 2번 표 `차이점검`은 플랫폼과 점검 주제의 조합마다 판정과 차이·제약(`LD`), 3번 표 `기능후보`는 차이에서 드러난 후보(`LC`), 4번 표 `릴리스영향`은 플랫폼별 릴리스 조건(`LR`)이다(SA-09, SA-11, SA-35, SA-41, OM-03, OM-13). 속성 표와 표 없는 필수 블록, 선택 블록은 없다.
- **이유:** 이 단계의 본질은 플랫폼마다 같은 질문을 되풀이해 차이를 드러내는 것이다. 질문에 답하는 도출 표와 판정 표는 해당하지 않는다. 템플릿의 모든 변경이 분석서의 줄에 대응한다(정의서 6절 4번).
- **영향:** 도메인 교체 시험(8번)과 변환 분석서 `승인`이 남았다. 인터페이스 표에 18번 보내는 줄 28개를 더했다(DL-18-008).
- **상태:** 유효

### DL-18-002 · 차이 점검은 칸 하나가 행 하나인 목록 표로 쓰고 플랫폼은 별도 목록 표에 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/18_플랫폼_채널_template.md` 1·2절 (표 키 `플랫폼목록`, `차이점검`), `docs/규칙_템플릿.md` (TP-12, TP-27)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 행이 주제이고 열이 플랫폼 셋(`iOS(P-01)`, `Android(P-02)`, `관리자 웹(P-03)`)인 교차표이며 칸마다 서술과 `N/A`와 `동일`이 섞여 있다(SA-10~12). 플랫폼 수는 서비스마다 다르다(OM-19, OM-22). 06번과 12번 세트도 같은 이유로 칸 하나가 행 하나인 목록 표를 골랐다(DL-06-002, DL-12-002).
- **검토한 대안:** (a) 샘플처럼 플랫폼을 열로 두고 칸에 서술을 쓴다 / (b) 열을 플랫폼 셋으로 고정한 교차표를 템플릿에 둔다 / (c) 플랫폼을 별도 목록 표로 정의하고 점검 표의 한 행이 주제와 플랫폼의 조합 하나를 맡는다
- **결정:** (c). 점검 표의 열은 `ID | 주제 | 플랫폼 | 판정 | 차이·제약 | 근거`이고 행마다 `LD-` ID를 부여한다. 칸을 가리킬 키가 필요한 이유는 후보의 출처가 점검 행을 가리켜야 하기 때문이다(SA-12, SA-43, OM-08). 플랫폼은 1번 표에 `LP-` ID로 정의한다(OM-03).
- **이유:** (a)는 칸마다 판정과 근거를 붙일 수 없고 한 칸에 후보 ID와 사유가 섞인다. (b)는 플랫폼 수가 다른 서비스에 쓸 수 없다. (c)는 칸마다 근거를 요구하는 공통 규칙(CM-05)과 맞고 열 이름이 고정되어 인터페이스 표의 필드 키를 쓸 수 있다.
- **영향:** 교차표로 한눈에 훑는 보기가 없다. 포함 플랫폼 수 × 점검 주제 수 이상의 행이 생겨 산출물이 길어진다(DL-18-010). 조합이 빠졌는지는 도구가 확인하지 못해 완료 체크와 가이드의 누락 점검이 맡는다.
- **상태:** 검토 대기

### DL-18-003 · 점검 주제를 닫힌 선택지 열여덟 가지로 고정한다
- **날짜:** 2026-10-08
- **대상:** `templates/18_플랫폼_채널_template.md` 2절 (필드 `주제`), `guides/18_플랫폼_채널_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 주제 열은 16개의 열린 목록이고 모바일 앱과 관리자 웹에 묶인 이름이 많다(SA-10, SA-13~26). 단계 이름이 "플랫폼·채널"인데 채널 주제가 없고(OM-01, OM-18), 지원하는 운영체제 버전과 스토어 심사 요건과 결제 방식 같은 주제도 빠져 있다(OM-06, SA-40, OM-23).
- **검토한 대안:** (a) 주제를 자유 서술로 둔다 / (b) 샘플의 16개를 일반화한 이름만 선택지로 둔다 / (c) 샘플의 주제에 채널과 심사·승인 같은 주제를 더해 열여덟 가지 닫힌 선택지로 두고 남는 것은 `그 밖의 플랫폼 제약`에 쓴다
- **결정:** (c). 12번 세트가 처리를 열두 가지로 고정한 것과 같은 방식이다. 주제의 뜻은 단계 가이드 3.2가 표로 설명한다.
- **이유:** (a)는 점검에서 빠지는 주제를 막을 수 없다. (b)는 채널과 심사 요건이 빠진 채 남는다. (c)는 주제를 하나씩 따지게 해 빈 곳이 드러나고 서비스마다 다른 것은 마지막 주제와 차이·제약 문장이 받는다.
- **영향:** 행 수가 늘어난다(DL-18-010). 열여덟 가지가 모든 서비스에 충분한지는 도메인 교체 시험에서 본다. 선택지가 늘면 템플릿 버전을 올리고 가이드와 완료 체크를 함께 고친다.
- **상태:** 검토 대기

### DL-18-004 · 판정을 네 값으로 하고 판정에 따라 차이·제약을 닫는다
- **날짜:** 2026-10-08
- **대상:** `templates/18_플랫폼_채널_template.md` 2절 (필드 `판정`, `차이·제약`), `guides/18_플랫폼_채널_guide.md` 3.2, 5절
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 칸은 서술, `N/A: 사유`, `N/A: 해당 없음`, `동일`, `Later(LT-10)`, `—`가 섞여 있다(SA-28~32). 사유 없는 닫음이 열 곳이 넘는데도 완료 기준은 "모든 N/A에 사유가 있다"고 체크되어 있다(SA-29, SA-51). 플랫폼이 하나뿐인 서비스에서는 "다른 플랫폼과의 차이"로 판정을 정의할 수 없다(OM-19).
- **검토한 대안:** (a) 샘플의 표기를 유지하고 사유를 요구한다 / (b) 판정을 `차이 있음` / `차이 없음` 둘로 한다 / (c) `전용 대응` / `공통 대응` / `성립하지 않음` / `범위 밖` 넷으로 하고 `전용 대응`만 차이·제약에 값을 쓴다
- **결정:** (c). 판정은 다른 플랫폼과의 비교가 아니라 이 플랫폼에서 서비스가 따로 정할 것이 있는지로 고른다. 나머지 세 판정은 차이·제약을 `해당 없음`과 사유로 닫는다. 후속 목록의 항목은 판정이 아니라 후보의 구분 `후속 후보`로 옮긴다(SA-31, OM-11).
- **이유:** (a)는 `N/A`가 이 체계의 닫는 말이 아니고 값이 섞여 읽을 수 없다. (b)는 개념이 없는 경우와 범위 때문에 다루지 않는 경우를 가르지 못하고 비교 대상이 없을 때 쓸 수 없다. (c)는 12번 세트의 판정 `제외` 방식과 같은 틀이면서 뒤 단계가 `범위 밖`과 `성립하지 않음`을 의도적 제외 목록의 후보로 읽을 수 있다(IF-18-012).
- **영향:** 공통 규칙 CM-04는 `해당 없음`을 "개념 자체가 이 프로젝트에 없을 때"로 정의하는데 `공통 대응`과 `범위 밖` 행의 차이·제약에도 `해당 없음`을 쓰게 된다. 12번 세트의 같은 문제(DL-12-010)와 함께 사용자가 정한다(DL-18-010). 판정과 차이·제약의 조합이 맞는지는 도구가 확인하지 못해 완료 체크가 맡는다.
- **상태:** 검토 대기

### DL-18-005 · 기능 후보 표에 적용 플랫폼과 구분을 두고 앞 단계와 같은 어휘를 쓴다
- **날짜:** 2026-10-08
- **대상:** `templates/18_플랫폼_채널_template.md` 3절 (필드 `출처`, `적용 플랫폼`, `구분`, `공통·고유(잠정)`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 후보 표에는 후보가 필요한 플랫폼이 없어 32번의 플랫폼 태그와 36번의 플랫폼별 분할이 점검 표를 거슬러 읽어야 한다(SA-07, SA-48, OM-10). 기능이 아닌 설계 기준과 후속으로 미룬 후보가 문장 속 표시뿐이다(SA-46, SA-47, OM-02, OM-11). 출처는 주제 이름뿐이다(SA-43). 앞 단계(이벤트, 시나리오 5유형)가 같은 문제를 `구분`(기능 후보 / 후속 후보 / 설계 기준)과 `공통·고유(잠정)`(공통 / 고유)로 풀었다(DL-16-005).
- **검토한 대안:** (a) 샘플처럼 후보에 플랫폼과 구분을 두지 않는다 / (b) 앞 단계와 같은 `구분`, `공통·고유(잠정)`에 `적용 플랫폼`을 더한다 / (c) 이 단계만의 새 어휘를 만든다
- **결정:** (b). 같은 값을 두 단계가 서로 다른 어휘로 쓰지 않는다. `공통·고유(잠정)`은 갈리면 `고유`를 고른다(이벤트 단계의 기준과 같은 보수적 쪽). 출처는 점검 행의 `LD-`를 쉼표로 쓰고(SA-43), 적용 플랫폼은 `LP-`를 쉼표로 쓴다. `전체` 같은 묶음 값은 두지 않는다.
- **이유:** 뒤 단계(통합·정규화, 도메인 공통·고유)가 여러 단계의 후보를 한 어휘로 읽어야 한다. 적용 플랫폼은 플랫폼 태그와 릴리스 분할에 필요한 사실이다.
- **영향:** 후속 후보의 후속 항목을 읽는 입력이 인터페이스 표에 아직 없다(DL-18-008). 플랫폼마다 달라지는 후보는 행이 나뉜다.
- **상태:** 검토 대기

### DL-18-006 · 플랫폼 목록에 종류, 범위 구분, 이용 액터, 기준 버전·정책을 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/18_플랫폼_채널_template.md` 1절 (필드 `종류`, `범위 구분`, `이용 액터`, `기준 버전·정책`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 플랫폼은 열 제목의 이름과 02번 ID뿐이다(SA-11). 제외한 플랫폼은 칸 안의 `N/A` 사유로만 나오고(SA-33, OM-04), 어느 버전과 정책을 기준으로 점검했는지 없다(SA-08, OM-05). 같은 종류라도 이용자가 다르거나 알림 받는 사람이 다른 서비스가 있고(OM-17, OM-24), 채널이나 장치는 비사람 액터이기도 하다(OM-20, OM-21).
- **검토한 대안:** (a) 플랫폼을 열 제목에만 둔다 / (b) 플랫폼의 이름과 종류만 목록으로 둔다 / (c) 종류, 범위 구분, 이용 액터, 기준 버전·정책을 함께 둔다
- **결정:** (c). `종류`는 여섯 값(네이티브 앱 / 웹 / 데스크톱 앱 / 장치·단말 / 메시지 채널 / 대화형 채널)이다. `범위 구분`은 범위·제약 문서의 어휘(포함 / 후속 / 제외)를 그대로 쓴다. `이용 액터`는 사람 액터와 비사람 액터의 ID를 모두 허용한다. 입력이 붙인 플랫폼 후보 ID(`P-` 등)는 쓰지 않고 `LP-`를 새로 부여하되 원래 ID는 근거에 참조로 남긴다. 범위·제약 템플릿이 생기면 ID를 어떻게 이어받을지 다시 정한다.
- **이유:** 점검 표가 플랫폼을 ID로 가리키려면 정의가 필요하다. 범위 구분이 있어야 점검 대상이 포함 플랫폼으로 한정되고 제외와 후속도 기록으로 남는다. 기준 버전·정책은 정책이 버전에 따라 바뀐다는 샘플의 주의(SA-08)를 칸으로 옮긴 것이다.
- **영향:** 지원할 버전의 범위는 호환성 요구를 정하는 뒤 단계의 몫이라 입력에 없으면 `미정`이 많아진다(입력 부족이며 구조의 결함이 아니다). 범위 구분의 값은 범위·제약 템플릿이 생길 때 어휘가 같은지 확인한다.
- **상태:** 검토 대기

### DL-18-007 · ID 접두어는 플랫폼 `LP`, 차이 점검 `LD`, 기능 후보 `LC`, 릴리스 영향 `LR`로 한다
- **날짜:** 2026-10-08
- **대상:** `templates/18_플랫폼_채널_template.md` (정의 ID `LP`, `LD`, `LC`, `LR`)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 후보 ID는 `CF-18-nn`이라 단계 번호를 ID 안에 넣는다(SA-42). 템플릿 규칙(TP-28)은 접두어가 모든 템플릿에 걸쳐 유일하라고 하고, 이번 호출은 `L`로 시작하는 접두어만 쓰게 했다.

- **결정:** (b). 열 이름 `기능 후보`를 `후보 문장`으로 바꾸고 열 순서를 통일했다(적용 플랫폼은 단계 고유 열로 출처 뒤에 둔다). 구분 선택지에 `프로세스`를 더했다. 필드 키가 바뀌어 인터페이스 표와 변환 분석서의 이름을 맞췄다. `구분`의 선택지는 `기능 후보`, `후속 후보`, `설계 기준`, `프로세스` 네 가지다.
- **이유:** 뒤 단계(20, 31, 34)가 후보 표를 단계마다 다른 열로 읽지 않게 한다.
- **영향:** 템플릿 버전이 올랐다. 이 단계의 가이드는 열 이름과 `구분` 설명을 맞춰야 한다. 이미 쓴 이 단계의 시험 산출물은 열 구성이 달라 다시 써야 한다.
- **상태:** 검토 대기

### DL-18-015 · `미정`의 확인처를 값을 받아 쓰는 뒤 단계로 지정하지 않는다
- **날짜:** 2026-10-09
- **대상:** `guides/18_플랫폼_채널_guide.md` v1.4
- **결정 주체:** 사용자 결정
- **배경:** 그룹 F 도메인 교체 시험(22번 DT-05)에서 14번 허용 지연의 확인처가 비기능·품질 담당으로 지정되어 있고 22번에 그 값을 정할 입력이 없어 확인처가 순환했다. 사용자가 정리하기로 했다(G23의 둘째 부분).

- **결정:** (b).
