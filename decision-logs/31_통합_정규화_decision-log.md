> 31번 세트(템플릿, 단계 가이드, 변환 분석서, 인터페이스 표의 31 관련 연결)의 결정 이력이다. 항목은 추가만 하고 과거 항목은 고치지 않는다(`docs/규칙_결정로그.md`).

### DL-31-001 · 31번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-10
- **대상:** `conversions/31_통합_정규화_conversion.md`, `templates/31_통합_정규화_template.md`, `guides/31_통합_정규화_guide.md` (04번, 05번, 08번, 20번, 30번에 이은 복제)
- **결정 주체:** 사용자 승인 (그룹 단위 진행을 승인함(DL-05-005))
- **배경:** 샘플 해부 53행(SA-01~53)과 누락 탐색 28행(OM-01~28)을 같은 절차로 만들었다. 단계 정의의 목적은 단계마다 나온 후보의 중복과 동의어를 병합해 하나의 기능 목록으로 정리하는 것이고 산출물은 기능 목록 초안이다. 샘플의 31번에는 기능 하나를 한 행으로 쓴 표가 없고 요약과 355행의 매핑표만 있으며(OM-01), 판단 규칙을 산출물 안에 표로 두고(SA-08), 최종 기능 ID를 먼저 쓰고(SA-39), 같은 사실을 후보→기능과 기능→후보 두 방향으로 쓴다(SA-35).
- **검토한 대안:** 04·05번처럼 도출 질문 → 후보 → 판정 → 목록의 구성으로 하는 안, 29·30번처럼 외부 기준의 항목을 한 행씩 판정하는 안, 풀 전체를 소진하는 제외 목록·용어 정리·기능 목록·표별 소진·집계의 구성으로 하는 안을 비교했다. 이 단계는 후보를 찾는 단계도 외부 기준을 맞대는 단계도 아니고 풀 안의 후보를 하나의 목록으로 줄이는 단계이므로 앞의 두 안은 버렸다.
- **결정:** 값 표 다섯을 둔다. 제외 목록(목록 표, 정의 ID `FE`), 용어 정리(목록 표, 정의 ID 없음), 기능 목록(목록 표, 정의 ID `FN`), 표별 소진(목록 표, 정의 ID 없음), 집계(속성 표, 정의 ID 없음). 필드는 모두 34개다. 선택 블록과 표 없는 절은 없다. 표 순서는 작성 순서(제외할 후보를 가리고, 용어를 정리하고, 병합하고, 소진을 맞추고, 센다)를 따른다.
- **이유:** 템플릿의 모든 표와 필드가 분석서의 줄에 대응한다(정의서 6절 4번). 표 키 `기능목록`, `제외목록`, `용어정리`, `집계`는 같은 그룹의 세 단계 사이 약속으로 고정되었다.
- **영향:** 도메인 교체 시험(작업 순서 8번)이 남았다. 시험 전까지 변환 분석서의 상태는 `초안`이다. 인터페이스 표는 DL-31-002~DL-31-003.
- **상태:** 유효

### DL-31-002 · 인터페이스 표: 잠정 줄 105개를 필드 수준으로 바꾸고 31번 보내는 줄 42개를 추가한다
- **날짜:** 2026-10-10
- **대상:** `tools/data/interfaces.csv` (받는 단계가 31인 IF-09-018부터 IF-30-034까지 105개 수정, IF-31-001~042 추가)
- **결정 주체:** 유지보수자 판단
- **배경:** 31번 템플릿이 생겨 앞 단계(09~30번)가 31번으로 보내던 문서 수준 잠정 줄 105개를 필드 수준으로 바꿀 수 있게 되었다(IR-10). 템플릿 필드 34개는 모두 보내는 필드로 한 줄 이상 나와야 한다(IR-07). 쓰이는 곳은 샘플의 머리말(SA-07)과 단계 정의가 뒷받침한다.
- **검토한 대안:** 받는 쪽 필드를 하나로 고르지 않고 잠정 줄을 그대로 두는 안, 줄마다 받는 쪽 필드를 하나 고르는 안을 비교했다. 앞 안은 31번의 입력 블록이 필드 수준이 되지 못해 버렸다.
- **결정:** 수정한 줄의 받는 쪽은 후보 ID가 `31.기능목록.병합 후보`(참조), 후보 문장이 `31.기능목록.기능명`, 구분이 `31.기능목록.구분`, 공통·고유(잠정)이 `31.기능목록.공통·고유`, 출처와 유사 서비스 후보가 `31.기능목록.근거`(근거 인용), 용어집의 표준 용어와 사용하지 않는 동의어와 정의가 `31.용어정리.표준 용어`, `31.용어정리.바꾼 말`, `31.용어정리.근거`, 영역·모듈의 줄 일곱이 `31.기능목록.영역`이다. 타이머의 관련 후보, 이벤트 목록의 소비 기능 칸 넷, 도메인 공통·고유의 공통 기능 ID, 위협 목록의 기존 방어 후보, 성장 지점의 현재 대응, 성장·측정 후보의 유형, 표준 카탈로그 대조의 공통 기능과 환류 대상은 후보를 합칠 단서이므로 `31.기능목록.병합 후보`(판단 입력 또는 참조)로 보냈다. 요구 목록의 처리는 `31.제외목록.사유`, 위협 목록의 대응 방침은 `31.기능목록.구분`으로 보냈다. 수정한 줄의 근거 칸에는 이 항목을 덧붙였다. 추가한 31번 줄은 42개다. 소비자가 있는 줄은 20개이고 받는 단계는 32, 33, 34, 36이며 모두 문서 수준 잠정 값이다. 소비자가 없는 줄 22개는 `최종 소비자 없음`과 사유로 닫았다(제외 목록의 후보 문장과 근거, 용어 정리 네 칸, 기능 목록의 근거, 표별 소진 다섯 칸, 집계 열 칸). 샘플의 쓰이는 곳 표시와 단계 정의가 뒷받침하지 않는 소비자는 근거 칸에 `추정: 가정`을 썼다.
- **이유:** 템플릿 필드마다 소비자나 사유가 있어야 한다(IR-07). 후보 문장을 `기능명`으로 보낸 것은 받는 쪽 필드를 하나로 골라야 해서이고, 설명·제외 목록 문장·용어 정리로 가는 줄은 DL-31-003에서 병합 때 더한다.
- **영향:** 32, 33, 34, 36번 템플릿의 입력 블록은 이 줄들로 바뀐다. 31번 템플릿의 입력 블록은 `build.py`로 다시 만들었다. 받는 쪽 필드를 어느 칸으로 할지는 판단이라 `검토 대기`다.
- **상태:** 검토 대기

### DL-31-004 · 임시 번호 `FN-001`을 쓰고 최종 기능 ID는 계층·ID·태그 단계가 붙인다
- **날짜:** 2026-10-10
- **대상:** `templates/31_통합_정규화_template.md` 31.기능목록.ID, `guides/31_통합_정규화_guide.md` 3.3
- **결정 주체:** 사용자 결정
- **배경:** 샘플의 31번은 최종 기능 ID `F-<영역 코드>-번호`를 먼저 쓰는데(SA-39, OM-02) 단계 정의는 고유 ID를 붙이는 일을 32번의 목적으로 둔다. 그룹 I 호출 지시서가 사용자가 확정한 설계(DL-05-005 방식, 이 그룹의 쟁점 1)로 전달했다.

### DL-31-005 · 구분별 처리: 기능 후보와 후속 후보는 기능 목록의 행으로, 설계 기준과 프로세스는 제외 목록으로

### DL-31-006 · 후보 전수 소진: 후보 ID는 입력 그대로 하나씩 쓰고 표별 소진으로 맞춘다

### DL-31-014 · 도메인 교체 시험 반영: 영역을 정하는 순서와 공통 기능을 구현하는 기능이 없는 경우
- **날짜:** 2026-10-10

- **배경:** 그룹 I 도메인 교체 시험(학교 급식 알레르기 관리, 농장 센서 모니터링). 영역 결정 순서(엔티티, 목표, 공통 기능 배정)가 문장 안에서 서로 어긋나 두 도메인이 달리 읽었고, 공통 기능의 호출 후보가 모두 설계 기준이라 구현하는 기능이 없는 경우(도메인 A의 DC-19, 도메인 B의 DC-11·12·16)를 가이드가 다루지 않았다.

### DL-31-015 · 판정이 혼합인 후보를 같은 공통 기능의 혼합 후보나 고유 후보와 합칠 수 있게 한다
- **날짜:** 2026-10-10
- **대상:** `guides/31_통합_정규화_guide.md` v1.2 (3.3절 병합 기준과 공통·고유)
- **결정 주체:** 사용자 승인
- **배경:** DL-31-008은 판정이 혼합인 후보를 다른 후보와 합치지 않게 했다. 그룹 I 시험에서 도메인 B는 의미가 같은 기능 여섯 개(혼합과 혼합, 혼합과 고유)가 따로 생겨 이름만 달리 지어야 했다. 또 DL-31-008의 이유와 가이드의 입도 규칙은 "나뉜 기능은 역추적 검증 단계에서 합칠 수 있다"고 썼는데, 단계 정의상 합치는 단계는 31번 하나이고 34번은 과잉과 누락을 가려내기만 하므로 이 전제는 틀렸다.
- **검토한 대안:** (a) 혼합 후보를 합치지 않는 규칙을 유지한다 / (b) 혼합 후보를 같은 목표·대상·동작이고 같은 공통 기능 ID를 가리키는 혼합 후보, 그리고 고유 후보와 합칠 수 있게 하고 판정이 공통인 후보는 합치지 않는다 / (c) 혼합 후보를 공통 후보와도 합친다
- **결정:** (b). 사용자가 2026-10-10에 권장안으로 승인했다. 합친 기능의 공통·고유는 `고유`이고 근거에 혼합 판정과 공통 기능 ID를 쓴다. 서로 다른 공통 기능 ID를 가리키는 후보, 영역이 다른 후보, 구분이 다른 후보는 여전히 합치지 않는다. 입도 규칙의 근거 문장은 이후 단계가 기능을 합치지 않는다는 사실에 맞게 고쳤다.
- **이유:** 공통 부분과 고유 정책의 분리는 20번의 공통 기능 표와 혼합 분리 표에 남고, 병합 후보에 그 후보 ID가 들어 있으면 33번이 병합 후보에서 공통 기능을 찾아갈 수 있어 합쳐도 근거를 잃지 않는다. 공통 후보는 공통 기능으로 한 번만 구현되어야 하므로 합치지 않는다. 합치는 단계가 31번 하나뿐이어서 여기서 정하지 않으면 중복이 32번 기능 ID로 굳는다.
- **영향:** 31번 가이드 v1.2. 기능 수가 줄 수 있다. 도메인 A에서 보고된 경우(같은 문장이 20번 판정은 공통, 다른 단계의 잠정 값은 고유)는 이 결정이 다루지 않는다. 이 변경은 시험 자료로 다시 시험하지 않았다. DL-31-008의 해당 항목과 DL-31-010의 "혼합은 다른 후보와 합치지 않는다"는 이 결정이 바꾼다.
- **상태:** 검토 대기

### DL-31-016 · 후보 판정에 행이 없는 후보를 환류 미완료로 알리게 한다
- **날짜:** 2026-10-10
- **대상:** `guides/31_통합_정규화_guide.md` v1.3 (1절, 4절)
- **결정 주체:** 사용자 승인
- **배경:** 그룹 I 시험에서 도메인 A는 같은 기능을 가리키는 두 후보 가운데 하나만 20번 판정이 있고(공통), 다른 하나는 다른 단계의 잠정 값(고유)만 있어 합치지 못했다. 22~30번의 모든 후보는 20번 후보판정으로 환류되도록 인터페이스 표가 정하고 있으므로 판정 없는 후보는 환류가 끝나지 않은 상태이고, 시험이 20번을 09~19번 후보로만 먼저 만들고 환류를 건너뛴 것이 원인이었다.
- **검토한 대안:** (a) 판정이 잠정 값을 이기는 합치기 규칙을 더한다 / (b) 31번이 쓰기를 멈추게 한다 / (c) 환류 누락을 알리고 기계 검사로 잡는다(합치기 규칙은 그대로) / (d) 집계에 판정 없는 후보 수 칸을 더한다
- **결정:** (c). 사용자가 2026-10-10에 권장안으로 승인했다. 가이드 v1.3은 판정 행이 없는 후보를 사용자에게 알리고, 잠정 값으로 쓰되 판정 후보와 공통·고유가 다르면 합치지 않게 한다. `check_chain.py`에 CH-K07(경고)을 더한다.
- **이유:** (a)는 환류 누락을 31번이 조용히 덮고 판정 공통 후보를 합치지 않는 원칙에 예외를 만든다. (b)는 입력이 부족하면 멈추지 않고 `미정`으로 닫는 체계의 원칙과 다르다. (d)는 템플릿 변경이 필요하고 근거 칸이 이미 잠정 값 사용을 기록한다.
- **영향:** 31번 가이드 v1.3. 전체 점검 시험은 22~30번 후보를 20번에 환류한 뒤 31번을 쓰는 순서로 하고 CH-K07이 경고 0인지 확인한다. 환류를 거쳐도 판정 없는 후보가 남으면 그때 규칙을 정한다.
- **상태:** 검토 대기
