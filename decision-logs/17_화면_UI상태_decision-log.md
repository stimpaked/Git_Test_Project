### DL-17-001 · 17번 변환 분석서와 템플릿 v1.0, 단계 가이드 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `conversions/17_화면_UI상태_conversion.md`, `templates/17_화면_UI상태_template.md`, `guides/17_화면_UI상태_guide.md`
- **결정 주체:** 사용자 승인
- **배경:** 그룹 단위 진행을 승인함(DL-05-005). 04~16번에 이어 17번 세트를 만든다. 샘플 해부 45행(SA-01~45)과 누락 탐색 20행(OM-01~20)을 같은 절차로 만들었다. 샘플의 화면 62행, 비정상 상태 14행, 후보 13행은 같은 틀을 되풀이하므로 값은 표 단위로 묶어 해부했다(CV-06). 도메인 교체 시험(③)은 템플릿과 가이드를 쓴 뒤에 하므로 아직 하지 않았고 분석서의 상태는 `초안`이다.
- **검토한 대안:** 해당 없음 — 변환 절차(정의서 6절)를 따랐다.
- **결정:** 04·05번의 "도출 질문 → 후보 → 판정 → 목록" 흐름을 따르지 않고 단계의 목적(화면과 화면마다 정상이 아닌 상태를 정리해 빠진 화면과 상태를 드러낸다)에서 구성을 정했다. 구성은 DL-17-002에 있다. 도메인 교체 시험은 하지 않았다.
- **이유:** 샘플을 해부하고 누락을 찾은 결과가 템플릿의 모든 변경에 대응한다(정의서 6절 4번, 검사 CV-K04).
- **영향:** 도메인 교체 시험과 변환 분석서 `승인`이 남았다. 입력 연결 중 아직 인터페이스 표에 없는 줄은 만들지 않았다(DL-17-010). 18·20·22·26·31·34·35번 템플릿이 생기면 17번이 보내는 잠정 줄을 필드 수준으로 바꾼다.
- **상태:** 유효

### DL-17-002 · 값 표를 화면 인벤토리, 비정상 상태, 후보 목록 셋으로 둔다
- **날짜:** 2026-10-08
- **대상:** `templates/17_화면_UI상태_template.md` 1~3절 (표 키 `화면인벤토리`, `비정상상태`, `후보목록`)
- **결정 주체:** 유지보수자 판단
- **배경:** 단계 정의의 산출물은 화면 인벤토리와 화면별 비정상 상태 목록이다. 샘플은 같은 두 표에 후보 풀로 넘기는 표를 더한 셋이다(SA-09, SA-22, SA-34). 04·05번의 도출 질문과 판정 표는 이 단계의 목적에 없다. 그림이나 표 없는 필수 블록은 이 단계에 필요하지 않다.
- **검토한 대안:** (a) 샘플의 세 표를 그대로 둔다 / (b) 상태 종류를 정의하는 표를 더해 작성자가 상태 목록을 정하게 한다 / (c) 세 표를 유지하되 표마다 판정과 근거를 갖게 하고 후보 표는 판정이 후보인 행에서만 나오게 한다
- **결정:** (c). 1번 표는 화면 목록(정의 ID `U`), 2번 표는 핵심 화면 × 상태의 목록(정의 ID 없음), 3번 표는 두 표에서 드러난 기능 후보(정의 ID `UC`)다. 뒤 표가 앞 표의 ID를 참조하는 순서이며 TP-16과 맞는다.
- **이유:** (a)는 판정과 근거가 없어 새로 드러난 것을 읽을 수 없다(OM-02, OM-03). (b)는 상태 종류가 서비스와 무관한 닫힌 낱말이라 정의 표의 값이 모든 산출물에서 같아진다(DL-17-004). (c)는 12번 세트의 구성(판정을 가진 목록 표와 후보 목록)과 같은 방향이면서 이 단계의 두 산출물을 그대로 담는다.
- **영향:** 화면 인벤토리의 후보 화면과 상태 표의 후보 행이 후보 목록에 모두 있는지는 도구가 검사하지 못해 완료 체크와 가이드의 누락 점검이 맡는다(DL-17-012).
- **상태:** 검토 대기

### DL-17-003 · 비정상 상태는 화면과 상태의 조합이 한 행인 목록 표로 쓴다
- **날짜:** 2026-10-08
- **대상:** `templates/17_화면_UI상태_template.md` 2절 (표 키 `비정상상태`), `docs/규칙_템플릿.md` (TP-12, TP-27)
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 행이 화면이고 열이 상태 여섯인 교차표이며 칸마다 동작 또는 `N/A: 사유`가 한 줄로 들어 있다(SA-22, SA-30~33). 06번과 12번 세트는 교차 구조를 칸 하나가 행 하나인 목록 표로 바꾸었다(DL-06-002, DL-12-002). 이 단계는 상태 종류가 아홉 가지로 고정되므로 열을 템플릿에 고정할 수 있지만, 칸마다 판정과 근거를 붙여야 한다(OM-02, OM-03).
- **검토한 대안:** (a) 화면을 행, 상태를 열로 둔 교차표를 쓰고 칸에 동작을 쓴다 / (b) 교차표에 판정·근거를 칸마다 따로 적는 상세 표를 더한다 / (c) 화면과 상태의 조합이 행 하나인 목록 표를 쓰고 원인마다 동작이 다르면 행을 나눈다
- **결정:** (c). 열은 `화면 | 상태 | 판정 | 동작 | 근거`다. 별도의 칸 ID는 만들지 않고 화면 ID와 상태 이름의 조합을 칸의 키로 본다(OM-06).
- **이유:** (a)는 칸 하나에 판정과 근거를 붙일 수 없고 한 칸의 여러 원인(위치와 사진의 권한 거부)을 따로 읽을 수 없다(OM-13). (b)는 같은 사실을 두 곳에 쓰게 한다(CM-12). (c)는 칸마다 근거를 요구하는 공통 규칙(CM-05)과 맞고 인터페이스 표의 필드 키를 그대로 쓸 수 있다.
- **영향:** 교차표로 한눈에 훑는 보기가 없다. 핵심 화면 수 × 9 이상의 행이 생겨 산출물이 길어진다. 칸이 빠지지 않았는지는 도구가 확인하지 못해 완료 체크가 맡는다. 규칙 문서 변경 제안은 DL-17-012에 있다.
- **상태:** 검토 대기

### DL-17-004 · 비정상 상태의 종류를 샘플의 여섯에서 아홉 가지로 가른다
- **날짜:** 2026-10-08
- **대상:** `templates/17_화면_UI상태_template.md` 2절 (필드 `상태`), `guides/17_화면_UI상태_guide.md` 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플의 열 여섯(빈 상태, 로딩, 오류, 오프라인, 권한 거부, 세션 만료·정지) 중 둘이 서로 다른 출처를 묶는다. `권한 거부`에는 기기 권한 거부(SA-25)와 서비스의 접근 규칙이 막은 경우(SA-26)가, `세션 만료·정지`에는 로그인이 풀린 경우와 사용자 상태 제한(SA-27, SA-28)이 있다. 열려는 대상이 없는 경우는 빈 상태의 `N/A`에 접혀 있다(SA-29). 소유·권한 단계는 접근 규칙(`불가`, `조건부 허용`)과 사용자 상태별 제한을 따로 만들고 화면에 보낸다(IF-15-017~030)(OM-07).
- **검토한 대안:** (a) 샘플의 여섯 열을 그대로 쓴다 / (b) 권한 거부와 세션 만료·정지만 가르고 대상 없음은 두지 않는다 / (c) 아홉 가지(빈 상태, 로딩, 오류, 오프라인, 기기 권한 거부, 접근 권한 없음, 세션 만료, 이용 제한, 대상 없음)로 가른다
- **결정:** (c). 입력 검증 실패, 일부 성공, 오래된 값은 오류에 배정하고 엔티티 상태의 표시는 비정상 상태가 아니라는 기준을 가이드에 둔다(OM-15, OM-20). 서비스 전체 상태(점검 등)는 상태가 아니라 화면 하나로 인벤토리에 올린다(OM-10).
- **이유:** (a)는 소유·권한 단계가 보내는 두 입력이 한 열에 섞여 어느 입력이 어느 칸을 채우는지 읽을 수 없다. (b)는 상세 화면이면 어느 서비스에서나 생기는 대상 없음을 빈 상태로 접어 넣게 한다(OM-18). (c)는 입력의 출처와 상태가 일대일로 맞는다.
- **영향:** 핵심 화면마다 아홉 행이 필요해 `제외` 행이 늘어난다(OM-16, OM-17). 여섯으로 줄이려면 사용자가 정해야 한다. 닫힌 목록이라 아홉 가지 밖의 상태는 가장 가까운 상태에 배정하는 기준으로 다룬다. 도메인 교체 시험에서 배정 기준이 흔들리는지 본다.
- **상태:** 검토 대기

### DL-17-005 · 핵심 화면을 인벤토리의 열로 표시하고 비정상 상태 표는 핵심 화면만 다룬다
- **날짜:** 2026-10-08
- **대상:** `templates/17_화면_UI상태_template.md` 1·2절 (필드 `핵심 화면`, `비정상상태.화면`), `guides/17_화면_UI상태_guide.md` 3.1
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 62개 화면 중 14개의 비정상 상태만 쓰고 "핵심"의 기준이 없다(SA-20, OM-05). 06번 세트도 핵심 구간으로 표시한 단계에서만 접점·불편을 쓰는 선례가 있다. 12번 세트는 엔티티 × 처리를 모두 한 행씩 쓰는 구조를 사용자 결정으로 유지했다(DL-12-012). 같은 판단이 이 단계에 그대로 맞는지는 다르다. 화면 수가 많고 입력 전용 화면은 대부분의 상태가 성립하지 않는다.
- **검토한 대안:** (a) 샘플처럼 핵심 화면 기준 없이 작성자가 고른다 / (b) 모든 화면 × 아홉 상태를 한 행씩 쓴다 / (c) 인벤토리에 핵심 화면 열(핵심 / 핵심 아님)을 두고 기준을 가이드에 쓰며, 비정상 상태 표는 핵심 화면만 다룬다
- **결정:** (c). 기준은 가이드 3.1에 있다. 핵심 구간의 플로우에 나온 화면, 데이터를 보여 주거나 입력받아 저장하는 화면, 접근 규칙이나 사용자 상태 제한이 걸린 행위를 제공하는 화면 중 하나라도 해당하면 `핵심`이고, 갈리면 `핵심`이다. 핵심 아님 화면의 상태는 이 표에 쓰지 않는다.
- **이유:** (a)는 어느 화면의 상태를 안 봤는지 알 수 없다. (b)는 가장 철저하지만 화면 수 × 9행이 되어 산출물이 매우 길고 `제외`와 `미정` 행이 대부분일 수 있다(DL-12-012 참조). (c)는 샘플의 범위를 지키면서 범위를 칸 값으로 드러낸다. 핵심 아님 화면에서 비정상 상태가 빠지는 위험은 갈리면 핵심으로 보는 보수적 기준과 누락 점검(공통 처리의 후보화)으로 줄인다.
- **영향:** 핵심 아님 화면의 상태 누락은 이 단계에서 드러나지 않는다. 사용자가 모든 화면을 요구하면 (b)로 바꾸고 `핵심 화면` 열과 완료 체크를 뺀다. 이 열은 뒤 단계가 쓰지 않아 `최종 소비자 없음`으로 닫았다(IF-17-011).
- **상태:** 검토 대기

### DL-17-006 · 판정은 CRUD 매트릭스 단계와 같은 어휘(제공, 후보, 제외)를 쓴다
- **날짜:** 2026-10-08
- **대상:** `templates/17_화면_UI상태_template.md` 1·2절 (필드 `판정`), `guides/17_화면_UI상태_guide.md` 3.1, 3.2
- **결정 주체:** 유지보수자 판단
- **배경:** 샘플은 어느 화면과 상태가 앞 단계 산출물에서 나왔고 어느 것이 이 단계에서 새로 드러났는지 칸 값으로 알 수 없다(SA-18, OM-02). 12번 세트가 같은 문제를 `제공`, `후보`, `제외`로 풀었다(DL-12-004). 같은 값을 두 단계가 서로 다른 어휘로 쓰지 않는다는 앞 단계 시험의 교훈이 있다.
- **검토한 대안:** (a) 이 단계만의 어휘(입력에 있음 / 새로 드러남 / 성립하지 않음)를 만든다 / (b) 12번과 같은 어휘를 쓴다 / (c) 판정 열 없이 후보 표만 둔다
- **결정:** (b). 인벤토리는 `제공` / `후보`, 비정상 상태 표는 `제공` / `후보` / `제외`다. 뜻은 12번과 같다(앞 단계 산출물에서 찾았다 / 찾지 못했지만 있어야 한다 / 성립하지 않는다). 인벤토리에는 `제외`를 두지 않는다. 이번 범위에서 제외한 기능의 전용 화면은 화면으로 올리지 않는다고 가이드 1절에 썼다.
- **이유:** 뒤 단계(역추적 검증)가 여러 단계의 판정을 같은 낱말로 읽는다. (c)는 목적(빠진 것을 드러낸다)을 칸에서 확인할 수 없게 한다.
- **영향:** `제공`은 앞 단계 산출물의 항목을 근거로 가리켜야 해서 작성 부담이 있다. 인벤토리에서 제외한 화면은 근거 없이 사라진다. 범위·제약의 제외 목록을 인벤토리에서 추적하고 싶으면 `제외`를 더해야 하며 사용자가 정한다.
- **상태:** 검토 대기

### DL-17-007 · 인벤토리에 플랫폼, 사용 액터, 관련 행위 열을 두고 앱·관리자 절 구분과 집계를 뺀다
- **날짜:** 2026-10-08
