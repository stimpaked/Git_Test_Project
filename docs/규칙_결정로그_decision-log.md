# 결정 로그 — 규칙 결정 로그

> `docs/규칙_결정로그.md`의 결정 이력이다. 항목은 추가만 하고 과거 항목은 고치지 않는다.
> 이 문서는 `docs/규칙_결정로그.md` v1.0 초안의 형식(DR-05)을 처음으로 적용한다.

---

### DL-DR-001 · 항목 칸에 `날짜`와 `결정 주체`를 둔다
- **날짜:** 2026-10-08
- **대상:** `docs/규칙_결정로그.md` DR-05
- **결정 주체:** 사용자 승인
- **배경:** 임시 로그의 항목에는 날짜가 소제목에만 있었고, 누가 정했는지(사용자가 정했는지, 제안이 승인된 것인지, 유지보수자가 정한 것인지)가 항목에 드러나지 않았다. 규칙 문서를 만들면서 사용자 확인 없이 정한 내용이 늘어나, 어떤 결정이 확인되었는지 구분할 필요가 생겼다.
- **검토한 대안:** (a) 칸을 더하지 않고 `결정` 문장에 주체를 서술한다 / (b) `결정 주체` 칸을 둔다
- **결정:** (b). `결정 주체`는 `사용자 결정` / `사용자 승인` / `유지보수자 판단` 세 값이고, `유지보수자 판단`은 상태를 `검토 대기`로 둔다. `날짜` 칸도 항목마다 둔다.
- **이유:** 칸으로 두면 검사 도구가 확인하고 `검토 대기` 항목을 한 번에 모아 볼 수 있다. 서술에 섞으면 놓치기 쉽다.
- **영향:** 기존 임시 형식 항목에는 이 두 칸이 없으므로 보완해야 한다(DR-09, 수정목록 C16).
- **상태:** 유효

### DL-DR-002 · 상태 값에 `검토 대기`를 더한다
- **날짜:** 2026-10-08
- **대상:** `docs/규칙_결정로그.md` DR-05
- **결정 주체:** 사용자 승인
- **배경:** 기존 임시 로그의 상태는 `유효` 하나로 쓰였지만, 실제로는 사용자 확인을 기다리는 항목(예: 규칙_공통의 새 요건)이 있었다.
- **검토한 대안:** 해당 없음 — 선택지를 비교한 결정이 아니고 기존 상태 값의 부족을 메운 것이다.
- **결정:** 상태 값을 `유효` / `대체됨(→ ID)` / `보류` / `검토 대기` 네 가지로 한다. 사용자가 확인하면 `검토 대기`를 `유효`로 바꾸고 결정 주체를 `사용자 승인`으로 갱신한다(이 변경은 상태 변경에 속하므로 추가만 한다는 원칙(DR-07)을 위반하지 않는다, DR-08).
- **이유:** 확인되지 않은 결정을 확정된 것처럼 두지 않는다(CM-01).
- **영향:** 해당 없음 — 상태 값 정의의 추가이고 다른 문서를 바꾸지 않는다.
- **상태:** 유효

### DL-DR-003 · 문서의 변경 이력 표와 결정 로그를 연결한다
- **날짜:** 2026-10-08
- **대상:** `docs/규칙_결정로그.md` DR-11
- **결정 주체:** 사용자 승인
- **배경:** 정의서 10절에 "템플릿·가이드를 바꿀 때 대응하는 결정 로그 항목이 없으면 변경 검사가 실패한다(버전 번호와 로그 항목의 대응)"고 정해 두었으나, 도구가 확인할 수 있는 연결 지점이 없었다.
- **검토한 대안:** (a) 문서 머리말의 버전 줄에 결정 ID를 적는다 / (b) 문서에 변경 이력 표(버전·날짜·요약·결정 ID)를 둔다 / (c) 연결을 두지 않고 사람이 확인한다
- **결정:** (b). 버전을 올리는 문서(템플릿, 가이드, 규칙 문서, 정의서, 단계 정의)가 변경 이력 표를 갖고, 표의 결정 ID가 로그에 존재하는지 검사한다(DR-K05). 기록 대상이 아닌 변경은 `해당 없음` + 사유를 쓴다.
- **이유:** 표는 검사 도구가 읽기 쉽고, 문서를 읽는 사람도 버전별 변경 이유로 바로 이동할 수 있다.
- **영향:** 이미 만든 정의서, 단계 정의, 규칙_공통, 규칙_결정로그에 변경 이력 표를 추가해야 한다(수정목록 C17).
- **상태:** 유효

### DL-DR-004 · 결정 로그 ID의 코드 체계와 옮김 규칙을 정한다
- **날짜:** 2026-10-08
- **대상:** `docs/규칙_결정로그.md` DR-06, DR-10
- **결정 주체:** 사용자 승인
- **배경:** 로그 항목 ID가 임시 로그의 `DL-SYS-nnn`으로 시작했고, 규칙_공통에서 `DL-CM-nnn`이 새로 생겼다. 다른 문서의 로그에 쓸 코드를 정하지 않았다.
- **결정:** 항목 ID는 `DL-<코드>-nnn`이고 코드는 로그의 대상 문서를 가리킨다. 정의서 `SD`, 단계 정의 `ST`, 규칙 문서는 규칙 ID의 문서 코드(CM 등), 단계 세트는 단계 번호 두 자리, 임시 로그는 `SYS`로 한다. ID는 옮겨도 바꾸지 않고, 옮긴 원본에는 본문을 그대로 두고 `이동됨 → 파일명`을 덧붙인다.
- **이유:** ID만으로 어느 문서의 결정인지 알 수 있고, 이동 후에도 다른 문서의 참조가 깨지지 않는다.
- **영향:** 정의서와 단계 정의의 로그를 새로 만들 때 이 코드를 쓴다(수정목록 C10).
- **상태:** 유효

### DL-DR-005 · 규칙_결정로그 v1.0 초안을 작성한다
- **날짜:** 2026-10-08
- **대상:** `docs/규칙_결정로그.md` (작업 순서 2단계, 두 번째 규칙 문서)
- **결정 주체:** 사용자 승인 (작성 순서와 범위는 2단계 계획에서 승인됨). 세부 규칙은 DL-DR-001~004 각각의 결정 주체를 따른다.
- **배경:** 규칙 문서마다 대응하는 로그를 두기로 했으므로(DL-SYS-019), 로그를 어떻게 쓰는지를 다른 규칙 문서보다 먼저 정해야 했다.
- **검토한 대안:** 해당 없음 — 작성 순서는 사용자가 승인한 2단계 계획에 따랐다.
- **결정:** 기록 대상(DR-01), 기록 시점(DR-02), 파일과 순서(DR-03), 다층 결정의 위치(DR-04, 정의서 2절의 원칙과 같음), 항목 칸(DR-05), ID(DR-06), 추가만 하는 원칙과 허용되는 변경(DR-07~10), 버전과의 연결(DR-11), 샘플 언급(DR-12), 검사(DR-K01~K07)를 정했다. 추가만 한다는 원칙, 다층 결정을 가장 가까운 공통 상위 문서의 로그에 쓴다는 원칙, 버전과 로그의 대응은 이전에 사용자가 승인한 내용을 그대로 옮긴 것이다.
- **이유:** 이후 규칙 문서들이 같은 형식으로 로그를 만들 수 있게 한다.
- **영향:** 정의서와 단계 정의의 로그를 만들고(수정목록 C10), 임시 형식 항목을 보완하고(C16), 변경 이력 표를 추가해야 한다(C17).
- **상태:** 유효
