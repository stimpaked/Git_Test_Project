# tools — 문서 생성·검증 도구

이 폴더의 파이썬 프로그램은 `feature-list-sample/`의 문서 일부를 **기능 명세 데이터에서 자동으로 만들고**, 문서 전체의 **ID 연결과 숫자가 서로 맞는지 검사**합니다. 파이썬 3만 있으면 되고 별도 설치는 없습니다(표준 라이브러리만 사용).

## 실행 방법

저장소 루트나 `feature-list-sample/` 어디에서 실행해도 같습니다.

```bash
python3 feature-list-sample/tools/verify.py   # 검사: 전부 통과하면 종료 코드 0
python3 feature-list-sample/tools/build.py    # 31~36번 문서와 00_README.md 다시 생성
```

문서나 데이터를 고친 뒤에는 `build.py` → `verify.py` 순서로 실행하세요.

## 어떤 문서를 누가 만드나

| 문서 | 만드는 주체 | 고치는 방법 |
|---|---|---|
| 01~30번 | 사람이 직접 작성 | 문서를 직접 수정 |
| 31, 32, 33, 34, 36번, 00_README.md | `build.py`가 자동 생성 | **문서가 아니라 데이터·도구를 수정**하고 `build.py` 재실행 (문서를 직접 고쳐도 다음 생성 때 덮어씌워짐) |
| 35번 | `build.py`가 생성(본문은 `gen35.py` 안의 표 데이터) | `gen35.py`의 `WT`, `FIND`, `ROLES`를 수정 |

## 파일 설명

| 파일 | 역할 |
|---|---|
| `feature_spec.txt` | **기능 명세 데이터**(기능 146개의 이름·설명·액터·화면·근거·의존성·우선순위·공수). 아래 "데이터 형식" 참고 |
| `lib.py` | 경로 설정, 1~30번 문서에서 후보(Q-, CF-)를 읽는 함수, 명세 읽는 함수 |
| `gen_data.py` | 명세를 읽어 36번의 조정(우선순위 상향, R1 이동, 공수·용량 가정)을 적용한 최종 데이터 구성 |
| `gen_docs.py` | 31·32·33·34·36번 문서 생성 |
| `gen35.py` | 35번 문서 생성(워크스루·리뷰·발견 사항 표 포함) |
| `gen_readme.py` | 00_README.md 생성(각 문서 머리말의 입력·산출물·쓰이는 곳 표를 모아 만듦) |
| `build.py` | 위 생성 프로그램을 순서대로 실행 |
| `verify.py` | 검사 43개 실행 |

## `verify.py`가 확인하는 것

- 후보 355건이 모두 기능 하나로 병합되었거나 제외 사유가 있는지(미처리·중복 없음)
- 기능 사이의 `uses`·선후행 참조가 존재하고, 방향(고유→공통)이 맞고, 순환이 없는지
- 목표(UG)·비즈니스 목표(G)·저니 격자 칸·화면이 기능과 이어지는지
- 영역·엔티티·목표의 영역 배정에 누락·중복이 없는지
- 릴리스 순서·우선순위 의존성이 어긋나지 않았는지, MVP 공수가 용량 이내인지
- 문서에 적은 집계 숫자(13·22·29·30·08번 등)와 항목 수가 실제와 같은지
- 문서가 참조하는 모든 ID가 정의되어 있는지, Mermaid 블록 기본 문법

**한계:** ID와 숫자의 일관성만 확인합니다. 내용이 현실적으로 맞는지, 빠진 기능이 없는지는 판단하지 못합니다(그건 34·35번의 사람 검토 몫입니다).

## 데이터 형식 (`feature_spec.txt`)

파일은 세 구역으로 나뉩니다.

**1. 기능 표** — 첫 줄은 열 이름, 그 아래는 기능 한 줄씩. 열은 `|`로 구분합니다.

```
id | L2 | name | desc | scope | actors | stages | plat | scr | basis | uses | deps | pri | rel | eff | gate | added
```

| 열 | 값 |
|---|---|
| `id` | `F-<영역코드 3자>-<번호 3자리>` |
| `L2` | 같은 영역 안의 기능군 이름 |
| `scope` | `공통` 또는 `고유` (영역의 구분과 같아야 함) |
| `actors`, `stages`, `scr`, `basis`, `uses`, `deps` | 쉼표로 구분한 ID 목록, 없으면 `-` (`scr`의 `*`는 전 화면 공통) |
| `plat` | `A`(앱), `W`(관리자 웹), `B`(백엔드·배치) 조합 |
| `pri` | `M` Must · `S` Should · `C` Could · `L` Later |
| `rel` | `MVP` · `R1` · `Later` |
| `eff` | `S` · `M` · `L` (인일 환산은 `gen_data.py`의 `W`) |
| `gate` | `law`(법령) · `store`(스토어) · 비움 |
| `added` | `v0` · `34-r1` · `35-r1` (어느 단계에서 생긴 기능인지) |

**2. `###SOURCES`** — `기능ID: 후보ID 후보ID …` 형식으로, 그 기능에 병합된 후보(Q-, CF-)를 적습니다. 플로우의 정상 경로에서 나온 기능은 `FL-01`, 검증에서 발견된 기능은 `R34-02`, `R35-01` 같은 출처를 씁니다.

**3. `###EXCLUDED`** — `후보ID: 제외 사유`. 기능이 아닌 후보(설계 기준·프로세스·의도적 제외)를 적습니다.

## 자주 하는 작업

| 하고 싶은 일 | 방법 |
|---|---|
| 기능 추가 | 기능 표에 한 줄 추가 → `###SOURCES`에 출처 한 줄 추가 → `build.py` → `verify.py` |
| 기능의 우선순위·릴리스 변경 | `gen_data.py`의 `PRI_UP`, `CUT_TO_R1`, `KEEP_SHOULD` 수정(원본 값은 명세에 둠) |
| 개발 용량 가정 변경 | `gen_data.py`의 `W`(공수 환산), `CAP_RAW`, `BUFFER` 수정 |
| 새 후보 추가 | 1~30번 문서의 후보 표에 `| Q-xxx |` 또는 `| CF-xx-xx |` 행 추가 → 명세 `###SOURCES`에 연결 |
| 다른 서비스에 적용 | 01~30번 문서와 `feature_spec.txt`를 새 서비스 내용으로 바꾸고, `gen_data.py`·`gen_docs.py`·`gen35.py` 안의 이 서비스 전용 문장(영역 이름, 트랙, 워크스루 시나리오 등)을 교체 |
