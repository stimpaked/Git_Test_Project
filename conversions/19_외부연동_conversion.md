| OM-01 | 단계의 목적은 연동에 필요한 설정·장애 대응·재시도·모니터링 기능을 도출하는 것인데, 샘플은 연동 행에서 후보로 가는 연결이 순서 오류인 `담당 후보` 열 하나뿐이다. 연동 행에 ID가 없고 후보의 출처는 액터 ID와 `공통`이 섞여 있어 어느 연동에서 어느 후보가 나왔는지, 후보 없이 남은 연동이 있는지 따라갈 수 없다 | 목적 대비 | 반영: 19.연동정의.ID, 19.기능후보.출처 |

| OM-03 | 단계 규칙은 외부 액터마다 설정·키 관리를 정의하라고 하는데 샘플 표에는 열이 없다. 설정 기능을 도출하려면 액터마다 어떤 키·접속 설정이 필요하고 누가 바꾸는지가 있어야 한다 | 목적 대비 | 반영: 19.연동정의.설정·키 관리 |
| OM-04 | 샘플의 값에는 어디서 확인했는지가 없고 해당 없는 칸은 `—`로 비워 둔다. 연동이 입력에 근거한 것인지, 칸을 닫았는지 알 수 없다 | 목적 대비 | 반영: 19.연동정의.근거, 19.기능후보.근거, 19.공통점검 표의 근거 열(공통 규칙 CM-05, CM-18) |

| OM-06 | 서비스가 외부를 호출하는 연동뿐 아니라 외부가 서비스를 호출하거나 결과를 보내오는 연동이 있다(결과 수신, 장치 전송, 자동 호출 주체). 샘플에는 방향을 표시할 칸이 없어 `(요건) →`처럼 괄호나 화살표로 암시한다. 방향에 따라 재시도·한도의 의미(내가 다시 보내는가, 상대의 재전송을 받는가)가 달라진다 | 목적 대비 | 반영: 19.연동정의.방향 |
| OM-07 | 연동 정의의 모든 행이 기능 후보로 이어졌는지 확인할 항목이 샘플에 없다. 샘플 완료 체크는 정의가 있는지만 확인한다 | 목적 대비 | 반영: 구성: 완료 체크 |
| OM-08 | 단계 목적(설정·장애 대응·재시도·모니터링 기능 도출)에 비추면 외부 액터 전체에 걸치는 연동 기능이 샘플의 세 항목보다 많다. 점검 질문 없이 값으로만 적으면 놓친 종류를 확인할 방법이 없다 | 목적 대비 | 반영: 표:공통점검 |
| OM-09 | 후보 중에는 기능이 아닌 출시 절차(스토어 심사, 업체 계약, 약관 동의)와 범위 밖으로 미룬 연동, 모든 연동이 따를 구조 기준이 섞인다. 샘플은 문장 속 굵은 표시로만 구분한다(SA-31) | 목적 대비 | 반영: 19.기능후보.구분 |

### 도메인 대입

대입한 가상 도메인은 병원 예약 서비스, 정기 구독 결제 서비스, 스마트 온실 모니터링 서비스, 사내 휴가 신청 도구, 어린이 독서 앱 다섯 가지다.

| ID | 발견 내용 | 발견 방법 | 처리 |
|---|---|---|---|
| OM-10 | 병원 내부 진료 시스템은 예약 가능 시간을 조회하는 호출(서비스→액터)과 진료 일정 변경을 통지하는 수신(액터→서비스)이 호출 시점·정보·장애 동작이 서로 다르다. 액터 하나에 행 하나로는 둘을 한 칸에 섞어야 한다 | 도메인 대입: 병원 예약 서비스 | 반영: 표:연동정의 (연동 하나를 행 하나로 쓴다. 같은 액터가 여러 행에 나올 수 있다) |
| OM-11 | 병원 예약 서비스는 환자의 개인·건강 정보를 보험 자격 조회 기관 같은 곳에 보낸다. 무엇이 나가는지, 동의와 기록이 필요한지는 연동 하나의 칸이 아니라 외부로 나가는 정보 전체에 걸치는 문제다 | 도메인 대입: 병원 예약 서비스 | 반영: 19.공통점검.IQ-09 외부 전달 정보 관리 (법령 매핑은 규제·정책 단계의 몫이다) |

## ③ 도메인 교체 시험

작업 순서 6단계에서 템플릿과 단계 가이드를 쓴 뒤에 시험한다. 시험 전이라 도메인별 결과 줄(DT-nn)은 아직 없다.
