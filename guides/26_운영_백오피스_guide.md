## 1. 입력을 읽는 법

- **액터 목록(사람)**: 유형이 운영·지원인 액터가 이 단계의 주인공이다. 도출 질문의 운영·지원 답이 운영 조직의 구성이다. 운영 업무의 액터 칸에는 이 목록의 `A-` ID만 쓴다. 유형이 운영·지원이 아닌 액터(이용 액터, 감독·열람 액터)가 운영 업무를 맡는다고 입력이 말할 때만 그 액터를 쓰고 근거에 밝힌다.
- **저니 매트릭스, 목표 목록, 유저 플로우, 시나리오 5유형**: 구간 분류가 운영 업무인 여정 단계의 운영 액터 행동이 업무의 출발점이다. 질문과 추가 질문 가운데 "운영자가 어떻게 처리하는가"로 끝나는 것은 업무의 출처다.
- **CRUD 매트릭스, 상태 전이**: 운영 액터가 하는 처리와 운영이 계기인 전이는 필요한 조작의 재료다. 빈 칸 중 운영 화면이 답인 것은 새 도구의 후보다.
- **시간·주기, 이벤트, 외부 연동**: 자동 처리의 실패 시 동작, 운영자에게 알리는 이벤트, 연동의 모니터링 항목은 사건이 계기인 업무의 재료다.
- **소유·권한**: 권한 매트릭스의 행위 ID가 필요한 권한 칸의 값이다. 운영 액터가 하는 조작에 해당하는 행위가 없으면 ID를 만들지 않고 `미정`으로 닫는다. 승인 규칙과 권한 부여 단위는 승인·이중 확인과 운영 권한 관리의 재료다.
- **화면·UI 상태**: 화면 인벤토리의 화면이 기존 화면 칸의 값이다. 운영 액터가 쓰는 화면이 이미 있으면 업무마다 그 화면을 먼저 찾는다.
- **영역·모듈**: 배치 방침의 운영 기능 배치가 공통·고유 잠정 값의 기준이다. 소속 영역 안에 두고 태그로 표시하는 방침이면 도메인 개념이 있어야 정의되는 운영 도구를 `고유`로 둔다. 별도 영역으로 분리하는 방침이면 어느 서비스에나 있는 운영 도구를 `공통`으로 둔다. 영역을 정하는 일은 뒤 단계가 한다.
- **비기능·규제·보안·데이터 생애**: 모니터링과 복구 요구, 사람이 처리해야 하는 규제 대응, 제재와 탐지·대응 단계의 방어 기능, 정보 주체 요청과 파기 보류는 운영 업무의 출처다. 같은 기능을 이미 후보로 낸 입력이 있으면 도구 후보를 새로 만들지 않고 근거에 그 후보 ID를 쓴다.
- **수익 모델, 성장·측정(같은 그룹의 단계 산출물)**: 읽을 수 있을 때만 금전 후속 처리와 공지·발송 같은 업무의 재료로 쓴다. 읽을 수 없으면 해당 관점을 `미정`으로 닫는다.
- **범위·제약**: 후속 목록과 제외 목록의 항목은 도구 후보의 구분을 `후속 후보`로 가르는 기준이다.
- **사람이 주는 자료**: 운영 매뉴얼, 응대 절차, 근무 분담표, 문의·요청의 건수와 처리 기록이 업무와 빈도의 직접 근거다. 이런 자료가 없는 빈도와 건수는 일반적인 관행으로 채우지 않는다.
- 입력에 없는 업체 이름, 화면 이름, 운영 인력 수를 만들어 쓰지 않는다. 사람 액터 목록이 통째로 없으면 쓰기를 멈추고 사용자에게 알린다.

## 2. 작성 절차

1. 운영 점검 관점 열두 질문에 답한다. 답은 그 일을 맡는 액터의 `A-` ID와 요지다. 해당하는 일이 없으면 `해당 없음`과 사유, 입력이 말하지 않으면 `미정`이다.
2. 답이 값인 관점마다 업무를 행으로 옮긴다. 업무 ID는 `BKW-01`부터 부여한다. 한 관점에서 업무가 여럿 나올 수 있고 한 업무가 여러 관점에 걸치면 출처에 관점을 모두 쓴다.
3. 업무마다 계기, 빈도, 기존 화면, 필요한 데이터, 필요한 조작, 필요한 권한을 쓴 뒤 도구 판정을 마지막에 닫는다.
4. 도구 판정이 새 도구 필요인 업무와 후속·프로세스로 남길 일에서 도구 후보를 쓴다. ID는 `BKC-01`부터 부여한다.
5. 4절의 누락 점검을 하고 완료 체크를 확인한 뒤 검사 도구를 돌린다.

## 3. 항목별 해설

<!-- 해설: 점검관점 -->
### 3.1 운영 점검 관점

- 열두 질문은 운영 업무가 숨는 곳을 묻는다. 서비스에 없는 관점은 `해당 없음`으로 닫아 억지 업무를 만들지 않는다.
- 답에는 일을 맡는 액터의 `A-` ID와 일의 요지를 쓴다. 입력의 ID를 쓰고 이름을 지어내지 않는다.
- 질문마다 이렇게 따진다.
  - **BKQ-01 접수 큐 처리**: 사용자가 서비스 안에서 보낸 요청이 운영자에게 쌓이는 곳이 있는지 본다. 문의, 이의, 신청처럼 운영자가 받아 처리해야 끝나는 흐름이다.
  - **BKQ-02 콘텐츠·활동 조정**: 사용자가 만든 내용이나 활동에 운영자가 개입하는 경로가 있는지 본다. 개입의 종류(숨김, 삭제, 제한)와 결과 통지를 요지에 쓴다.
  - **BKQ-03 사용자·계정 지원**: 특정 사용자를 찾아 상태를 보고 바꾸는 일이 있는지 본다. 본인 확인과 대리인 확인이 업무의 일부이면 요지에 쓴다.
  - **BKQ-04 내용·설정 관리**: 코드를 고치지 않고 운영자가 바꾸는 값과 내용이 있는지 본다. 공지, 분류, 정책 값, 금지 목록, 서비스가 보여 주는 내용, 고객 단위의 설정이 그 예다.
  - **BKQ-05 운영 권한 관리**: 운영자 계정의 발급·역할 변경·회수가 사람의 일인지 본다. 권한 부여 단위를 읽고 역할 단위인지 개인 단위인지 요지에 쓴다.
  - **BKQ-06 승인·이중 확인**: 한 사람이 끝낼 수 없는 일이 있는지 본다. 소유·권한의 승인 규칙을 읽는다.
  - **BKQ-07 현황 감시**: 운영자가 지표나 처리 대기량을 보는 일이 있는지 본다. 목표의 지표와 외부 연동의 모니터링 항목을 읽는다.
  - **BKQ-08 장애·실패 대응**: 자동 처리가 실패하거나 외부가 멈췄을 때 사람이 보고 다시 실행하는 일이 있는지 본다. 시간·주기의 실패 시 동작과 연동의 장애 시 동작을 읽는다.
  - **BKQ-09 기록 점검**: 운영자의 조치와 접근을 나중에 찾아볼 일이 있는지 본다. 운영 액터가 주체인 위협과 파기 기록을 읽는다.
  - **BKQ-10 데이터 요청 처리**: 열람·정정·삭제 요청과 파기 보류를 사람이 처리하는 경로가 있는지 본다. 데이터 생애의 공통 정책에서 사람이 처리한다고 적힌 것을 옮긴다.
  - **BKQ-11 금전 후속 처리**: 돈과 관련해 사람이 확인하거나 처리하는 일이 있는지 본다. 수익 모델 단계가 돈이 오가는 지점이 없다고 판정했으면 그 판정을 사유로 `해당 없음`을 쓴다. 읽을 수 없으면 `미정`이다.
  - **BKQ-12 개방 질문**: 입력을 다시 훑어 앞 열한 질문에 잡히지 않은 운영 일을 찾는다. 없으면 어떤 문서를 다시 훑었는지를 사유로 쓴다.
- 예시(형식 시연, 값이 아님): 병원 예약 서비스라면 BKQ-01 답을 "예약 변경 요청을 받아 일정을 다시 잡는 접수 직원(A-03)"처럼 액터 ID와 일의 요지로 쓴다. 정기 구독 결제 서비스라면 BKQ-11 답을 "결제 실패 건의 재청구와 환불 확인을 하는 정산 담당(A-05)"처럼 쓴다.

### 3.2 운영 업무

- **한 줄은 업무 하나**다. 업무와 액터, 업무와 화면을 곱한 행을 만들지 않는다. 같은 일을 두 액터가 하면 액터 칸에 둘을 쓴다.
- **업무**는 "~한다"로 끝나는 한 문장이다. 도구 이름을 쓰지 않고 운영자가 하는 일을 쓴다.
- **액터**는 사람 액터 목록의 `A-` ID다. 이름은 쓰지 않는다. 업무에 제한(타인의 것만 가능 등)이 있으면 필요한 권한이나 근거에 쓴다.
- **계기**는 업무를 시작시키는 것이다. 사용자나 다른 담당이 보낸 일이 쌓여 있으면 요청 접수, 자동 처리의 실패나 알림이 계기이면 사건 발생, 정해진 날짜나 주기에 하면 정해진 주기, 운영자가 필요할 때 스스로 하면 운영자 판단이다. 둘 이상이면 가장 많이 시작시키는 것을 고르고 나머지는 근거에 쓴다.
- **빈도**는 횟수나 주기를 입력 자료의 표현으로 쓴다. 사람이 주는 자료에 건수가 없으면 숫자를 지어내지 않고 아는 부분(매일, 건마다)에 모르는 부분을 `미정`으로 이어 쓴다.
- **기존 화면**은 화면 인벤토리의 `U-` ID다. 쓸 수 있는 화면이 없으면 `해당 없음`과 "화면 인벤토리에 이 업무의 화면이 없음"을 사유로 쓰고, 이 업무의 도구 판정은 새 도구 필요로 둔다. 인벤토리를 읽을 수 없으면 `미정`이다.
- **필요한 데이터**는 운영자가 업무를 하려고 보아야 하는 것이다. 엔티티 `E-` ID와 속성 이름을 쓰고, 개인정보를 가린 채 보는지도 쓴다.
- **필요한 조작**은 운영자가 데이터에 가하는 처리다. 조회, 변경, 승인, 발송, 재실행처럼 동사로 쉼표로 구분한다. 검증 규칙(두 사람 확인 등)은 승인 규칙의 ID와 함께 쓴다.
- **필요한 권한**은 권한 매트릭스의 행위 ID다. 조작에 해당하는 행위가 매트릭스에 없으면 ID를 만들지 않고 `미정`(확인처: 소유·권한 단계의 담당 역할)으로 닫고 근거에 어느 조작인지 쓴다. 이 `미정`은 권한 매트릭스로 돌려주는 목록이 된다.
- **도구 판정**은 이렇게 고른다.
  - `새 도구 필요`: 기존 화면이 없거나 있어도 필요한 데이터나 조작을 다 하지 못한다.
  - `기존 화면으로 충분`: 기존 화면 칸의 화면이 필요한 데이터와 조작을 모두 갖는다. 근거에 그 화면의 행위를 쓴다.
  - `도구 없이 수행`: 입력 자료가 사람이 서비스 밖의 수단으로 한다고 밝힌 업무다. 그 수단과 자료의 위치를 근거에 쓴다.
  - 판단할 입력이 없으면 `새 도구 필요`를 고르지 않고 `미정`으로 닫는다.
- **출처**에는 업무를 찾아낸 `BKQ-`와 입력 산출물의 목표, 질문, 이벤트, 후보 ID를 쉼표로 쓴다.
- **근거**에는 업무와 판정을 확인한 입력 항목과 자료의 문서·위치를 쓴다.
- 예시(형식 시연, 값이 아님): 스마트 온실 모니터링 서비스라면 계기 `사건 발생`, 빈도 "경보가 울린 때마다", 필요한 조작 "경보 내역 조회, 점검 담당 지정"처럼 쓴다. 사내 휴가 신청 도구라면 도구 판정 `기존 화면으로 충분`에 근거 "내부 자료: 인사 담당 업무 분담표, 관리 메뉴 화면 U-04의 행위 PA-12"처럼 쓴다.

<!-- 해설: 도구후보 -->
### 3.3 도구 후보

- 도구 판정이 새 도구 필요인 업무에서 후보를 올린다. 처리가 같은 업무는 후보 하나로 묶고 출처에 `BKW-`를 쉼표로 쓴다. 처리 규칙이 다르면 나눈다. 두 후보가 같은 일을 해 보이면 합치는 일은 통합 단계가 하므로 이 단계는 처리가 다른 것만 나눈다.
- 후보 문장은 해법을 정해 쓰지 않고 운영자가 무엇을 볼 수 있고 무엇을 할 수 있어야 하는지 한 문장으로 쓴다. 입력 산출물에 같은 기능의 후보가 이미 있으면 새로 만들지 않고 근거에 그 ID를 쓴다.
- **구분**은 이렇게 고른다.
  - `기능 후보`: 정의가 필요한 운영 도구다. 기본값이다.
  - `후속 후보`: 범위·제약의 후속 목록의 항목과 이어진다. 근거에 그 항목을 쓴다. 후속 목록에서 찾지 못하면 `기능 후보`로 둔다.
  - `설계 기준`: 모든 운영 도구가 따를 구조나 기준이다. 개인정보를 가려 보여 주기, 조치 기록을 남기기가 그 예다.
  - `프로세스`: 코드로 만들지 않는 절차다. 본인 확인 절차나 운영 교대 방식이 그 예다. 기능 후보로 두지 않는다.
- **공통·고유(잠정)**는 서비스 종류를 바꿔도 거의 모든 서비스에 있는 운영 도구면 `공통`, 이 서비스의 업무 개념이 있어야 정의되는 도구면 `고유`다. 갈리면 `고유`를 고른다. 근거가 없으면 `미정`이다. 확정은 뒤 단계가 한다.
- **도구 형태**는 이렇게 고른다. 화면 인벤토리에 없는 화면을 새로 만들어야 하면 `새 화면`, 인벤토리의 화면에 기능을 더하면 `기존 화면에 추가`, 화면 없이 도는 알림·자동 종결·일괄 처리이면 `화면 없는 기능`이다. `새 화면` 후보는 화면 인벤토리로 돌려줄 목록이 된다.
- 새 후보가 하나도 없으면 한 줄만 쓴다. ID 칸에는 `BKC-01`을 쓰고 나머지 칸은 `해당 없음`과 같은 사유로 닫으며 근거에는 점검한 표를 쓴다.
- 예시(형식 시연, 값이 아님): 정기 구독 결제 서비스라면 "운영자가 결제 실패 건을 모아 보고 재청구를 실행하며 결과를 남기는 기능"을, 어린이 독서 앱이라면 "운영자가 보호자 확인을 마친 열람 요청을 처리하고 처리 기록을 남기는 기능"을 한 문장으로 쓴다.

## 4. 누락 점검

- 유형이 운영·지원인 액터가 모두 업무에 나오는가. 업무가 없는 운영 액터는 없는지, 있다면 사유가 근거에 있는가.
- 열두 관점 가운데 값으로 닫은 것이 모두 업무의 출처에 나오는가.
- 운영 액터가 하는 조작에 대해 권한 매트릭스의 행위가 있는가. 없는 조작이 `미정`으로 남아 목록에 있는가.
- 사건이 계기인 업무마다 운영자에게 알리는 이벤트가 이벤트 목록에 있는가.
- 업무의 기존 화면이 화면 인벤토리에 실제로 있는가. 화면이 없는 업무가 새 도구 필요로 닫혀 `새 화면` 후보를 갖는가.
- 운영자가 개인정보를 보는 업무의 필요한 데이터에 가려 보이는지가 쓰였는가.
- 운영자의 조치를 남기는 일과 두 사람이 확인하는 일이 설계 기준이나 업무로 있는가.
- 도구 판정이 새 도구 필요인 업무가 모두 후보의 출처에 나오고, 후보의 출처 ID가 모두 업무 표에 있는가.
- 입력 산출물이 이미 낸 운영 쪽 후보를 되풀이하지 않았는가.

## 5. `미정`·`해당 없음` 판단

- **업무와 액터가 입력에 없을 때**: 운영 조직의 구성이나 업무를 입력 자료가 말하지 않으면 해당 관점은 `미정`이다. 확인처는 서비스 운영 책임 역할이다. 입력에 언급이 없다는 사실만으로는 `해당 없음`이 아니다.
- **앞 단계 표가 비어 있을 때**: 권한 매트릭스, 화면 인벤토리, 이벤트 목록이 비어 있는 이유가 "없다고 확인했다"이면 기존 화면은 `해당 없음`, 필요한 권한은 `해당 없음`과 그 확인을 사유로 쓴다. 질문이 `미정`이어서 비어 있는 것이면 `해당 없음`이 아니라 `미정`(확인처: 해당 앞 단계의 담당)이다.
- **관점의 `해당 없음`**: 서비스에 그 개념이 없다고 입력이 밝힐 때만 쓰고 사유에 확인한 문서·위치를 쓴다. 신고나 문의를 받는 기능이 없다는 범위의 제외 항목이 접수 큐 처리의 사유가 되는 것이 그 예다.
- **칸의 일부만 알 때**: 아는 값을 먼저 쓰고 모르는 부분을 `미정`(확인처·담당·기한)으로 이어 쓴다. 액터는 알지만 빈도를 모르면 빈도 칸만 `미정`이다.
- **선택지 칸과 ID 칸, 날짜 칸**: 계기, 도구 판정, 구분, 도구 형태, 액터, 기존 화면, 필요한 권한도 값을 모르면 선택지나 ID를 추측하지 않고 `미정`(확인처·담당·기한)으로 닫는다.
- **운영 인력과 건수**: 사람이 주는 자료에 없으면 `미정`이다. 확인처는 운영 책임 역할이다. 합리적인 건수를 가정해 쓰지 않는다.
- **구분을 고르기 어려울 때**: `미정`을 쓰지 않는다. 후속 목록에서 찾지 못하면 `기능 후보`다.

## 6. 흔한 실수

- 이용 액터가 쓰는 기능을 운영 도구로 되풀이한다.
- 업무 칸에 도구 이름이나 화면 이름을 쓴다.
- 입력에 없는 권한 행위 ID나 화면 ID를 만들어 쓴다.
- 기존 화면이 없는데 도구 판정을 기존 화면으로 충분으로 닫는다.
- 계기 칸에 빈도(`일 단위`)를 쓰거나 빈도 칸에 계기(`장애 시`)를 쓴다.
- 업무와 액터의 교차곱으로 행을 만든다.
- 모르는 관점에 `해당 없음`을 쓴다.
- 본인 확인 절차 같은 코드로 만들지 않는 일을 `기능 후보`로 둔다.
- 서비스 개발팀이 직접 하는 일을 모두 운영 도구로 올린다.
- 샘플이나 예시의 업무를 값으로 옮긴다.
