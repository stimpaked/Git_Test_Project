## 1. 입력을 읽는 법

- **유저 플로우**: 등장 화면 표가 화면 인벤토리의 출발 목록이다. 목표 매핑에서 플로우 없이 이 단계가 맡기로 한 목표는 반드시 인벤토리에 반영한다. 플로우의 분기와 미결 질문에서 실패하거나 결과가 없는 지점을 찾아 비정상 상태의 출처로 읽는다.
- **CRUD 매트릭스**: 엔티티와 처리 조합마다 그 처리를 보여 주거나 받는 화면이 있는지 본다. 접점 칸은 이미 정해진 화면과 기능의 이름이고, 주체 칸은 사용 액터의 후보다.
- **소유·권한**: 권한 매트릭스의 행위는 화면이 제공하는 행위를 가리킬 때 쓴다. `불가`와 `조건부 허용`은 접근 권한 없음 상태의 출처이고, 사용자 상태별 제한 표는 이용 제한 상태의 출처다. 접근 규칙은 소유자에게만 보이거나 승인 전에는 막히는 동작을 정할 때 읽는다.
- **목표 목록, 저니 매트릭스, 액터 목록(사람)**: 목표 ID와 핵심 구간 표시, 접점에 나온 화면 이름, 액터 ID를 가져온다. 접점이 이미 화면 이름이면 인벤토리의 후보로 읽는다.
- **상태 전이, 액터 목록(비사람), 시나리오 5유형**: 사라지거나 만료되어 화면이 찾지 못하는 대상은 대상 없음의 출처다. 외부 시스템이 멈출 때의 영향과 시나리오 5유형의 추가 질문(예외와 복구 유형)은 오류 상태의 출처다.
- **범위·제약**: 플랫폼 후보는 플랫폼 칸의 출처다. 이번에 제외로 둔 기능의 전용 화면은 인벤토리에 올리지 않는다.
- **앞 단계의 기능 후보 표**: 관련 후보 칸에 쓸 후보 ID를 찾는 곳이다.
- 입력에 없는 화면, 플랫폼, 액터 이름을 일반적으로 그럴 것이라는 이유로 만들어 쓰지 않는다. 입력이 화면을 하나도 주지 않으면 쓰기를 멈추고 사용자에게 알린다.

## 2. 작성 절차

1. 입력에 나온 화면을 모두 모아 인벤토리에 쓴다. 판정은 `제공`이고 `U-01`부터 ID를 부여한다.
2. 4절의 질문으로 입력에 없는 화면을 찾아 판정 `후보`로 더한다.
3. 화면마다 플랫폼, 사용 액터, 관련 목표, 관련 행위, 관련 후보를 채운다.
4. 3.1의 기준으로 핵심 화면을 표시한다.
5. 핵심 화면마다 상태 아홉 가지를 모두 한 행 이상 쓴다. 입력에서 동작을 찾을 수 있으면 `제공`, 없으면 `후보`나 `제외`를 정한다.
6. 판정이 `후보`인 화면과 상태 행을 기능 단위로 묶어 후보 목록에 쓴다.
7. 4절의 누락 점검을 하고 완료 체크를 확인한 뒤 검사 도구를 돌린다.

## 3. 항목별 해설

<!-- 해설: 화면인벤토리 -->
### 3.1 화면 인벤토리

- **화면**은 사용자가 한 덩어리로 보고 따로 열리고 닫히는 것이다. 하단 시트와 대화상자도 자기 동작이 있으면 화면이다. 여러 플로우가 같은 화면을 지나면 한 행으로 쓴다. 서비스 밖에서 보내는 알림과 메시지는 화면이 아니다.
- 서비스 전체에 걸친 상태(점검, 강제 갱신, 공통 오류, 연결 끊김)는 화면 하나로 올린다. 이런 화면의 관련 목표는 `해당 없음`(모든 목표가 지나가는 서비스 공통 화면)으로 닫는다.
- 입력의 이름이 괄호나 `/`로 화면 둘을 이었으면 화면마다 행을 나누고 원래 이름을 근거에 인용한다. 같은 화면에 이름이 둘이면 하나로 쓰고 다른 이름을 근거에 남긴다.
- **플랫폼**은 범위·제약에 나온 플랫폼과 채널의 이름을 그대로 쓴다. 화면의 구성이 플랫폼마다 같으면 쉼표로 이어 쓰고, 달라지는 화면은 플랫폼마다 행을 나눈다. 달라지는 기능을 정리하는 일은 플랫폼·채널 단계의 몫이다.
- **사용 액터**는 액터 목록(사람)의 ID만 쓴다. 서비스 안의 구성요소와 비사람 액터는 쓰지 않는다. 운영 화면은 운영·지원 유형의 액터를 쓴다.
- **관련 목표**는 목표 목록의 ID이고 화면 하나에 여럿일 수 있다. **관련 행위**는 권한 매트릭스의 행위 ID이며 화면이 보여 주거나 하게 하는 행위만 쓴다. **관련 후보**는 앞 단계 기능 후보 표의 ID이고 `~`로 줄인 범위는 풀어 쓴다.
- 권한 매트릭스와 앞 단계 후보 표를 훑어 이 화면과 이어지는 항목이 없음을 확인했으면, 훑은 표를 사유로 들어 관련 행위와 관련 후보를 `해당 없음`으로 닫는다. 훑지 못했으면 `미정`이다.
- **핵심 화면**은 아래 셋 중 하나라도 해당하면 `핵심`이다. 셋 다 아니면 `핵심 아님`이고, 갈리면 `핵심`이다.
  - 목표 목록에서 핵심 구간으로 표시한 목표를 이루는 플로우에 나온 화면
  - 서비스의 데이터를 목록이나 상세로 보여 주거나 입력받아 저장하는 화면
  - 접근 규칙이나 사용자 상태 제한이 걸린 행위를 제공하는 화면
- **판정**은 이렇게 고른다.
  - `제공`: 앞 단계 산출물에서 이 화면을 찾았다. 근거는 그 항목의 ID나 필드 키로 시작한다.
  - `후보`: 찾지 못했지만 있어야 한다고 판단한다. 근거에 어느 엔티티의 처리, 목표, 액터 때문에 필요한지 쓴다. 후속 단계가 되돌려 준 누락 화면도 `후보`다.
- 근거는 `;`로 나누고 근거마다 출처 유형이나 참조로 시작한다. 잘못된 모양은 `유저 플로우 등장 화면 표; 입력에 언급 없음`, 맞는 모양은 `09 유저 플로우 등장 화면, 입력에 언급 없음`이다.
- 예시(형식 시연, 값이 아님): 사내 휴가 신청 도구라면 "신청 현황" 화면의 사용 액터는 신청자와 결재자, 관련 행위는 신청 조회와 승인이다. 병원 예약 서비스라면 "예약 확인" 화면의 플랫폼은 웹과 키오스크로 나누고 구성이 다르면 행도 나눈다.

<!-- 해설: 비정상상태 -->
### 3.2 비정상 상태

- 이 표는 핵심 화면만 다룬다. 표에 나오는 화면은 모두 핵심 화면이고, 핵심 화면마다 아래 아홉 상태가 한 행 이상 있다.

| 상태 | 뜻 |
|---|---|
| 빈 상태 | 보여 줄 데이터가 없다. 검색 결과가 없는 것도 여기에 쓴다 |
| 로딩 | 데이터를 기다리거나 처리 중이다 |
| 오류 | 불러오기, 저장, 전송이 실패했다. 입력 검증 실패, 일부만 성공한 경우, 믿을 수 없을 만큼 오래된 값도 여기에 쓴다 |
| 오프라인 | 서비스에 닿지 못한다 |
| 기기 권한 거부 | 사용자가 기기나 브라우저의 권한(위치, 알림, 사진 등)을 허용하지 않았다 |
| 접근 권한 없음 | 서비스의 접근 규칙이 이 사용자의 접근을 막았다 |
| 세션 만료 | 로그인이 풀렸거나 일정 시간 입력이 없어 진행하던 일이 끊겼다 |
| 이용 제한 | 사용자의 상태(정지, 유예 등) 때문에 일부 동작이 막혔다 |
| 대상 없음 | 열려는 대상이 삭제, 취소, 만료되어 화면이 찾지 못한다 |

- 엔티티가 가진 상태를 화면에 보여 주는 것(예: 비활성, 연결 끊김 표시)은 정상 내용이다. 이 표의 상태가 아니다.
- **판정**은 이렇게 고른다. 뜻은 CRUD 매트릭스 단계와 같다.
  - `제공`: 앞 단계 산출물에서 이 화면과 상태의 동작을 찾았다. 플로우의 예외 분기, 시나리오 5유형의 예외·복구 질문, 권한 매트릭스의 `불가`, 사용자 상태별 제한이 그 출처다.
  - `후보`: 찾지 못했지만 이 화면이 이 상태가 될 수 있다고 판단한다.
  - `제외`: 이 화면에서는 성립하지 않는다. 같은 화면과 상태의 다른 행과 섞지 않는다.
- **동작**은 기능 단위로 한 문장이다(안내, 다시 시도, 대체 경로, 작성 내용 보존 같은 처리). 화면 배치, 문구, 애니메이션은 쓰지 않는다. 같은 화면과 상태에서 원인마다 동작이 다르면(위치와 사진의 권한 거부) 행을 나눈다.
- `후보` 행의 동작은 상태의 성질에서 곧바로 따라오는 처리(오류에는 다시 시도할 길, 오프라인에는 연결 안내)만 쓰고 근거에 `가정:`과 이유를 쓴다. 그 밖의 처리는 `미정`으로 닫는다.
- `제외` 행의 동작은 `해당 없음`과 사유다. 사유는 입력의 닫힌 목록(플랫폼 목록, 액터 목록)이나 화면의 성질(입력 전용 화면은 빈 상태가 없다)을 든다.
- **근거**는 `제공`이면 입력 항목의 ID나 필드 키로 시작하고, `후보`이면 `가정:`으로 시작하며, `제외`이면 사유를 확인한 자료로 시작한다.
- 예시(형식 시연, 값이 아님): 사내 휴가 신청 도구의 신청 현황 화면에서 접근 권한 없음은 "결재 권한이 없는 사용자에게 승인 동작을 숨기고 안내한다"(제공)로, 오프라인은 웹만 쓰는 서비스라면 "연결 끊김 안내와 다시 시도"(후보)로 쓴다. 병원 예약 서비스의 예약 확인 화면에서 대상 없음은 "취소된 예약을 열면 취소 안내로 보낸다"처럼 쓴다.

<!-- 해설: 후보목록 -->
### 3.3 후보 목록

- 인벤토리의 `후보` 화면과 비정상 상태 표의 `후보` 행에서 정의가 필요한 기능을 모아 쓴다. 같은 처리를 여러 칸이 요구하면 한 행에 쓴다.
- **출처**는 화면 ID 또는 화면 ID 뒤에 상태 이름을 공백으로 이은 칸이다. 칸이 여럿이면 쉼표로 나눈다. 상태 하나가 여러 화면에 같은 처리를 요구하면 `전체 오류`처럼 쓴다.
- **기능 후보**는 정의가 필요한 기능 하나를 한 문장으로 쓴다. 화면 배치나 해법은 쓰지 않는다.
- **잠정 도메인 구분**은 서비스 종류를 바꿔도 거의 모든 서비스에 있으면 `공통`, 이 서비스의 업무에만 있으면 `고유`다. 갈리면 `고유`를 고른다. 근거가 없으면 `미정`(확인처: 도메인 공통·고유 단계의 담당)이다.
- **근거**에는 후보를 도출한 칸과 입력 자료를 쓴다. 후보가 하나도 없으면 한 줄만 쓴다. ID 칸에는 `UC-01`을 쓰고 나머지 칸은 `해당 없음`과 같은 사유로 닫으며 근거에는 점검한 두 표를 쓴다. 이때 두 표에 `후보` 판정이 없어야 한다.
- 예시(형식 시연, 값이 아님): 스마트 온실 모니터링 서비스라면 "측정값을 불러오지 못할 때 마지막 정상값과 시각을 보여 주는 기능"(공통), 사내 휴가 신청 도구라면 "결재자 부재 시 대리 결재 안내 화면"(고유)처럼 한 문장으로 쓴다.

## 4. 누락 점검

- 엔티티마다 CRUD 매트릭스의 `제공`이나 `후보` 행을 보여 주거나 받는 화면(목록, 상세, 입력, 수정)이 있는가.
- 사람 액터마다 쓰는 화면이 하나 이상 있는가. 한 번도 나오지 않는 액터는 서비스 밖 채널로만 만나는지 확인한다.
- 운영·지원 액터가 하는 일에 필요한 화면이 있는가.
- 가입에서 탈퇴까지 계정이 거치는 단계, 약관과 정책을 열람하고 동의하는 화면, 서비스 정보를 보는 화면이 있는가.
- 사용자가 낸 요청(신청, 신고, 문의)의 처리 결과를 확인하는 화면이 있는가.
- 시간 기반 기능과 자동 실행의 결과를 운영자가 확인하는 화면이 있는가.
- 점검, 강제 갱신, 공통 오류처럼 서비스 전체에 걸친 상태의 화면이 있는가.
- 권한 매트릭스에서 `불가`나 `조건부 허용`이 있는 행위를 제공하는 화면에 접근 권한 없음 행이 있는가. 사용자 상태별 제한이 있는 행위를 제공하는 화면에 이용 제한 행이 있는가.
- 핵심 화면마다 상태 아홉 가지가 모두 있고, 핵심 아님으로 둔 화면에 입력이나 저장이 숨어 있지 않은가.
- 같은 상태 처리가 여러 화면에서 되풀이되면 후보 목록의 공통 후보로 올렸는가.
- 판정이 `후보`인 화면과 상태 행이 후보 목록의 출처에 모두 있고, 후보 목록의 출처가 두 표에 모두 있는가.
- 입력 산출물에 없는 화면이나 상태가 필요해 보여도 앞 단계를 직접 고치지 않는다. 사용자에게 알리고 해당 칸은 `미정`으로 닫는다.

## 5. `미정`·`해당 없음` 판단

- **`해당 없음`**은 닫힌 목록이 그 개념을 배제할 때만 쓴다. 입력에 언급이 없다는 사실만으로는 쓰지 않는다.
  - 로그인하는 사람 액터가 액터 목록에 없는 서비스의 세션 만료, 접근 권한 없음, 이용 제한
  - 플랫폼 목록이 기기 권한을 쓰지 않는 플랫폼뿐인 서비스의 기기 권한 거부
  - 입력 전용 화면의 빈 상태, 데이터를 읽지 않는 화면의 로딩
  - 사유에 어느 입력의 어디서 확인했는지 쓴다.
- **`미정`**은 입력으로 알 수 없을 때 쓴다. 선택지 칸, ID 칸에서 값을 모를 때도 선택지 밖의 말을 만들지 않고 `미정`(확인처·담당·기한)으로 닫는다. 확인처는 그 값을 정하는 단계의 담당이고 기한은 이 문서의 완료 전이다.
  - 사용 액터를 모르면 `미정`이다. 아는 액터가 있으면 아는 ID를 먼저 쓰고 모르는 부분을 `미정`으로 이어 쓴다.
  - 플랫폼을 모르면 `미정`(확인처: 범위·제약 담당)이다.
  - 핵심 화면 여부를 가릴 입력이 없으면 `미정`이다. 핵심이 아닌 것이 분명하면 `핵심 아님`이다.
  - 판정을 모르면 `미정`이다. 앞 단계의 `미정`에 기대는 접근 권한 없음과 이용 제한 행은 판정을 함께 `미정`으로 닫는다.
- 입력이 얇아 `미정`이 많은 것은 구조의 문제가 아니라 입력 부족이다. 칸을 줄이려고 묶음 행이나 생략을 만들지 않는다.
- 유저 플로우나 CRUD 매트릭스 입력이 통째로 없으면 쓰기를 멈추고 사용자에게 알린다.

## 6. 흔한 실수

- 입력에 없는 화면 이름을 만들어 쓴다.
- 서비스 안의 구성요소나 비사람 액터를 사용 액터에 쓴다.
- 괄호나 `/`로 이은 입력의 화면 이름을 한 행에 그대로 쓴다.
- 핵심 화면에 상태를 빠뜨리거나 핵심 아님 화면의 행을 상태 표에 쓴다.
- 입력에 동작이 없는데 `제공`으로 쓴다.
- 입력에 언급이 없다는 이유만으로 `제외`와 `해당 없음`을 쓴다.
- 엔티티가 가진 상태의 표시를 비정상 상태로 쓴다.
- 동작에 화면 배치, 문구, 애니메이션을 쓴다.
- 같은 화면과 상태에서 원인이 다른데 동작을 한 행에 섞어 쓴다.
- 서비스 전체 상태를 화면으로 올리지 않고 후보 목록에만 쓴다.
- 근거에 설명만으로 된 조각을 `;`로 따로 둔다.
- 샘플이나 예시의 화면과 상태를 값으로 옮긴다.
