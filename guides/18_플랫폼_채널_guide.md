## 1. 입력을 읽는 법

- **범위·제약**: 플랫폼 후보는 플랫폼·채널 목록의 출발점이다. 제외 목록은 범위 구분 `제외`와 판정 `범위 밖`의 출처, 후속 목록은 범위 구분 `후속`과 구분 `후속 후보`의 출처다.
- **근거 수집**: 기술 제약과 규제·정책 목록에서 이미 정해진 플랫폼, 메시지 채널 사업자, 플랫폼 정책을 본다. 정책 내용의 근거(문서 이름과 확인일)는 여기서 나온다.
- **액터 목록(사람)**: 이용 액터와 알림을 받는 사람의 ID를 가져온다. 이용자와 알림 받는 사람이 다르면 둘 다 본다.
- **액터 목록(비사람)**: 외부 플랫폼, 메시지 전달 사업자, 장치는 플랫폼 후보를 찾는 곳이다. 사업자가 채널을 제공하면 채널이 목록의 행이고 이용 액터에는 그 채널로 받는 사람의 ID를 쓴다. 장치가 서비스에 신호를 보내는 주체이면 그 비사람 액터 ID를 쓴다.
- **유저 플로우**: 플로우와 등장 화면에서 플랫폼 차이가 닿는 지점(진입, 알림, 로그인, 저장, 결제, 내보내기)을 찾는다.
- **화면·UI 상태**: 화면이 어느 플랫폼에 있는지 읽는다. 이 산출물이 입력에 없으면 화면에 닿는 차이는 찾지 못한 것이므로 사용자에게 알린다.
- **앞 단계의 기능 후보 목록**(시나리오 5유형, CRUD 매트릭스, 상태 전이, 시간·주기, 소유·권한, 이벤트 등): 같은 차이가 이미 후보로 있는지 확인한다.
- 입력에 없는 플랫폼, 정책, 사업자, 화면 이름을 만들어 쓰지 않는다. 필요해 보이면 해당 칸을 `미정`으로 닫는다.

## 2. 작성 절차

1. 입력의 플랫폼 후보를 모두 플랫폼·채널 목록에 옮기고 `LP-01`부터 ID를 부여한다. 알림 채널처럼 플랫폼 후보에 없는 길도 입력에서 찾아 더한다.
2. 범위 구분을 정한다. 범위 구분이 `포함`인 플랫폼만 차이 점검의 대상이다.
3. 포함 플랫폼마다 3.2의 점검 주제 열여덟 가지를 차례로 따져 차이 점검에 한 행 이상 쓴다. `LD-01`부터 ID를 부여한다.
4. `전용 대응` 행에서 정의가 필요한 기능이나 규칙을 기능 후보에 쓴다. `LC-01`부터 ID를 부여한다.
5. 플랫폼별로 릴리스를 나눌 때 지켜야 할 조건을 릴리스 영향에 쓴다. `LR-01`부터 ID를 부여한다.
6. 4절의 누락 점검을 하고 완료 체크를 확인한 뒤 검사 도구를 돌린다.

## 3. 항목별 해설

<!-- 해설: 플랫폼목록 -->
### 3.1 플랫폼·채널 목록

- **플랫폼**은 사용자가 서비스를 만나는 곳이나 서비스가 사람에게 닿는 길이다. 같은 종류라도 이용 액터가 다르면 행을 나눈다. 입력의 이름에 ID나 괄호가 붙어 있으면 이름만 쓰고 입력의 원래 ID는 근거에 참조로 남긴다. 목록의 ID는 `LP-`로 새로 부여한다.
- **종류**는 이렇게 고른다.
  - `네이티브 앱`: 기기에 설치해 쓰는 앱이다.
  - `웹`: 브라우저로 쓴다. 이용 화면이 다른 웹은 이름을 나눠 행을 둘로 쓴다.
  - `데스크톱 앱`: 컴퓨터에 설치해 쓰는 프로그램이다.
  - `장치·단말`: 키오스크, 센서 허브처럼 서비스 전용 기기다.
  - `메시지 채널`: 문자, 이메일, 푸시, 메신저처럼 서비스가 사람에게 보내는 길이다.
  - `앱 안 알림`: 앱이나 웹을 열었을 때 그 안에서 보여 주는 알림이다. 서비스 밖으로 보내는 푸시는 `메시지 채널`이다.
  - `대화형 채널`: 챗봇, 음성처럼 말이나 글을 주고받으며 쓰는 길이다.
  - `API`: 다른 시스템이 서비스를 호출하거나 서비스가 다른 시스템을 호출하는 인터페이스를 입력이 플랫폼으로 밝힌 경우다. 입력이 밝히지 않은 연동 대상은 이 단계의 플랫폼이 아니라 외부 연동 단계의 몫이다.
- **범위 구분**: `포함`은 입력이 이번 범위에 든다고 밝힌 것, `후속`은 후속 목록에 있는 것, `제외`는 제외 목록에 있거나 입력이 다루지 않는다고 밝힌 것이다. 입력이 범위를 밝히지 않았으면 `미정`으로 닫는다.
- **이용 액터**는 그 플랫폼을 쓰거나 그 채널로 받는 액터의 ID(`A-`, `X-`)를 쉼표로 쓴다. 쓰는 사람과 받는 사람이 다르면(보호자가 받는 알림 등) 받는 사람을 쓰고 이용자는 근거에 쓴다.
- **기준 버전·정책**은 지원할 버전의 범위(운영체제, 브라우저, 펌웨어)와 차이 점검에 쓴 플랫폼 정책 문서의 이름이다. 버전 범위는 호환성 요구를 정하는 뒤 단계가 확정하므로 입력에 없으면 알고 있는 부분만 쓰고 나머지를 `미정`으로 이어 쓴다. 정책 문서의 이름은 근거 수집에서 가져온다.
- **근거**는 `;`로 나눈 조각마다 출처 유형이나 참조로 시작한다.
- 예시(형식 시연, 값이 아님): 사내 휴가 신청 도구라면 "02 범위·제약 플랫폼 후보 둘째 줄; 내부 자료: 요구사항 메모 3절, 담당 부서 명시"처럼 쓴다.
- 포함 플랫폼이 하나뿐이어도 차이 점검과 기능 후보는 쓴다. 비교할 대상이 없는 것이 아니라 그 플랫폼에서 서비스가 따로 정할 것이 있는지를 묻는다.
- 예시(형식 시연, 값이 아님): 병원 예약 서비스라면 환자용 모바일 웹(웹), 직원용 데스크톱 웹(웹), 예약 안내 문자(메시지 채널), 접수대 단말(장치·단말)을 각각 한 행으로 쓴다. 어린이 독서 앱이라면 태블릿 앱(네이티브 앱)의 이용 액터는 어린이, 알림 채널의 이용 액터는 보호자다.

### 3.2 차이 점검

- 행은 포함 플랫폼과 점검 주제의 조합마다 한 행 이상이다. 한 조합에서 서로 독립인 차이가 둘 이상이면(위치와 사진 접근처럼 기능이 다른 경우) 행을 나눈다. 조합이 하나도 빠지지 않아야 빈 곳이 드러난다.
- 점검 주제 열여덟 가지의 뜻은 이렇다. 어느 주제에도 맞지 않는 것은 마지막 주제에 쓰고 차이·제약에 무엇인지 밝힌다.

| 주제 | 뜻 |
|---|---|
| 알림 수신 동의 | 알림을 받기 위해 사용자나 플랫폼에서 받아야 하는 권한과 동의 |
| 알림 표시 방식 | 받은 알림을 보여 주는 방식(배지, 알림 분류, 메일 본문 형식) |
| 전달 한도·형식 | 메시지의 길이와 형식 제한, 발송 한도, 전달 보장 여부 |
| 기기 기능 접근 | 위치, 카메라, 사진, 마이크, 연락처, 센서 같은 기기 기능의 권한 |
| 진입 경로 | 링크나 코드로 서비스 안의 특정 지점에 바로 들어오는 길 |
| 백그라운드·연결 유지 | 화면이 보이지 않거나 절전 중에도 실시간 처리가 이어지는지 |
| 인증·세션 저장 | 인증 정보를 어디에 두고 세션을 언제 끊는지 |
| 배포·업데이트 | 새 버전을 내보내고 사용자에게 갱신을 알리거나 강제하는 방식 |
| 심사·승인 요건 | 내놓기 전에 플랫폼이나 외부 기관의 심사와 승인을 받는 조건 |
| 지원 환경 범위 | 지원하는 운영체제 버전, 브라우저, 기기의 범위와 미지원 환경의 처리 |
| 화면 크기·입력 방식 | 화면 크기, 방향, 터치·키보드·음성 같은 입력 방식 |
| 접근성 | 보조 기술과 키보드 조작, 대비, 글꼴 크기의 지원 |
| 표시 설정 | 테마, 글꼴 크기, 언어 같은 표시 설정의 따름 |
| 오프라인·연결 불안정 | 연결이 끊기거나 느릴 때의 동작과 다시 이어졌을 때의 동기화 |
| 결제·구독 정책 | 플랫폼이 강제하는 결제 방식과 구독 규칙 |
| 내보내기·인쇄·공유 | 파일 내려받기, 인쇄, 다른 곳으로 공유하는 길 |
| 기기 변경·복원 | 기기를 바꾸거나 다시 설치한 뒤 데이터와 알림 등록을 되살리는 방법 |
| 그 밖의 플랫폼 제약 | 위 주제에 들지 않는 플랫폼의 제약 |

- **판정**은 다른 플랫폼과의 비교가 아니라 이 플랫폼에서 서비스가 따로 정할 것이 있는지로 고른다.
  - `전용 대응`: 이 플랫폼 때문에 서비스가 따로 만들거나 따로 지켜야 하는 기능이나 제약이 있다. 다른 플랫폼과 같은 기능이어도 이 플랫폼의 정책이 요구하면 `전용 대응`이다.
  - `공통 대응`: 이 주제는 이 플랫폼에도 있지만 플랫폼이 기본으로 처리하거나 서비스의 공통 기능으로 충분해 따로 정할 것이 없다.
  - `성립하지 않음`: 이 주제의 개념 자체가 이 플랫폼에 없다.
  - `범위 밖`: 개념은 있지만 제외 목록 때문에 이번에 다루지 않는다. 후속 목록의 항목은 `범위 밖`이 아니라 차이를 정리하고 기능 후보의 구분을 `후속 후보`로 쓴다.
- **차이·제약**은 `전용 대응` 행에서만 값을 쓰고 한 문장으로 쓴다. 기능이면 "무엇을 해야 한다", 제약이면 "무엇이 불가능하거나 제한된다"로 쓴다. 나머지 세 판정은 `해당 없음`과 사유로 닫는다. 사유는 공통 대응이면 플랫폼이 어떻게 처리하는지, 성립하지 않음이면 그 개념이 없는 이유, 범위 밖이면 제외 목록의 항목이다. "동일"만 쓰는 것은 사유가 아니다.
- **근거**는 판정을 정한 자료다. 플랫폼 정책에서 나온 판정은 `조사: <정책 문서 이름>, 확인일 <날짜>`로 쓴다. 정책은 버전에 따라 바뀌므로 확인일이 없으면 확인한 것이 아니다. 같은 차이를 앞 단계가 이미 후보로 정의했으면 후보를 다시 만들지 않고 그 ID를 참조로 쓴다. 맞는 모양: `조사: 알림 권한 정책 문서, 확인일 2026-09-01; 12 CRUD 매트릭스 후보 목록 CF-03`.
- 입력에 언급이 없다는 사실만으로 `성립하지 않음`이나 `범위 밖`을 쓰지 않는다. 플랫폼 종류나 제외 목록이 그 개념을 배제할 때만 쓴다.
- 예시(형식 시연, 값이 아님): 사내 휴가 신청 도구의 데스크톱 웹이라면 주제 "인증·세션 저장"의 차이·제약은 "무활동이 이어지면 세션을 끊고 다시 로그인하게 한다"(전용 대응), 주제 "알림 수신 동의"는 `해당 없음`(웹 푸시를 쓰지 않고 사내 메신저로 알린다, 성립하지 않음)처럼 쓴다. 스마트 온실 모니터링 서비스의 현장 장치라면 주제 "배포·업데이트"는 "원격으로 펌웨어를 갱신하고 실패하면 이전 버전으로 되돌린다"(전용 대응)처럼 쓴다.

### 3.3 기능 후보

- 전용 대응 행에서 정의가 필요한 기능이나 규칙을 한 행에 하나씩 쓴다. 입력에 같은 후보가 이미 있으면 다시 만들지 않는다.
- **출처**는 후보가 나온 `LD-` ID를 쉼표로 쓴다. 한 후보가 여러 행에서 나오면 모두 쓴다. **적용 플랫폼**은 그 후보가 필요한 `LP-` ID를 쉼표로 쓴다. 뒤 단계가 이 칸으로 플랫폼 태그와 릴리스 분할을 정하므로 플랫폼마다 달라지는 후보는 행을 나눈다.
- **후보 문장**은 해법을 정해 쓰지 않고 무엇을 정의해야 하는지 한 문장으로 쓴다. 입력에 없는 횟수, 시간, 업체 이름은 쓰지 않는다.
- **구분**은 이렇게 고른다.
  - `기능 후보`: 정의가 필요한 기능이나 규칙이다. 기본값이다.
  - `후속 후보`: 후속 목록에 있는 항목과 이어진다. 근거에 그 항목을 쓴다. 찾지 못하면 `기능 후보`로 둔다.
  - `설계 기준`: 기능이 아니라 모든 기능이 따라야 할 구조나 조건이다. 화면이나 기능으로 만들지 않는다. 제약만 있는 전용 대응 행(지원하지 않는 방향, 저장 위치의 제한)이 여기에 든다.
  - `프로세스`: 코드로 만들지 않는 조직의 절차다. 심사 신청, 업체 계약, 약관·정책 동의가 그 예다. 기능 후보로 두지 않는다.
- **공통·고유(잠정)**는 서비스 종류를 바꿔도 거의 모든 서비스에 있는 기능이면 `공통`, 이 서비스의 업무 개념이 있어야 정의되는 기능이면 `고유`다. 갈리면 `고유`를 고른다. 확정은 뒤 단계가 한다.
- **근거**에는 후보를 도출한 점검 행과 입력 자료를 쓴다.
- 새 후보가 하나도 없으면 한 줄만 쓴다. ID 칸에는 `LC-01`을 쓰고 나머지 칸은 `해당 없음`과 같은 사유로 닫으며 근거에는 점검한 차이 점검 표를 쓴다. 이때 `전용 대응` 행이 모두 입력의 기존 후보를 가리켜야 한다.
- 예시(형식 시연, 값이 아님): 어린이 독서 앱이라면 "아동 대상 정책이 요구하는 보호자 동의 절차를 앱 안에서 제공한다"(기능 후보, 고유), 병원 예약 서비스라면 "문자 발송 전에 수신 동의 여부를 확인한다"(기능 후보, 공통)처럼 쓴다.

### 3.4 릴리스 영향

- 플랫폼별로 릴리스를 나눌 때 지켜야 하는 조건을 한 행에 하나씩 쓴다. 플랫폼 칸에는 영향을 받는 `LP-` ID를 쉼표로 쓴다.
- **영향 유형**은 이렇게 고른다.
  - `출시 순서`: 어느 플랫폼을 먼저 내놓아야 한다.
  - `기능 동등성`: 플랫폼 사이에 같은 기능을 맞출지, 어느 기능은 맞추지 않을지 정했다.
  - `동반 출시`: 한 플랫폼이 다른 플랫폼과 함께 나가야 한다.
  - `외부 심사·승인`: 내놓기 전에 외부의 심사나 승인이 필요하고 그 조건이 기능을 요구한다.
- **영향**은 지켜야 하는 조건 하나를 한 문장으로 쓴다. 심사·승인이 요구하는 기능은 차이 점검의 `심사·승인 요건` 행에서 후보가 되고 여기에는 심사가 일정에 미치는 조건을 쓴다.
- **근거**는 조건을 정한 목표나 범위 문서의 위치, 또는 정책의 확인일이다. 확인하지 못한 주장("통과할 가능성이 높다")은 값으로 쓰지 않고 `미정`으로 닫는다.
- 포함 플랫폼이 하나뿐이고 외부 심사도 없으면 한 줄만 쓴다. ID 칸에는 `LR-01`을 쓰고 나머지 칸은 `해당 없음`과 같은 사유로 닫는다. 사유에는 포함 플랫폼이 하나라는 사실과 확인한 목록의 위치를 쓴다.
- 예시(형식 시연, 값이 아님): 병원 예약 서비스라면 "직원용 데스크톱 웹은 환자용 모바일 웹과 같은 릴리스에 나간다"(동반 출시), 어린이 독서 앱이라면 "앱 스토어의 아동 대상 심사를 통과해야 첫 출시가 가능하다"(외부 심사·승인)처럼 쓴다.

## 4. 누락 점검

- 입력의 플랫폼 후보가 모두 목록에 있는가. 제외와 후속인 후보도 범위 구분과 함께 남아 있는가.
- 알림을 보내는 서비스라면 알림 채널(문자, 이메일, 푸시, 메신저)이 목록에 행으로 있는가.
- 포함 플랫폼마다 점검 주제 열여덟 가지가 모두 한 행 이상 있는가.
- 플랫폼을 쓰는 사람과 알림을 받는 사람이 다른 경우 이용 액터에 받는 사람이 있는가.
- 판정이 `전용 대응`인데 차이·제약이 `해당 없음`이거나, 다른 판정인데 차이·제약에 값이 있는 행이 없는가.
- `성립하지 않음`과 `범위 밖` 행의 사유가 입력의 목록이나 플랫폼 종류를 가리키는가.
- 정책에서 나온 판정마다 근거에 정책 문서의 이름과 확인일이 있는가.
- 플랫폼의 심사나 정책이 요구하는 기능(신고, 차단, 계정 삭제, 보호자 동의 같은 것)이 심사·승인 요건 행과 후보로 올라 있는가.
- `전용 대응` 행마다 기능 후보의 출처에 있거나 근거가 입력의 기존 후보를 가리키는가. 제약만 있는 행은 `설계 기준`으로 올렸는가.
- 기능 후보의 적용 플랫폼이 모두 목록에 있고 포함 플랫폼인가.
- 화면이나 화면 상태가 새로 필요해 보이면(권한 요청 전 안내, 갱신 안내) 직접 고치지 말고 화면 정의 쪽에서 보완할 일을 사용자에게 알렸는가.

## 5. `미정`·`해당 없음` 판단

- **`해당 없음`**은 판정이 `공통 대응`, `성립하지 않음`, `범위 밖`인 행의 차이·제약에 쓴다. 사유는 3.2의 기준을 따르고 어느 입력의 어디서 확인했는지 쓴다. 범위에 든 플랫폼 목록과 기능 목록은 닫힌 목록으로 본다. 입력에 말이 없다는 사실만으로는 `해당 없음`이 아니다.
- **`미정`**은 이 주제가 이 플랫폼에 있는지, 따로 정할 것이 있는지 입력만으로 알 수 없을 때 쓴다. 확인처는 플랫폼 정책이나 범위를 정하는 사람이나 역할, 기한은 이 문서의 완료 전이다. 값을 받아 쓰기만 하는 뒤 단계(비기능·품질 등)의 담당을 확인처로 쓰지 않는다. 그 단계에도 값을 정할 입력이 없으면 확인처가 서로를 가리키기만 한다.
  - 판정을 알 수 없으면 판정과 차이·제약을 모두 `미정`으로 닫는다.
  - 판정은 알지만 차이·제약의 일부만 모르면 아는 부분을 먼저 쓰고 모르는 부분을 `미정`(확인처·담당·기한)으로 이어 쓴다.
  - 선택지 칸(종류, 범위 구분, 판정, 구분 등)과 ID 칸에서도 값을 모르면 `미정`(확인처·담당·기한)으로 닫는다. 선택지에 없는 말을 쓰지 않는다.
- 플랫폼 정책의 내용은 입력에서 확인한 것만 값으로 쓴다. 입력에 없는 정책은 기억에 기대어 확정하지 않고 `미정`으로 닫는다. 틀려도 나중에 바로잡을 수 있는 일반적인 동작은 값을 쓰고 출처 유형을 `일반 지식(미검증)`으로 표시한다. 심사 통과 조건처럼 틀리면 이후 단계가 크게 흔들리는 사실은 `미정`으로 닫는다. 표시한 값과 `미정` 칸은 작성을 마친 뒤 사용자에게 알린다.
- 입력이 얇으면 `미정`이 많이 나온다. 그것은 입력 부족이 드러난 것이다. 칸을 줄이려고 행을 묶거나 생략하지 않는다.
- 플랫폼 후보 입력이 통째로 없으면 쓰기를 멈추고 사용자에게 알린다. 포함 플랫폼이 하나도 없으면 차이 점검과 기능 후보, 릴리스 영향에 각각 한 줄을 `해당 없음`과 같은 사유로 닫는다. 서비스가 플랫폼 없이 존재할 수 없으므로 먼저 입력을 의심한다.
- **범위 구분이 `미정`인 채널**: 포함인지 아직 모르는 채널도 차이 점검 대상에서 빼지 않는다. 그 채널의 이용 액터와 주제 행을 쓰고 판정을 `미정`(확인처·담당·기한)으로 닫는다. 포함이 정해지면 판정을 확정한다. 모바일 앱이나 웹 행에 그 채널의 차이를 대신 넣지 않는다.

## 6. 흔한 실수

- 플랫폼 이름 대신 입력의 ID나 괄호를 목록에 그대로 쓴다.
- 채널을 빼먹고 운영체제와 웹만 쓴다.
- 포함 플랫폼과 주제의 조합을 빠뜨리거나 `성립하지 않음` 행을 생략한다.
- "동일", "해당 없음", "N/A"만 쓰고 사유를 쓰지 않는다.
- 판정을 다른 플랫폼과의 비교로 고른다.
- 개념이 없는 경우(`성립하지 않음`)와 제외 목록 때문에 다루지 않는 경우(`범위 밖`)를 섞는다.
- 정책에서 나온 판정의 근거에 확인일을 쓰지 않는다.
- 입력에 없는 정책, 사업자, 한도를 기억으로 확정해 쓴다.
- 앞 단계가 이미 정의한 후보를 후보 표에 다시 만든다.
- 제약만 있는 차이를 기능 후보로 올린다. 설계 기준으로 쓴다.
- 후속 목록의 항목을 `기능 후보`로 두거나 제외 목록의 항목을 후보로 올린다.
- 기능 후보의 적용 플랫폼을 비우거나 `전체`로 쓴다. 필요한 플랫폼의 ID를 쓴다.
- 근거에 설명만으로 된 조각을 `;`로 따로 둔다.
- 샘플이나 예시의 플랫폼과 주제 값을 그대로 옮긴다.
