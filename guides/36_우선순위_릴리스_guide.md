## 1. 입력을 읽는 법

- **계층·ID·태그의 기능 트리**가 가장 중요한 입력이다. 우선순위 표의 행 하나가 기능 트리의 기능 하나이고 기능 ID는 한 글자도 바꾸지 않는다. 구분(후속 표시), 공통·고유, 기능군, 근거 ID, 근거 등급도 읽는다. 기능 트리가 없으면 쓰기를 멈추고 알린다(공통 가이드 1절). 이 단계는 기능을 더하거나 지우거나 합치거나 쪼개지 않는다.
- **의존성**의 호출 표와 선후행 표는 필수 기능이 기대는 기능을 찾고 릴리스 순서를 지키는 재료이고, 웨이브는 같은 릴리스 안의 순서를 알려 준다. 집계의 후속 의존 수와 웨이브 미정 수는 후속 기능을 앞당겨야 하는지와 순서를 확정할 수 있는지를 알려 준다.
- **역추적 검증과 워크스루 리뷰**가 기능을 더하거나 고친 뒤의 기능 트리를 읽는다. 역추적 검증의 의도적 제외 목록과 남은 갭, 워크스루 리뷰의 종료 조건 판정은 기준선을 선언해도 되는지를 가르는 입력이다. 둘이 없거나 열려 있으면 기준선의 선언일은 `미정`이다.
- **게이트의 재료**는 규제·정책의 규제 매핑(출시 게이트, 게이트 조건, 책임, 법무 확인 사항)과 설계 결정의 확정 상태, 비기능·품질의 요구(지표, 목표값, 측정 방법), 플랫폼·채널의 릴리스 영향, 범위·제약의 의존성(의존 대상, 필요 시점)과 리스크, 목표·가치의 초기 리스크, 데이터 생애의 정책(이용 종료 시, 법정 보존, 열람·내보내기), 통합·정규화 제외 목록의 프로세스 후보이다.
- **우선순위의 재료**는 목표·가치의 목표와 이해관계자 기대, 근거 수집의 사용자 조사 빈도와 비교칸, 유사 서비스 대조의 기능 성격과 제공 현황, 목표 목록의 핵심 구간, 보안·어뷰징 위협의 가능성과 영향, 운영·백오피스 업무의 빈도, 사람 액터 목록의 이해관계자 영향이다. 근거 등급이 미검증인 기능은 근거가 약하다는 신호다.
- **릴리스의 재료**는 범위·제약의 포함 목록과 후속 목록, 수익 모델 지점 점검의 판정, 플랫폼·채널의 범위 구분과 릴리스 영향, 유사 서비스 대조의 판정이다. 기능 트리의 구분이 후속인 기능은 릴리스가 후속인 것이 기본이다.
- **재검토의 재료**는 범위·제약의 포함·후속 목록의 재검토 조건, 수익 모델과 유사 서비스 대조의 재검토 조건, 목표·가치의 목표값과 평가 시점이다.
- **사람이 주는 자료**는 개발팀의 공수 추정과 단위, 개발 용량과 버퍼, 베이스라인 선언(오너, 선언일), 변경요청 절차이다. 에이전트가 추정하거나 선언하지 않고 입력에 없으면 해당 칸을 `미정`으로 닫는다.
- 입력에 없는 ID, 규제, 공수, 용량, 오너, 선언일을 만들지 않는다. 입력의 ID에 공백이나 괄호가 붙어 있으면 ID 형식에 맞는 부분만 칸에 쓰고 원래 표기는 근거 칸에 적는다.

## 2. 작성 절차

1. 기능 트리를 위에서 아래로 읽고 후속 표시와 의존성의 호출 표, 선후행 표를 훑어 둔다.
2. 게이트 표를 쓴다. 규제 매핑의 출시 필수 행에서 시작해 입력에서 게이트가 되는 조건을 모두 모은다. ID는 `GT-01`부터 부여한다.
3. 용량 표를 쓴다. 사람이 준 값만 쓰고 릴리스마다 한 행이다. ID는 `CL-01`부터 부여한다.
4. 우선순위 표를 쓴다. 기능마다 한 행이고 ID는 `PL-001`부터 기능 ID 순으로 부여한다. 기능마다 게이트, 1차 분류, 의존성 보정, 용량 컷라인의 순서로 정한다.
5. 재검토 표와 기준선 표를 쓴다. 기준선 표의 ID는 `BL-01`부터 부여한다.
6. 집계를 표에서 세어 쓰고 4절의 누락 점검과 완료 체크를 확인한 뒤 검사 도구를 돌린다.

## 3. 항목별 해설

<!-- 해설: 게이트 -->
### 3.1 게이트

- 게이트는 점수와 무관하게 출시 전에 갖춰야 하는 조건이다. 행 하나는 조건 하나이다. 같은 조건을 기능 여럿이 충족해야 하면 게이트는 한 행이고, 어느 기능이 걸렸는지는 우선순위 표의 게이트 칸이 가리킨다. 기능을 이 표에 쓰지 않는다.
- **구분**: `기능`은 앱이나 서버가 구현하는 동작이 있어야 통과하는 게이트이고 `프로세스`는 조직이 하는 일(신고, 계약, 심사 제출, 시험)이 끝나야 통과하는 게이트이다. 규제 매핑의 대응 유형이 기능이면 기능, 프로세스이면 프로세스로 옮기고 통합·정규화 제외 목록의 프로세스 후보도 프로세스 게이트 후보로 읽는다. 한 요건에 둘 다 필요하면 행을 나눈다. 시험이나 측정이 끝나야 통과하는 품질 기준은 `프로세스`로 쓴다.
- **종류**: 규제 매핑의 규제 항목이 법령이면 `법령`, 플랫폼 정책이면 `플랫폼 정책`이다. 비기능 요구에서 올린 것은 `품질 기준`이다. 법령이나 정책이 아닌 서비스 밖의 계약, 승인, 동반 출시는 `외부 선행 조건`이다. 어느 값인지 입력으로 알 수 없으면 `미정`으로 닫는다.
- **게이트가 되는 것**: 출시 게이트가 `출시 필수`인 규제 매핑 행은 게이트다. `조건부 필수`는 조건이 이번 출시에서 성립한다고 입력이 밝힐 때 게이트이고, 성립하지 않으면 게이트로 올리지 않고 조건이 생길 때를 재검토 표의 트리거로 쓴다. 성립 여부를 모르면 게이트로 올리고 통과 기준에 성립 여부를 `미정`(확인처·담당·기한)으로 이어 쓴다. `권고`는 게이트가 아니다. 비기능 요구 가운데 기능으로 올리지 않은 기준은 품질 기준 게이트다.
- **원천**은 게이트를 만든 입력 항목의 ID(규제 매핑 행, 요구, 의존성, 리스크, 릴리스 영향)를 쉼표로 쓴다. 통합·정규화의 제외 목록에서 온 게이트는 `FE-` 행 ID를 쓴다. 입력 산출물에 근거 항목이 없는 조건은 일반 지식만으로 게이트를 만들지 않고, 어느 입력을 보완해야 하는지 사용자에게 알린다.
- **항목**은 갖춰야 하거나 끝나야 하는 것을 입력의 대응 내용이나 요구에서 옮겨 한 문장으로 쓴다. 법령 이름, 조문, 기한을 입력 없이 쓰지 않는다.
- **책임**은 이름이 아니라 역할이나 부서이고 규제 매핑의 책임을 옮긴다. 입력에 없으면 `미정`(확인처: 제품 오너나 법무)이다.
- **시점**은 입력이 준 필요 시점이나 기한을 옮긴다. 기능 게이트의 시점은 출시 시점이다. 입력에 없으면 `미정`이다.
- **통과 기준**은 통과했는지 확인할 수 있는 상태(제출 완료, 계약 체결, 목표값 충족, 법무 확인 완료)를 한 문장으로 쓴다. 규제 매핑의 법무 확인 사항이 남아 있으면 그 확인이 끝난 상태를 넣고 비기능 요구의 목표값은 입력 그대로 쓴다.
- **근거**는 원천 항목을 가리키는 ID나 `NN <산출물 이름>`으로 시작하고 쉼표로 설명을 잇는다.
- 예시(형식 시연, 값이 아님): 병원 예약 서비스라면 환자 정보 동의 요건이 기능 게이트이고 의료 기관과의 연동 계약이 외부 선행 조건의 프로세스 게이트이다. 스마트 온실 모니터링 서비스라면 가용성 시험 목표값이 품질 기준 게이트이고 통과 기준에 입력의 목표값을 그대로 쓴다.

<!-- 해설: 용량 -->
### 3.2 용량

- 용량은 사람이 주는 외부 입력이다. 행은 용량을 정하는 릴리스마다 하나이고 MVP 행은 반드시 쓴다. 다음 릴리스에 둘 기능이 있으면 그 행도 쓰고, 용량을 모르면 칸을 `미정`으로 닫는다. 다음 릴리스에 둘 기능이 없으면 행을 만들지 않는다.
- **공수 단위**는 개발팀이 공수를 센 단위를 그대로 쓰고 모든 행이 같은 단위를 쓴다. 다른 단위로 환산하거나 크기 기호를 환산하는 규칙을 만들지 않는다. 단위를 모르면 `미정`(확인처: 개발팀)이다.
- **개발 용량**과 **버퍼**는 개발팀이 밝힌 숫자를 옮긴다. 인력, 기간, 집중률 같은 산정 방법이 입력에 있으면 근거에 쓰고 곱셈 결과를 새로 계산해 값으로 쓰지 않는다. 둘 중 하나라도 모르면 해당 칸을 `미정`으로 닫는다.
- **구현 용량**은 개발 용량에서 버퍼를 뺀 값이다. 둘 중 하나가 `미정`이면 구현 용량도 `미정`이다.
- **목표 시점**은 범위·제약의 기한 제약을 옮긴다. 기한이 입력에 없으면 `미정`이다.
- **컷라인 기준**은 구현 용량이 남을 때 중요 기능을 어떤 순서로 이번 릴리스에 두는지의 기준이다. 입력이 정한 순서를 옮기고 입력에 없으면 목표와의 연결이 강한 순, 같으면 공수가 작은 순을 `가정:`으로 쓰고 사용자에게 알린다. 필수 기능은 이 기준으로 자르지 않는다.
- **근거**는 범위·제약의 제약 항목 ID나 개발팀의 자료로 시작한다.
- 예시(형식 시연, 값이 아님): 어린이 독서 앱이라면 개발 용량을 `미정`(확인처: 개발팀)으로 닫고 공수 단위에 팀이 쓰는 단위 이름을 쓴다. 사내 휴가 신청 도구라면 MVP 행 하나만 쓴다.

<!-- 해설: 우선순위 -->
### 3.3 우선순위

- 행 하나는 기능 트리의 기능 하나이다. 기능을 지우거나 합치지 않고 모든 기능이 정확히 한 행 나온다. 후속 기능도 같은 규칙으로 쓴다.
- 기능마다 아래 순서로 정하고 앞이 뒤를 이긴다.
  1. **게이트**: 이 기능이 충족해야 하는 기능 게이트의 `GT-`를 쉼표로 쓴다. 규제 매핑의 기능 후보가 가리키는 규제 항목과 기능 트리의 근거 ID로 기능을 찾는다. 걸린 게이트가 없으면 `해당 없음`(사유: 걸린 게이트 없음)이다. 게이트가 걸린 기능은 점수와 용량에 상관없이 우선순위가 필수이고 릴리스가 MVP이다.
  2. **1차 분류**: 근거로 `필수`, `중요`, `선택`을 고른다. 필수는 없으면 서비스가 목표를 이루지 못하는 기능이고, 중요는 목표에 크게 기여하지만 없어도 출시할 수 있는 기능이며, 선택은 있으면 좋은 기능이다. 재료는 근거 ID가 가리키는 목표, 위협의 가능성과 영향, 사용자 조사 빈도, 유사 서비스의 제공 현황과 기능 성격(기본이 기대보다, 기대가 매력보다 앞선다), 핵심 구간, 운영 업무 빈도이다. 재료가 없으면 `미정`(확인처: 제품 오너)으로 닫고 추측으로 필수를 쓰지 않는다.
  3. **의존성 보정**: 필수 기능이 호출받는 기능이나 선행 기능으로 삼은 기능을 필수로 올린다. 올린 기능이 다시 기대는 기능도 같은 방식으로 끝까지 올린다. 올린 행의 근거는 의존성의 호출 표나 선후행 표의 행으로 시작한다.
  4. **용량 컷라인**: 필수는 MVP이다. MVP 구현 용량에서 필수의 공수 합을 뺀 만큼 중요 기능을 컷라인 기준대로 MVP에 두고, 나머지 중요 기능은 다음 릴리스에 둔다. 용량이나 공수를 몰라 컷라인을 적용할 수 없으면 중요 기능의 릴리스는 `미정`(확인처: 개발팀)으로 닫고 추측해 가르지 않는다. 선택 기능은 다음 릴리스나 후속이다. 기능 트리의 구분이 후속인 기능은 후속이 기본이다. 필수 기능이 후속 기능에 기대면 그 후속 기능을 필수와 MVP로 올리고 근거에 이유와 의존성 행을 쓴다.
- 기대는 쪽보다 기대받는 쪽의 릴리스가 같거나 앞서야 한다. 어긋나면 기대받는 쪽의 릴리스를 앞당기고 그것이 용량을 넘으면 집계에 센다. 필수만으로 구현 용량을 넘어도 필수를 낮추지 않고 사용자에게 알린다.
- **공수**는 개발팀이 준 숫자이고 용량 표의 공수 단위로 쓴다. 입력에 없으면 `미정`(확인처: 개발팀)이며 추정해 쓰지 않는다. 공수가 `미정`인 행은 공수 합에 더하지 않는다.
- **근거**는 첫 조각을 참조로 시작한다. 목표, 규제 매핑 행, 의존성 행처럼 ID가 있으면 `BG-01`처럼 ID로, 산출물 전체를 가리키면 `32 계층·ID·태그`처럼 번호와 이름으로 시작한다. 설명은 쉼표로 잇는다.
- 예시(형식 시연, 값이 아님): 병원 예약 서비스라면 근거는 `GT-02, 환자 정보 동의 게이트가 걸린 기능; 33 의존성 호출 표의 첫 행, 이 기능이 호출받는 쪽이다`처럼 쓴다. 사내 휴가 신청 도구라면 `BG-01, 신청 처리 시간 단축 목표와 연결된 기능`처럼 쓴다.

<!-- 해설: 재검토 -->
### 3.4 재검토

- 행 하나는 릴리스를 앞당기거나 미루게 하는 조건 하나이다. 조건은 범위·제약, 수익 모델, 유사 서비스 대조의 재검토 조건과 목표의 목표값에서 온 것만 쓰고 지어 쓰지 않는다.
- **트리거**는 사건이나 지표의 상태를 한 가지 쓴다. 지표 수치는 입력의 목표값을 그대로 쓰고 평가 시점이 있으면 함께 쓴다.
- **관련 목표**는 트리거가 재는 목표의 ID이다. 입력의 목표 목록에 이을 목표가 없는 조건이면 `해당 없음`(사유: 확인한 목표 목록)이고, 목표와 이어질 가능성은 있는데 입력이 이어 주지 않으면 `미정`(확인처·담당·기한)이다.
- **대상**은 조치가 걸리는 기능의 기능 ID나 입력 산출물의 후속·제외 항목 ID이다. 정할 수 없으면 `미정`이다.
- **조치**는 이렇게 고른다. 후속이나 다음 릴리스의 기능을 앞 릴리스로 옮기면 `앞당김`, MVP나 다음 릴리스의 기능을 뒤로 옮기면 `미룸`, 제외나 후속 항목을 범위에서 다시 따지면 `범위 재검토`이다. 이번 출시에서 효력이 없는 조건부 필수 규제는 조건이 생길 때를 트리거로 하고 조치는 `앞당김`이다.
- 입력에 재검토 조건이 하나도 없으면 한 줄을 쓰고 트리거를 `미정`(확인처: 제품 오너)으로 닫는다. 입력에 언급이 없다는 사실만으로 `해당 없음`을 쓰지 않는다.
- 예시(형식 시연, 값이 아님): 어린이 독서 앱이라면 학습 완료율이 목표값에 못 미치면 후속의 보호자 리포트 기능을 앞당긴다. 스마트 온실 모니터링 서비스라면 장치 수가 늘어 처리 지연이 목표값을 넘으면 후속의 일괄 설정 기능을 앞당긴다.

<!-- 해설: 기준선 -->
### 3.5 기준선

- 행 하나는 기준선 선언 하나이다. 첫 기준선은 `기능 목록 v1.0`이고 기준선 이후 변경으로 새 기준선이 생기면 행을 더한다. 과거 행은 고치지 않는다.
- **구성**은 기준선을 이루는 산출물과 버전을 `NN <산출물 이름> vX.Y`로 쉼표로 구분해 쓴다. 계층·ID·태그, 의존성, 우선순위·릴리스 세 산출물을 모두 쓰고 버전은 각 산출물 머리말의 버전 줄에 적힌 그대로 쓴다. 역추적 검증이나 워크스루 리뷰의 환류로 앞 산출물의 버전이 올랐다면 올라간 버전이다. 앞 단계가 기능을 더하거나 고친 이력은 그 단계의 결정 로그가 갖고 여기에 쓰지 않는다.
- **오너**와 **선언일**은 사람이 하는 베이스라인 선언에서 온다. 에이전트가 선언하지 않는다. 입력에 없거나, 역추적 검증의 남은 갭이나 워크스루 리뷰의 열린 종료 조건이 있어 선언할 수 없으면 `미정`(확인처: 제품 오너)으로 닫는다. 오너는 변경을 판정하는 역할 하나이고 여러 역할을 나열하지 않는다.
- **변경요청 절차**는 오너가 준 절차를 한 문장으로 옮긴다. 입력에 없으면 접수, 영향 분석, 판정, 반영의 네 단계와 판정자를 오너로 한 안을 `가정:`으로 쓴다. 영향 분석은 추적 결과로 영향받는 목표·기능·규제를 찾는 일이고 판정은 범위, 용량, 게이트를 기준으로 하며 반영은 해당 산출물과 기능 목록의 버전을 올리는 일이다.
- 변경요청 양식에 담을 최소 항목은 요청자, 변경 유형(추가·수정·삭제·릴리스 이동), 대상 기능 ID, 근거 ID, 영향 분석 결과, 공수 영향, 판정, 반영 버전이다. 양식은 이 표의 칸이 아니다.
- **근거**는 선언과 절차를 받은 자료의 문서와 위치로 시작하고, 구성의 버전은 `내부 자료: 각 산출물의 버전 줄`처럼 쓴다.
- 예시(형식 시연, 값이 아님): 병원 예약 서비스라면 구성은 `32 계층·ID·태그 v1.1, 33 의존성 v1.0, 36 우선순위·릴리스 v1.0`처럼 쓴다. 어린이 독서 앱이라면 선언 전이어서 오너와 선언일이 `미정`이다.

<!-- 해설: 집계 -->
### 3.6 집계

- 숫자는 표의 행을 세어 쓴다. 근거는 센 표를 가리키는 참조(`36 우선순위·릴리스 3번 표`처럼 `NN <산출물 이름>`)로 시작한다. 0이어도 `0`을 쓴다.
- 릴리스가 `미정`인 기능이 있으면 그 릴리스의 용량 행도 쓰고 칸을 `미정`으로 닫는다.
- 입력 기능 수는 기능 트리의 행 수이고 우선순위 행 수와 같아야 한다. 필수·중요·선택·우선순위 미정 수의 합과 MVP·다음 릴리스·후속·릴리스 미정 수의 합은 우선순위 행 수와 같고, 기능·프로세스·구분 미정 게이트 수의 합은 게이트 수와 같다.
- 공수 합은 공수가 숫자인 행만 더한다. 공수 미정 수가 0이 아니면 합은 일부만 더한 값이므로 근거에 밝힌다.
- 용량 초과 릴리스 수는 용량 표의 행마다 같은 릴리스의 공수 합과 구현 용량을 비교해 센다. 구현 용량이나 공수 합을 알 수 없으면 `미정`(확인처: 개발팀)으로 닫는다. 0이 아니면 근거에 릴리스를 쓰고 사용자에게 알린다.
- 게이트 기능 필수 아닌 수, 필수 MVP 밖 수, 필수 의존 위반 수, 릴리스 순서 위반 수, 참조 없는 기능 게이트 수는 0이 되도록 행을 고친다. 고칠 수 없으면 수와 행을 근거에 쓰고 사용자에게 알린다.
- 후속 표시 앞당김 수는 0이 아닐 수 있다. 의존성 단계가 센 후속 의존 때문에 앞당겼다면 근거에 해당 행을 쓴다.
- 필수 의존 위반 수와 릴리스 순서 위반 수는 의존성 산출물의 호출 표와 선후행 표 행을 하나씩 우선순위 표와 대조해 센다.

## 4. 누락 점검

- 기능 트리의 모든 기능이 우선순위 표에 한 행씩 있는가. 이 단계가 기능을 지우거나 합치지 않았는가.
- 규제 매핑의 출시 필수 행이 모두 게이트 표에 있는가. 통합·정규화 제외 목록의 프로세스 후보와 비기능 기준 요구, 범위·제약의 의존성 가운데 출시 전에 끝나야 하는 것이 게이트에 빠지지 않았는가.
- 기능 게이트마다 우선순위 표에 그 게이트를 충족하는 기능이 있는가. 프로세스 게이트가 기능 행의 게이트 칸에 쓰이지 않았는가.
- 필수 기능이 기대는 기능이 모두 필수인가. 기대받는 기능의 릴리스가 기대는 기능보다 늦지 않은가.
- 기능 트리의 구분이 후속인데 앞 릴리스에 둔 기능에 이유와 의존성 행이 있는가.
- 사람이 주지 않은 공수, 용량, 오너, 선언일을 값으로 쓰지 않았는가. 입력에 없는 것을 `미정`으로 닫았는가.
- 재검토 조건이 입력의 재검토 조건과 목표값에서 모두 올라왔는가. 조건부 필수 가운데 성립하지 않는 것이 트리거로 쓰였는가.
- 기준선의 구성에 세 산출물이 모두 있고 버전이 각 산출물의 버전 줄과 같은가.

## 5. `미정`·`해당 없음` 판단

- **`해당 없음`**: 그 개념이 이 프로젝트에 없다고 입력으로 확인했을 때 쓴다. 우선순위 표의 게이트 칸에서 걸린 게이트가 없는 기능, 목표와 이어지지 않는 재검토 행의 관련 목표가 그 예이다. 게이트 표에 게이트가 하나도 없으면 입력으로 확인한 뒤 한 행을 쓰고 ID를 제외한 칸을 `해당 없음`과 같은 사유(출시 필수와 조건부 필수 규제도, 외부 선행 조건도 없다)로 닫는다.
- 입력에 언급이 없다는 사실만으로는 `해당 없음`이 아니다. 기능 트리와 규제 매핑 같은 입력을 닫힌 목록으로 보고 그 목록이 개념을 배제할 때만 목록을 사유로 들어 쓴다.
- **`미정`**: 입력만으로 알 수 없을 때 쓴다. 공수, 개발 용량, 버퍼, 공수 단위, 목표 시점, 오너, 선언일, 우선순위 판단의 재료, 게이트의 책임과 시점이 그 예이다. 선택지 칸, ID 칸, 숫자 칸, 날짜 칸에서도 값을 모르면 `미정`(확인처·담당·기한)으로 닫는다. 확인처는 개발팀, 제품 오너, 법무 같은 역할이고 기한은 이 문서의 완료 전이나 출시 전이다.
- 칸의 일부만 모르면 아는 값을 쓰고 모르는 부분을 `미정`(확인처·담당·기한)으로 이어 쓴다. 게이트 ID 둘 중 하나만 알면 아는 ID에 `미정`을 잇는다.
- 입력이 얇아 `미정`이 많아지는 것은 구조의 결함이 아니다. 공수와 용량을 지어서 칸을 채우지 않고, 칸 수를 줄이려고 행을 합치거나 빼지 않는다.
- 공수가 모두 `미정`이면 공수 합은 더한 행이 없어 0이지만 공수가 0이라는 뜻이 아니므로 근거에 밝히고, 용량 초과 릴리스 수는 `미정`이다. 이때 우선순위와 릴리스는 용량 컷라인 없이 정하고 근거에 용량을 확인하지 못했다고 쓴다.

## 6. 흔한 실수

- 기능을 이 단계에서 더하거나 지우거나 합친다. 기능을 나눠 두 릴리스에 두고 싶으면 기능 트리를 고쳐야 하므로 사용자에게 알린다.
- 사람이 주지 않은 공수, 개발 용량, 오너, 선언일을 그럴듯하게 채운다. S·M·L 같은 환산을 만든다.
- 필수만으로 용량을 넘자 필수를 중요로 낮춘다.
- 게이트 표에 대상 기능을 쓰거나, 우선순위 표의 게이트 칸에 프로세스 게이트를 쓴다.
- 게이트가 걸린 기능을 필수와 MVP로 쓰지 않는다. 필수 기능이 기대는 기능을 필수로 올리지 않는다.
- 조건부 필수와 권고를 모두 게이트로 올리거나 모두 뺀다. 성립하지 않는 조건부 필수를 재검토 표에 쓰지 않는다.
- 우선순위 칸에 릴리스 값을 쓰거나 릴리스 칸에 우선순위 값을 쓴다.
- 입력에 근거 항목이 없는 조건을 일반 지식만으로 게이트로 올린다.
- 근거 칸을 설명으로 시작한다. 맞는 모양은 `내부 자료: 개발팀 공수 추정표 2행, 입력에 언급 없음`처럼 쉼표로 이어 쓰는 것이다.
- 기준선 구성에 버전을 지어 쓰거나 선언하지 않은 기준선의 오너와 선언일을 채운다.
- 샘플이나 예시의 기능과 ID를 값으로 옮긴다.
