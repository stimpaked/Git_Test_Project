## 1. 입력을 읽는 법

- **유저 플로우**: 플로우의 노드와 분기마다 "여기서 서비스가 확정한 사실이 무엇이고, 그것을 누가 알아야 하고 무엇이 남아야 하는가"를 읽는다. 미결 질문의 ID는 발생 기능을 가리키는 ID로 쓴다.
- **상태 전이**: 전이 하나가 사건 하나의 후보다. 전이를 일으키는 계기와 전이 뒤의 상태를 함께 읽는다.
- **시간·주기, 소유·권한**: 시간이 일으키는 기능(만료, 기한 도래)과 승인·위임·권한 변경의 결과도 사건의 출처다. 이 산출물이 입력에 없으면 그 출처의 사건은 찾지 못한 것이므로 사용자에게 알린다.
- **액터 목록(사람, 비사람)**: 알림을 받는 사람과 사건을 일으키는 장치나 외부 시스템을 액터 ID로 가져온다.
- **프로젝트 자료**: 범위를 정한 문서의 후속 목록은 `구분`을 정할 때, 목표를 정한 문서의 지표는 `분석` 칸을 정할 때 쓴다.
- 입력에 없는 사건, 받는 사람, 전달 수단, 업체를 만들어 쓰지 않는다. 필요해 보이면 해당 칸을 `미정`으로 닫는다.

## 2. 작성 절차

1. 유저 플로우의 플로우와 상태 전이를 처음부터 끝까지 읽으며 3.1의 기준으로 사건을 찾는다. 사건마다 이벤트 목록에 한 행을 쓰고 `VE-01`부터 ID를 부여한다.
2. 사건마다 발생 기능을 정한다. 입력의 후보에 있으면 그 ID를 쓴다.
3. 사건마다 알림·로그·분석·후속 처리 네 칸을 차례로 따져 소비 기능을 쓴다. 네 칸 중 하나 이상에 소비 기능이 있어야 한다.
4. 소비 기능이나 발생 기능이 입력 후보에 없는 새 기능이면 기능 후보 표에 한 줄씩 쓰고 `VC-01`부터 ID를 부여한다.
5. 소비 종류 전체에 걸치는 공통 후보와 설계 기준을 기능 후보 표에 더한다.
6. 두 표가 서로 맞는지 확인하고 완료 체크를 실행한 뒤 검사 도구를 돌린다.

## 3. 항목별 해설

<!-- 해설: 이벤트목록 -->
### 3.1 이벤트 목록

- **사건**은 서비스가 처리해서 확정한 사실이다. 사용자가 버튼을 눌렀다는 조작이 아니라 그 결과로 서비스 안에서 일어난 일(저장되었다, 승인되었다, 기한에 도달했다)을 쓴다.
- **사건을 찾는 곳**은 다섯 가지다.
  - 플로우에서 성공이나 실패로 끝나는 노드
  - 상태 전이
  - 시간 기반 기능이 일으키는 기한 도래, 만료, 임박
  - 승인, 위임, 권한 변경의 결과
  - 장치나 외부 시스템이 보내 와서 서비스가 받은 것
- **한 행은 사건 하나**다. 문장에 `/`나 `·`로 두 사건을 이으면 나눈다. 같은 사건을 포괄하는 행과 구체적인 행으로 두 번 쓰지 않는다. 상태 변경처럼 하나의 사건이 여러 값으로 나뉘면 소비 기능이 모두 같을 때만 한 행으로 쓰고, 소비 기능이 하나라도 다르면 나눈다.
- **이벤트**는 과거형으로 쓴다. 시간이 일으키는 사건은 "기한이 지났다"처럼 시점에 도달한 사실로 쓰고 "다가온다"처럼 현재형으로 쓰지 않는다. 일어나지 않은 것을 감지하는 사건(값이 들어오지 않았다)은 그것을 감시하는 시간 기반 기능이 일으키는 것으로 쓴다.
- **발생 기능**은 사건을 일으키는 기능이다. 입력 산출물이 붙인 ID와 이름을 쓴다. 장치나 외부 시스템이 보낸 사건은 그것을 받아 처리하는 기능이 발생 기능이고, 보낸 주체는 액터이므로 근거나 이벤트 문장에 액터 ID로 밝힌다. 입력의 후보에 그 기능이 없으면 기능 이름을 쓰고 기능 후보 표에 올린다.
- 소비 기능의 네 칸은 이렇게 구분한다.
  - **알림**: 사람에게 알리는 기능이다. 받는 사람을 액터 ID로 쓴다. 사건을 일으킨 사람과 알림을 받는 사람이 다를 수 있으므로 받는 사람을 쓴다. 전달 수단은 입력에 있을 때만 쓴다.
  - **로그**: 기록으로 남기는 기능이다. 남기는 기록의 이름을 쓴다. 보존 기간과 파기는 이 단계가 정하지 않는다.
  - **분석**: 측정하거나 집계하는 기능이다. 무엇을 측정하는지를 쓰고 측정 이벤트의 이름은 짓지 않는다. 이름과 속성은 성장·측정 단계가 정한다.
  - **후속 처리**: 알림·로그·분석에 들지 않는 모든 소비다. 상태 갱신, 타이머 등록, 다른 기능 호출, 외부 시스템에 전달이 해당한다. 외부 시스템에 전달하면 그 비사람 액터 ID를 같이 쓴다. 후속 처리가 다른 사건을 일으키면 그 사건을 별도 행으로 쓴다.
- 한 칸에 소비 기능이 여럿이면 쉼표로 구분한다. 소비 기능마다 입력 후보에 같은 기능이 있으면 그 ID를 같이 쓰고, 없으면 새 기능이므로 기능 후보 표에 행을 만든다.
- 네 칸을 모두 `해당 없음`이나 `미정`으로 닫지 않는다. 소비 기능이 하나도 없는 사건은 이벤트로 만들지 않는다.
- **근거**에는 사건을 찾은 플로우의 노드, 상태 전이 등 입력 산출물의 위치를 쓴다.
- 예시(형식 시연, 값이 아님): 사내 휴가 신청 도구라면 이벤트 "휴가 신청이 승인되었다", 알림 "신청자에게 승인 결과를 알리는 기능", 로그 "승인 이력 기록", 후속 처리 "잔여 일수 갱신"처럼 쓴다. 병원 예약 서비스라면 "예약이 확정되었다", 알림 "환자와 병원 직원에게 확정을 알리는 기능", 후속 처리 "전날 알림 예약"처럼 쓴다.

### 3.2 기능 후보

- 이벤트 목록의 소비 기능과 발생 기능 중 입력 산출물의 후보에 없는 새 기능만 올린다. 입력에 이미 있는 후보는 다시 만들지 않고 이벤트 목록 칸에 ID로 쓴다.
- 한 줄은 기능 하나다. 한 문장에 기능이 둘이면 나눈다. 해법을 정해 쓰지 않고 무엇을 정의해야 하는지 쓴다. 입력에 없는 횟수, 시간, 업체 이름은 쓰지 않는다.
- **출처**에는 후보가 나온 이벤트의 ID를 쓴다. 알림 문구 관리, 측정 이벤트 표준, 중복 발송 방지처럼 특정 사건이 아니라 소비 종류 전체에 걸치면 `전체`를 쓴다.
- **구분**은 이렇게 고른다.
  - `기능 후보`: 정의가 필요한 기능이나 규칙이다. 기본값이다.
  - `후속 후보`: 범위를 정한 문서의 후속 목록에 있는 항목과 이어진다. 근거에 그 항목을 쓴다. 후속 목록에서 찾지 못하면 후속으로 두지 않고 `기능 후보`로 둔다.
  - `설계 기준`: 기능이 아니라 모든 기능이 따라야 할 구조나 기준이다. 사건의 발행과 소비를 어떤 구조로 처리할지가 그 예다. 화면이나 기능으로 만들지 않는다.
- **공통·고유(잠정)**는 서비스 종류를 바꿔도 거의 모든 서비스에 있는 기능이면 `공통`, 이 서비스의 업무 개념이 있어야 정의되는 기능이면 `고유`다. 갈리면 `고유`를 고른다. 공통으로 잘못 보면 재사용을 기대해 설계가 빠지고, 고유로 잘못 보면 공통·고유를 판정하는 단계가 바로잡기 때문이다. 확정은 뒤 단계가 한다.
- **ID**는 `VC-01`부터 쓴 순서대로 부여하고 지운 번호를 다시 쓰지 않는다.
- **근거**에는 후보를 도출한 이벤트와 입력 자료의 위치를 쓴다. 후속 후보는 후속 항목을 참조로 쓴다.
- 새 기능이 하나도 없으면 한 줄만 쓴다. ID 칸에는 `VC-01`을 쓰고 나머지 칸은 `해당 없음`과 같은 사유로 닫으며 근거에는 점검한 이벤트 목록을 쓴다.
- 예시(형식 시연, 값이 아님): 어린이 독서 앱이라면 "읽기 기록 저장 실패를 보호자에게 알리는 기능", 스마트 온실 모니터링 서비스라면 "센서 값 미수신을 감지해 담당자에게 알리는 기능"처럼 기능 하나를 한 문장으로 쓴다.

## 4. 누락 점검

- 유저 플로우의 모든 플로우를 훑어 성공과 실패로 끝나는 노드마다 사건이 있는지 물었는가.
- 상태 전이마다 사건이 있는지 확인했는가. 전이를 사건으로 올리지 않은 이유를 말할 수 있는가.
- 시간이 일으키는 기능(만료, 기한, 주기 점검)마다 사건이 있는가.
- 승인, 위임, 권한 변경, 운영자의 중요 행위가 사건으로 올라 있는가.
- 소비 기능이 실패하는 상황(전달 실패, 무효한 수신처)도 사건으로 올리고 그 소비 기능을 정했는가.
- 알림을 받는 사람이 사건을 일으킨 사람과 다른 경우 받는 사람을 썼는가.
- 사건을 받는 쪽의 기능이 입력 후보에도 기능 후보 표에도 없는 이벤트가 없는가.
- 소비 종류 전체에 걸치는 공통 후보(문구 관리, 측정 표준, 중복 발송 방지, 기록 정책)를 확인했는가.
- 이벤트 목록의 소비 기능마다 입력 후보 ID가 있거나 기능 후보 표에 행이 있는가. 기능 후보의 출처 `VE-` ID가 이벤트 목록에 모두 있는가.
- 한 행에 사건이 둘 이상 묶이지 않았는가.

## 5. `미정`·`해당 없음` 판단

- **소비 기능 칸의 `해당 없음`**: 그 사건에는 그 종류의 소비가 필요 없다고 입력으로 확인했을 때 쓴다. 범위가 그 종류의 기능(알림 채널, 측정 도구)을 밖에 둔다고 밝히거나, 사건의 주체가 결과를 화면에서 바로 확인해 알릴 상대가 없다고 플로우에서 확인되는 것이 근거다. 사유에 어느 입력의 어디서 확인했는지 쓴다. 입력에 말이 없다는 사실만으로는 `해당 없음`이 아니다.
- **소비 기능 칸의 `미정`**: 그 종류의 소비가 필요할 수 있는데 입력만으로 정할 수 없을 때 쓴다. 확인처는 소비 기능을 정하는 사람이나 역할, 기한은 이 문서의 완료 전으로 쓴다. 칸의 일부만 모르면(받는 사람은 알지만 전달 수단은 모를 때) 아는 값을 먼저 쓰고 모르는 부분을 `미정`(확인처·담당·기한)으로 이어 쓴다.
- 한 사건의 소비 기능이 네 칸 모두 `해당 없음`이나 `미정`이면 그 사건은 이벤트가 아니다. 행을 지우거나, 입력이 부족한 것이면 사용자에게 어느 입력이 필요한지 알린다.
- 이벤트가 하나도 없는 서비스는 드물다. 입력의 플로우와 상태 전이를 모두 확인해도 사건이 없을 때만 이벤트 목록과 기능 후보 표에 각각 한 줄을 `해당 없음`과 사유로 닫는다.
- 구분을 고르기 어렵다고 `미정`을 쓰지 않는다. 후속 목록에서 찾지 못하면 `기능 후보`다. 공통·고유(잠정)만 판단할 근거가 없으면 `미정`으로 닫는다.
- 유저 플로우나 상태 전이 입력이 통째로 없으면 쓰기를 멈추고 사용자에게 알린다.

## 6. 흔한 실수

- 화면 조작이나 버튼 누름을 사건으로 쓴다.
- 한 행에 사건 둘을 `/`로 이어 쓴다.
- 이벤트를 현재형이나 미래형으로 쓴다.
- 알림 칸에 사건을 일으킨 사람을 쓰고 받는 사람을 쓰지 않는다.
- 분석 칸에 측정 이벤트의 이름을 짓는다.
- 소비 기능이 없는 사건을 올리고 네 칸을 모두 `해당 없음`으로 닫는다.
- 입력에 이미 있는 후보를 기능 후보 표에 다시 만든다.
- 이벤트 목록에 쓴 새 소비 기능을 기능 후보 표에 올리지 않는다.
- 설계 기준이나 후속 항목을 `기능 후보`로 둔다.
- 입력에 없는 전달 수단, 업체, 한도를 쓴다.
- 샘플이나 예시의 이벤트를 값으로 옮긴다.
