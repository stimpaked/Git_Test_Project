## 1. 입력을 읽는 법

- **액터 목록(비사람)**: 유형이 `외부 시스템`, `장치`, `자동 호출 주체`인 액터가 연동 정의의 대상이다. `시간 트리거` 액터는 시간이 계기인 기능을 다루는 단계의 몫이므로 대상이 아니다. 방향과 주고받는 정보는 연동 정의의 출발값이고, 선정 상태와 장애 시 영향과 관련 제약·규제는 칸을 닫는 근거다.
- **유저 플로우**: 목표 매핑에서 다룬 곳이 이 단계인 목표를 가져온다. 비사람 액터가 등장하는 플로우의 노드는 호출 시점의 후보이고, 외부 호출이 실패하는 갈래의 미결 질문은 장애 시 동작의 후보다.
- **시나리오 5유형**: 예외와 복구 관점의 추가 질문에서 외부가 응답하지 않거나 틀린 값을 주는 경우를 읽는다.
- **엔티티, CRUD 매트릭스**: 주 소유 액터나 주체가 비사람 액터인 엔티티와 처리(가져오기, 내보내기 등)는 연동의 후보다. 개인정보 표시가 있는 엔티티가 외부로 나가는지 본다.
- **상태 전이, 시간·주기, 이벤트**: 계기 유형이 외부 호출인 전이, 외부를 호출하는 시간 기반 기능, 후속 처리로 외부에 전달하는 이벤트를 호출 시점으로 읽는다.
- **범위·제약, 근거 수집**: 정해진 업체, 호출 한도, 비용, 플랫폼 정책 같은 기술 제약과 의존성이 있으면 칸의 근거로 인용한다.
- 입력에 없는 업체 이름, 한도, 비용, 기간, 키는 일반적으로 그럴 것이라는 이유로 만들어 쓰지 않는다.

## 2. 작성 절차

1. 비사람 액터 목록에서 연동 대상 액터(외부 시스템, 장치, 자동 호출 주체)를 모두 가져온다.
2. 연동 정의에 연동 하나를 한 줄로 쓴다. 액터, 연동 목적, 방향, 호출 시점, 주고받는 정보를 차례로 쓰고 ID는 `IG-01`부터 부여한다.
3. 같은 줄의 설정·키 관리, 장애 시 동작, 재시도·한도, 모니터링·비용을 쓴다. 다섯 측면 가운데 어느 것도 "연동한다"로 끝내지 않는다.
4. 연동 정의를 모두 쓴 뒤에 공통 점검의 열 질문에 답한다. 값이면 필요한 기능과 대상 연동 ID를 쓴다.
5. 기능 후보를 쓴다. 연동 정의의 모든 줄과 값으로 닫은 공통 점검 항목에서 후보를 올린다. ID는 `IC-01`부터 부여한다.
6. 4절의 누락 점검을 하고 완료 체크를 확인한 뒤 검사 도구를 돌린다.

## 3. 항목별 해설

<!-- 해설: 연동정의 -->
### 3.1 연동 정의

- **한 줄은 연동 하나**다. 같은 액터라도 방향이 다르거나 호출 시점·주고받는 정보·장애 때의 동작이 다르면 줄을 나눈다. 한 액터가 여러 줄에 나와도 된다. 호출 시점과 정보가 같은 호출 여럿은 한 줄에 쓴다.
- **액터**는 비사람 액터 목록의 `X-` ID 하나다. 이름은 쓰지 않는다. 입력 산출물의 ID가 `X-` 형식이 아니거나 공백이나 괄호가 있으면 형식에 맞는 부분만 쓰고 원래 이름은 근거 칸에 적는다. 서비스 안의 서버나 관리자 화면은 액터가 아니다. 목록에 없는 외부 시스템이 필요해 보여도 줄을 만들지 않고 사용자에게 알린다. 액터를 추가하는 일은 비사람 액터 목록 단계의 몫이다.
- **연동 목적**은 서비스가 이 액터와 주고받아 무엇을 하려는지 한 문장으로 쓴다. 액터 이름을 되풀이하는 "~와 연동한다"는 목적이 아니다.
- **방향**은 연동을 시작하는 쪽으로 고른다. 서비스가 호출하거나 보내면 `서비스→액터`, 외부가 호출하거나 보내오면 `액터→서비스`다. 서로 다른 시작점을 모두 가진 한 연동일 때만 `양방향`을 쓰고, 시작점이 둘이면 보통 줄을 나눈다. 요건이나 정책만 주는 외부는 `액터→서비스`다.
- **호출 시점**은 계기를 입력 산출물의 ID와 함께 쓴다. 외부가 시작하는 연동은 외부의 요청이나 전송이 계기라고 쓴다. 시간이 계기이면 시간 기반 기능의 ID를 쓰고, 그 기능의 실패 시와 재시도는 되풀이하지 않고 ID로 가리킨다.
- **주고받는 정보**는 서비스를 기준으로 `보내는 것 → 받는 것` 순서로 쓴다. 한쪽뿐이면 있는 쪽만 쓰고 나머지는 방향이 말해 준다. 입력 산출물이 개인정보로 표시한 정보가 나가면 그 사실을 같이 쓴다.
- **설정·키 관리**는 접속 설정, 키·토큰·인증서, 시험 환경과 운영 환경의 구분, 바꾸는 사람과 방법을 쓴다. 서비스가 받는 키인지(`서비스→액터`) 서비스가 발급하는 키인지(`액터→서비스`)를 구분해 쓴다. 키나 비밀 값 자체는 어디에도 쓰지 않는다.
- **장애 시 동작**은 먼저 장애가 나도 진행하는지 막는지를 쓴다. 이어서 사용자에게 보이는 동작, 대체 경로, 운영자에게 알리는 방법을 쓴다. 법이나 정책이 정한 연동은 막는 쪽일 수 있으므로 관련 제약·규제를 확인한다. 사용자에게 영향이 없다면 그 사실과 이유를 쓰고 운영자에게 알리는 방법은 그래도 쓴다. 재시도는 이 칸에 쓰지 않는다.
- **재시도·한도**는 재시도 규칙(횟수, 간격, 그만두는 조건)과 호출 한도(횟수, 용량, 속도 제한)를 쓴다. `서비스→액터`이면 서비스가 다시 보내는 규칙과 상대가 두는 한도를, `액터→서비스`이면 외부의 재전송을 받는 규칙(중복 처리)과 서비스가 외부에 허용하는 한도를 쓴다. 숫자는 입력에 있을 때만 쓴다.
- **모니터링·비용**은 성공률·지연·사용량 같은 지표와 호출에 드는 비용의 구조(건당, 정액, 무료)를 쓴다. 사내 시스템처럼 비용이 없는 상대는 비용 부분을 `해당 없음`(사유)으로 닫고 지표는 쓴다.
- **근거**에는 연동을 확인한 입력 산출물의 항목(액터 ID)과 문서·위치를 쓴다.
- 예시(형식 시연, 값이 아님): 병원 예약 서비스라면 보험 자격 조회 기관 한 줄에 목적 "예약자의 보험 자격을 확인한다", 방향 `서비스→액터`, 주고받는 정보 "예약자 식별 정보 → 자격 여부", 장애 시 동작 "예약은 막지 않고 자격 확인 대기로 접수하며 담당자에게 알린다"처럼 쓴다. 스마트 온실 모니터링 서비스라면 센서 한 줄에 방향 `액터→서비스`, 재시도·한도 "장치의 재전송을 받아 같은 값은 한 번만 처리한다"처럼 쓴다.

<!-- 해설: 공통점검 -->
### 3.2 공통 점검

- 열 질문은 연동 정의를 모두 쓴 뒤에 답한다. 답은 필요한 기능의 이름과 그 기능이 쓰이는 연동의 `IG-` ID를 쉼표로 구분해 쓴다. 연동이 하나뿐이어도 같은 기능이 필요하면 값으로 쓰고 ID는 하나다.
- 질문마다 이렇게 따진다.
  - **IQ-01 연동 감시**: 연동 정의의 모니터링·비용 칸이 여러 줄에 걸쳐 있으면 한곳에서 보는 기능이 필요한지 본다.
  - **IQ-02 키·비밀 값 관리**: 설정·키 관리 칸에 키나 인증서가 있는 연동이 있는지 본다.
  - **IQ-03 사용자 안내 통일**: 장애 시 동작 칸에 사용자에게 보이는 안내가 있는 연동이 여럿인지 본다.
  - **IQ-04 재시도·한도 공통**: 재시도하는 연동이 둘 이상이거나 재시도가 중복 처리를 만들 수 있는지 본다. 응답을 못 받은 요청이 실제로 처리되었을 수 있으면 같은 요청을 두 번 처리하지 않게 하는 규칙이 필요한지 함께 본다.
  - **IQ-05 장애 격리·전환**: 한 외부 액터가 느려질 때 서비스의 다른 일까지 느려지는지, 대체 경로로 바꾸는 기능이 필요한지 본다.
  - **IQ-06 수신 요청 검증**: 방향이 `액터→서비스`인 연동이 있는지 본다. 없으면 `해당 없음`의 근거가 된다.
  - **IQ-07 외부 변경 대응**: 외부 액터가 규격·요금·정책을 바꾸거나 서비스를 끝낼 때 알아채는 수단이 있어야 하는 연동이 있는지 본다.
  - **IQ-08 연동 시험 환경**: 실제 액터를 시험에서 쓸 수 없거나 호출에 비용이 드는 연동이 있는지 본다.
  - **IQ-09 외부 전달 정보 관리**: 주고받는 정보에 개인·민감 정보가 있는 연동이 있는지 본다. 어떤 법령이 적용되는지는 이 단계가 정하지 않는다.
  - **IQ-10 개방 질문**: 입력 문서를 다시 훑어 앞 아홉 질문에 잡히지 않은 공통 기능을 찾는다. 없으면 어떤 문서를 다시 훑었는지를 사유로 쓴다.
- 예시(형식 시연, 값이 아님): 사내 휴가 신청 도구라면 IQ-02 답을 "사내 메신저 연동의 접속 토큰 보관·교체 기능(IG-02)"처럼 기능 이름과 연동 ID로 쓴다. 정기 구독 결제 서비스라면 IQ-04 답을 "결제 재시도 때 같은 요청이 두 번 처리되지 않게 하는 기능(IG-01)"처럼 쓴다.

<!-- 해설: 기능후보 -->
### 3.3 기능 후보

- 연동 정의의 모든 줄에서 후보를 최소 하나 올린다. 연동 자체(호출 또는 수신, 결과 처리)가 첫 후보이고, 다섯 측면에서 별도의 기능이 드러나면 한 줄씩 더 올린다. 한 줄은 기능 하나이고, 해법을 정해 쓰지 않고 무엇을 정의해야 하는지 쓴다.
- 입력 산출물에 같은 기능의 후보가 이미 있으면 새로 만들지 않고 연동 정의의 칸에 그 ID를 쓴다. 입력의 후보가 사용자가 보는 기능이고 외부와 주고받는 부분이 없으면 이 단계의 후보로 올리고 근거에 그 후보의 ID를 쓴다.
- **출처**에는 후보가 나온 `IG-`나 `IQ-` ID를 쉼표로 구분해 쓴다.
- **구분**은 이렇게 고른다.
  - `기능 후보`: 정의가 필요한 연동 기능이다. 기본값이다.
  - `후속 후보`: 범위·제약의 후속 목록의 항목과 이어진다. 근거에 그 항목을 쓴다. 후속 목록에서 찾지 못하면 `기능 후보`로 둔다.
  - `설계 기준`: 모든 연동이 따라야 할 구조나 기준이다. 화면이나 기능으로 만들지 않는다.
  - `프로세스`: 코드로 만들지 않는 절차다. 심사 신청, 업체 계약, 약관·정책 동의가 그 예다. 기능 후보로 두지 않는다.
- **공통·고유(잠정)**는 서비스 종류를 바꿔도 거의 모든 서비스에 있는 연동 기능이면 `공통`, 이 서비스의 업무 개념이 있어야 정의되는 기능이면 `고유`다. 갈리면 `고유`를 고른다. 근거가 없으면 `미정`이다. 확정은 뒤 단계가 한다.
- **ID**는 `IC-01`부터 쓴 순서대로 부여하고 지운 번호를 다시 쓰지 않는다. **근거**에는 후보를 도출한 연동 정의·공통 점검의 행과 입력 자료의 위치를 쓴다.
- 새 후보가 하나도 없으면 한 줄만 쓴다. ID 칸에는 `IC-01`을 쓰고 나머지 칸은 `해당 없음`과 같은 사유로 닫으며 근거에는 점검한 표를 쓴다.
- 예시(형식 시연, 값이 아님): 어린이 독서 앱이라면 "도서 정보 제공처의 규격 변경을 알아채 담당자에게 알리는 기능"을, 사내 휴가 신청 도구라면 "인사 시스템 조회 실패 때 마지막 확인값을 보여 주는 기능"을 한 문장으로 쓴다.

## 4. 누락 점검

- 비사람 액터 목록의 외부 시스템·장치·자동 호출 주체가 모두 연동 정의에 한 줄 이상 나오는가. 시간 트리거 액터가 연동 정의에 들어 있지 않은가.
- 한 액터의 연동이 둘 이상인데 한 줄에 섞어 쓰지 않았는가. 외부가 서비스를 호출하는 연동을 빠뜨리지 않았는가.
- 모든 줄의 설정·키 관리, 장애 시 동작, 재시도·한도, 모니터링·비용이 구체적인 값, `해당 없음`, `미정` 중 하나인가.
- 장애 시 동작에 진행하는지 막는지가 있는가. 사용자 안내와 운영자 알림이 둘 다 있는가.
- 입력의 유저 플로우와 시나리오 5유형에서 외부 호출 실패를 다룬 질문이 모두 어느 줄의 장애 시 동작이나 기능 후보에 닿는가.
- 개인정보가 표시된 엔티티가 외부로 나가는데 공통 점검의 외부 전달 정보 관리가 `해당 없음`으로 닫혀 있지 않은가.
- 연동 정의의 모든 줄이 기능 후보의 출처에 나오고, 기능 후보의 출처 ID가 모두 연동 정의나 공통 점검에 있는가.
- 값으로 닫은 공통 점검 항목마다 기능 후보가 있는가.

## 5. `미정`·`해당 없음` 판단

- **연동 대상 액터가 없을 때**: 비사람 액터 목록에 외부 시스템·장치·자동 호출 주체가 하나도 없으면 연동 정의에 한 줄만 쓴다. ID 칸에는 `IG-01`을 쓰고 나머지 칸은 `해당 없음`과 같은 사유로 닫는다. 공통 점검의 모든 항목은 같은 사유로 `해당 없음`이다. 액터 목록 입력이 통째로 없으면 쓰기를 멈추고 사용자에게 알린다.
- **업체나 제품을 아직 고르지 않았을 때**: 액터의 선정 상태가 정해지지 않았으면 업체마다 다른 값(키의 종류, 한도, 비용)은 `미정`(확인처·담당·기한)으로 닫는다. 확인처는 선정을 맡은 사람이나 역할이다. 선정과 상관없이 아는 부분(연동 목적, 방향, 호출 시점)은 먼저 쓴다.
- **칸의 일부만 알 때**: 아는 값을 먼저 쓰고 모르는 부분을 `미정`(확인처·담당·기한)으로 이어 쓴다. 재시도 규칙은 알지만 한도를 모르면 규칙 뒤에 한도 부분만 `미정`으로 쓴다.
- **한도, 비용, 기간, 횟수**: 입력(계약, 기술 제약, 요구사항)에 없으면 `미정`으로 닫는다. 합리적인 값을 가정해 쓰지 않는다. 틀린 값이 가용성 요구로 퍼지면 되돌리기 어렵기 때문이다.
- **방향 같은 선택지 칸과 액터 같은 ID 칸**: 값을 모르면 선택지나 ID를 추측하지 않고 `미정`(확인처·담당·기한)으로 닫는다.
- **재시도·한도와 모니터링·비용의 `해당 없음`**: 그 연동에 재시도할 일이나 한도가 개념으로 없다고 입력이 밝힐 때만 쓴다. 상대가 사내 시스템이라 한도와 비용이 없다는 입력의 문장이 근거다. 입력에 말이 없다는 사실만으로는 `해당 없음`이 아니라 `미정`이다.
- **설정·키 관리의 `해당 없음`**: 키나 접속 설정이 필요 없다고 입력이 밝힐 때만 쓴다. 공개 자료를 받아 오기만 한다는 문장이 그 예다.
- **공통 점검의 `해당 없음`**: 질문의 기능이 필요 없다고 연동 정의로 확인될 때 쓰고 사유에 확인한 연동 정의의 줄을 쓴다. 방향이 `액터→서비스`인 연동이 하나도 없다는 사실로 수신 요청 검증을 `해당 없음`으로 닫는 것이 그 예다. 필요할 수 있는데 입력만으로 정할 수 없으면 `미정`이다.
- **구분을 고르기 어려울 때**: `미정`을 쓰지 않는다. 후속 목록에서 찾지 못하면 `기능 후보`다.
- 위의 "연동 대상 액터가 없을 때"는 외부 연동이 없다고 입력이 확인한 경우에만 `해당 없음`을 쓴다. 액터 표가 빈 이유가 도출 질문이 `미정`이라서(외부 연동이 있는지 아직 모른다)이면 `미정`(확인처: 비사람 액터 목록 담당)으로 닫고 그 질문 ID를 근거에 쓴다.

## 6. 흔한 실수

- "문자 업체와 연동한다"처럼 연동 목적을 액터 이름의 되풀이로 쓴다.
- 한 액터의 요청과 통지 수신을 한 줄에 섞어 쓴다.
- 시간 트리거 액터나 서비스 안의 구성요소를 연동 정의의 액터로 올린다.
- 방향을 호출을 받는 쪽 기준으로 쓴다.
- 장애 시 동작에 재시도를 쓰거나, 진행하는지 막는지를 빠뜨린다.
- 재시도·한도의 숫자, 비용, 업체 이름을 입력에 없는데 쓴다.
- 해당 없는 칸을 `—`나 빈 칸으로 둔다.
- 설정·키 관리에 실제 키나 비밀 값을 쓴다.
- 시간 기반 기능이 이미 정의한 실패 시와 재시도를 이 표에서 다시 정의한다.
- 연동 정의의 칸에 이 단계의 `IC-` ID를 쓴다.
- 입력에 이미 있는 후보를 기능 후보 표에 다시 만든다.
- 심사 신청이나 업체 계약 같은 절차를 `기능 후보`로 둔다.
- 샘플이나 예시의 연동을 값으로 옮긴다.
