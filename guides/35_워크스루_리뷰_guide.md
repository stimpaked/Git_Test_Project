## 1. 입력을 읽는 법

- **기능 트리**(계층·ID·태그 산출물)가 따라갈 대상이다. 행마다 기능 ID, 기능명, 설명, 액터, 저니 단계, 화면, 근거 ID를 본다. 이 단계의 모든 기능 칸은 여기 있는 기능 ID이고 한 글자도 바꾸지 않는다. 기능 트리에 없는 기능을 만들어 쓰지 않는다. 기능 트리가 없으면 쓰기를 멈추고 알린다(공통 가이드 1절).
- **역추적 검증**의 갭 로그와 의도적 제외 목록은 종료 조건의 첫 입력이고, 갭이 있던 기능은 시나리오를 고르는 단서다. 이 산출물이 없으면 해당 조건은 `미정`이다.
- **유저 플로우**의 플로우 ID와 진입점, 이탈점, 분기 갈래, 막다른 길은 시나리오가 지날 길이다. **시나리오 5유형**의 점검표에서 정상이 아닌 네 칸(대안, 예외, 오남용, 복구)은 비정상 경로를 고르는 단서다.
- **화면·UI 상태**의 화면 인벤토리(화면, 사용 액터)와 비정상 상태의 동작은 시나리오가 지나갈 화면과 막혔을 때의 동작이다. **액터 목록**(사람, 비사람)의 액터 ID는 시나리오의 대상이다.
- **목표·가치**의 핵심 가설 가운데 검증 시점이 출시 전 시험인 것은 프로토타입 과제가 확인할 대상이고, 초기 리스크의 대응 방향은 역할 검토 범위에 올릴 항목이다.
- **범위·제약**의 제외 목록과 후속 목록은 발견이 이미 정해진 것인지 가르는 기준이다. **의존성**의 웨이브는 구현을 맡는 역할의 검토 범위다.
- 역할의 검토 범위는 앞 단계 산출물에서 정한다. 규제·정책과 데이터 생애는 법무와 개인정보를 맡는 역할, 보안·어뷰징은 보안, 운영·백오피스는 운영·고객 지원, 수익 모델은 재무, 성장·측정은 마케팅과 데이터, 비기능·품질은 품질 보증, 의존성은 구현, 화면·UI 상태는 화면 설계를 맡는 역할의 범위다.
- **사람이 주는 자료**는 프로토타입 테스트 기록, 역할별 검토 의견, 서명 기록이다. 이 단계에서 에이전트가 만들 수 없는 값은 모두 여기서 온다. 자료가 없으면 5절을 따른다.
- 입력의 ID에 공백이나 괄호가 붙어 있으면 ID 형식에 맞는 부분만 칸에 쓰고 원래 표기는 근거 칸에 적는다.
- 입력에 없는 시나리오, 기능, 역할, 의견은 일반적으로 그럴 것이라는 이유로 만들지 않는다.

## 2. 작성 절차

1. 기능 트리의 기능 수를 센다. 이것이 입력 기능 수다.
2. 워크스루 표를 쓴다. 시나리오를 고르고 시나리오마다 한 행을 쓴다. ID는 `WK-01`부터 부여한다.
3. 역할 검토 표를 쓴다. 역할과 검토 범위를 먼저 쓰고 의견, 검토자, 결과, 일자는 사람이 준 기록에서 옮긴다. ID는 `WR-01`부터 부여한다.
4. 프로토타입 표를 쓴다. 테스트 기록이 있으면 과제마다 한 행이고 ID는 `WP-01`부터 부여한다.
5. 세 표에서 발견을 모아 발견 표에 쓴다. ID는 `WF-01`부터 부여한다. 환류가 필요한 발견은 앞 단계에 알린다.
6. 환류가 반영되면 반영된 기능 트리로 라운드를 올려 2~5를 다시 한다. 마지막 라운드의 신규 발견이 0이 될 때까지 되풀이한다.
7. 라운드, 종료 조건, 집계를 쓴다. 4절의 누락 점검과 완료 체크를 확인한다.

## 3. 항목별 해설

<!-- 해설: 워크스루 -->
### 3.1 워크스루

- 행 하나는 시나리오 하나를 한 라운드에서 한 번 따라간 기록이다. 같은 시나리오를 다음 라운드에 다시 따라가면 라운드를 올려 새 행을 쓴다. 단계마다 한 줄씩 쓰지 않고 시나리오 전체를 한 행으로 쓴다.
- **시나리오**는 대상 액터가 겪는 하루나 한 과제를 시작에서 끝까지 한 문장으로 쓴 이름이다. 하루가 아니어도 된다. 사람 액터마다 시작에서 끝까지의 시나리오를 하나 이상 쓰고, 서비스를 운영하는 역할의 시나리오와 비사람 액터가 시작하는 시나리오(시간, 외부 시스템)도 쓴다. 역추적 검증의 갭이 있던 기능을 지나는 시나리오를 고른다.
- **대상 액터**는 사람 액터 `A-`와 비사람 액터 `X-`의 ID를 주된 액터부터 쉼표로 쓴다. 한 시나리오에 두 액터가 만나면 둘 다 쓴다.
- **플로우**는 시나리오가 지난 플로우 ID를 순서대로 쓴다. 모든 플로우가 한 시나리오 이상에 지나가게 한다.
- **따라간 기능**은 시나리오의 단계마다 필요한 기능을 기능 트리에서 찾아 처음 나온 순서대로 ID를 쓴다. 필요한 기능이 기능 트리에 없는 단계는 기능을 지어 쓰지 않고 비슷한 이름의 기능으로 대신하지 않는다. 그 단계를 끊김으로 쓰고 발견에 올린다.
- **화면**은 시나리오가 지난 화면 ID를 순서대로 쓴다. 화면을 지나지 않는 시나리오(비사람 액터가 시작하는 것)는 `해당 없음`(사유)으로 닫는다.
- **비정상 경로 포함**은 시나리오가 실패, 거부, 대기, 되돌리기, 오남용 중 하나 이상의 단계를 따라갔으면 `예`다. 점검표의 예외와 복구 칸, 비정상 상태를 단서로 비정상 경로를 고른다. 정상 경로만 따라간 시나리오는 표가 이미 잡은 것만 확인하므로 `아니오`로 쓰고 다시 고른다.
- **결과**는 단계마다 기능이 있고, 화면이 있고, 플로우가 다음으로 이어지고, 비정상 상태의 동작이 정해져 있으면 `끊김 없음`이다. 하나라도 막히면 `끊김 있음`이고 발견 표에 그 행을 출처로 하는 행을 쓴다.
- **근거**는 시나리오를 고른 이유가 된 액터 ID, 플로우 ID, 갭을 가리키는 조각으로 시작하고 `;`로 나눈다. 조각마다 참조(ID, 필드 키, `NN <산출물 이름>`)나 출처 유형으로 시작한다.
- 예시(형식 시연, 값이 아님): 사내 휴가 신청 도구라면 시나리오는 직원이 휴가를 신청하고 승인자가 반려해 다시 신청하기까지이고 비정상 경로 포함은 `예`다. 근거는 `09 유저 플로우 FL-02, 반려 분기가 있다; 34 역추적 검증 갭 로그 첫 행`처럼 쓴다. 병원 예약 서비스라면 예약 전날 알림을 보내는 배치가 시작하는 시나리오의 대상 액터는 비사람 액터이고 화면은 `해당 없음`(사유: 사람이 화면을 지나지 않는다)이다.

<!-- 해설: 역할검토 -->
### 3.2 역할 검토

- 행 하나는 역할 하나의 한 라운드 검토다. 역할을 고정 목록에서 고르지 않고 앞 단계 산출물을 맡는 역할마다 한 행을 둔다(1절의 대응). 앞 단계 산출물에 점검할 항목이 없는 역할은 행을 쓰지 않고 그 이유를 종료 조건의 역할별 서명 완료 근거에 쓴다.
- **역할**은 검토를 맡은 역할 이름 하나다. 조직 밖의 자문도 역할로 쓴다.
- **검토 범위**는 역할이 점검할 앞 단계 산출물의 번호와 이름으로 시작하고 점검 대상을 덧붙인다. 리스크의 대응 방향이나 화면처럼 입력이 역할에 맡긴 항목을 빠뜨리지 않는다.
- **의견, 검토자, 결과, 일자**는 사람이 준 검토 의견과 서명 기록에서 옮긴다. 에이전트가 역할의 관점으로 의견을 대신 쓰거나 검토자와 결과를 만들지 않는다. 기록이 없는 칸은 `미정`(확인처: 그 역할의 담당, 담당, 기한)으로 닫는다.
- 결과는 기록을 따른다. 의견이 해결되지 않은 발견을 남기면 `조건부 승인`, 승인할 수 없다는 기록이면 `반려`다. 한 역할의 의견이 둘 이상이면 의견 칸에 한 문장으로 모으고 변경이 필요한 의견은 발견 행으로도 올린다.
- 같은 역할이 다음 라운드에 다시 검토하면 라운드를 올려 새 행을 쓴다. 서명은 역할마다 마지막 라운드의 행으로 판정한다.
- **근거**는 의견과 결과를 받은 기록의 문서와 위치다. `내부 자료: <기록 이름·위치>`로 시작한다.
- 예시(형식 시연, 값이 아님): 어린이 독서 앱이라면 규제·정책을 맡는 역할의 검토 범위는 `23 규제·정책 규제 매핑의 출시 게이트 조건`이고, 스마트 온실 모니터링 서비스라면 구현을 맡는 역할의 검토 범위는 `33 의존성 웨이브`다.

<!-- 해설: 프로토타입 -->
### 3.3 프로토타입 테스트

- 행 하나는 한 라운드에서 맡긴 과제 하나다. 모든 칸은 사람이 진행한 테스트의 기록에서 옮긴다. 가상의 참가자나 결과를 만들지 않는다.
- **과제**는 기록에 적힌 과제를 한 문장으로 옮긴다. **플로우**는 과제가 다룬 플로우 ID, **확인 가설**은 그 과제가 확인하려던 핵심 가설 ID다. 기록이 가설을 말하지 않으면 `미정`이다.
- **참가자 수**와 **완료 수**는 기록의 숫자다. 완료 수는 참가자 수 이하이고 완료의 기준은 기록을 따른다. 도움을 받아 끝낸 경우는 찾지 못한 것에 쓴다.
- **찾지 못한 것**은 서비스에 있는데 참가자가 찾지 못하거나 헤맨 지점이다. **기대했으나 없던 것**은 프로토타입에 없는데 참가자가 있을 것으로 기대한 것이다. 둘 다 발견 행으로 올린다. 기록이 없다고 밝힌 칸은 `해당 없음`(사유: 기록에 없다고 적혀 있다)으로 닫는다.
- **근거**는 테스트 기록의 문서와 위치다.
- 예시(형식 시연, 값이 아님): 병원 예약 서비스라면 과제는 `예약을 잡고 취소하기`이고 찾지 못한 것은 `취소 버튼의 위치`다. 사내 휴가 신청 도구라면 `승인 상태 확인하기` 과제에서 기대했으나 없던 것은 `대리 승인자 지정`처럼 쓴다.

<!-- 해설: 발견 -->
### 3.4 발견

- 행 하나는 발견 하나다. 결과가 끊김 있음인 워크스루, 변경이 필요한 역할 의견, 프로토타입의 찾지 못한 것과 기대했으나 없던 것을 한 번씩 올린다. 같은 일을 둘 이상의 수행이 냈으면 **출처**에 행 ID를 모두 쉼표로 쓰고 행은 하나로 쓴다.
- **조치 유형**은 아래 질문을 순서대로 따지고 먼저 맞는 쪽을 쓴다.
  1. 범위·제약의 제외 목록이나 후속 목록이 이미 정한 것을 다시 제안했거나 확인 결과 바꿀 것이 없다. `변경 없음`이고 근거에 그 목록의 ID를 쓴다. 문제없다는 단순한 확인은 발견이 아니라 역할 검토의 의견에 쓴다.
  2. 기능 트리에 필요한 기능이 없다. `기능 추가`다.
  3. 기능은 있는데 조건이나 범위가 모자라 보강이 필요하다. `기존 기능 보강`이다.
  4. 기능은 있는데 액터, 화면, 플랫폼, 저니 단계 가운데 틀리거나 빠진 것이 있다. `태그 수정`이다.
  5. 기능이 필요 없다. `기능 삭제`다.
  6. 문제가 기능 트리가 아니라 앞 단계 산출물(플로우, 화면, 액터, 범위)에 있다. `상류 단계 환류`다. 범위 밖으로 보이는 제안은 기능 추가로 올리지 않고 이 유형으로 쓰고 사용자에게 알린다. 범위의 결정은 사람이 한다.
- **대상 기능**은 조치가 닿는 기능 ID 하나다. 기능 추가는 새 기능 ID를 기능 트리가 붙이므로 반영 전에는 `미정`(확인처: 계층·ID·태그 담당, 담당, 기한)이고 반영 뒤에 붙은 ID로 고친다. 상류 단계 환류처럼 대상이 기능 하나가 아니면 `해당 없음`(사유)이다.
- **조치**는 한 문장이다. 기능 추가는 기능의 대상과 동작, 보강은 보강할 조건, 태그 수정은 바꿀 태그와 값, 삭제는 사유, 환류는 앞 단계에서 고칠 것, 변경 없음은 확인한 결과와 이유를 쓴다.
- **환류 대상**은 조치가 되돌아가는 앞 단계의 번호와 이름이다. 기능 추가, 태그 수정, 기능 삭제는 계층·ID·태그다. 보강은 설명을 고쳐야 하면 계층·ID·태그이고 수용 조건만이면 `해당 없음`(사유: 이 체계 밖의 명세 단계가 받는다)이다. 변경 없음은 `해당 없음`(사유)이다.
- **반영 상태**는 환류가 받는 산출물에 반영되고 그 산출물의 버전이 올랐으면 `반영함`이다. 아직이면 `반영 대기`다. 변경 없음은 `해당 없음`(사유: 바꿀 것이 없다)이다. 환류가 일어나면 앞 단계 산출물의 버전을 올리고 결정 로그에 기록한다(정의서 10절).
- **근거**는 발견의 근거가 된 앞 단계 산출물의 항목과 위치다. 첫 조각은 그 항목의 ID나 `NN <산출물 이름>`으로 시작한다.
- 예시(형식 시연, 값이 아님): 사내 휴가 신청 도구에서 반려 뒤 다시 신청하는 기능이 기능 트리에 없으면 조치 유형은 `기능 추가`, 대상 기능은 `미정`, 환류 대상은 `32 계층·ID·태그`다. 어린이 독서 앱에서 보호자 동의 화면이 화면 인벤토리에 없으면 `상류 단계 환류`다.

<!-- 해설: 라운드 -->
### 3.5 라운드

- 행 하나는 라운드 하나다. 라운드는 세 방법을 수행하고 환류를 반영하는 한 바퀴다. 라운드 1은 처음 수행이고 다음 라운드는 환류가 반영된 기능 트리에서 한다.
- **수행**은 그 라운드에 수행한 워크스루, 역할검토, 프로토타입 행의 ID를 쉼표로 쓴다. 세 표의 라운드 칸과 일치해야 한다.
- 숫자 칸은 발견 표를 라운드로 세어 쓴다. **신규 발견 수**는 변경 없음이 아닌 발견의 수이고 기능 추가 수부터 상류 단계 환류 수까지의 합과 같다. 0도 `0`으로 쓴다.
- 근거는 `35 워크스루 리뷰 4번 표`처럼 센 표를 가리키는 참조로 시작한다.

<!-- 해설: 종료조건 -->
### 3.6 종료 조건

- 판정은 `충족`이나 `미충족`이다. 판정에 필요한 기록이 없으면 `미정`이다.
- **역추적 갭 소진**은 역추적 검증의 갭 로그에 조치가 끝나지 않은 갭이 없으면 충족이다. 의도적 제외로 닫은 것은 열린 갭이 아니다.
- **워크스루 끊김 소진**은 마지막 라운드의 워크스루가 모두 끊김 없음이면 충족이다.
- **발견 반영 완료**는 변경 없음이 아닌 발견이 모두 반영함이면 충족이다. 반영 대기가 있으면 미충족이다.
- **신규 발견 포화**는 마지막 라운드의 신규 발견 수가 0이고 그 라운드가 워크스루, 역할 검토, 프로토타입을 모두 수행했으면 충족이다. 라운드가 하나뿐이고 신규 발견이 있으면 미충족이다. 역할 검토나 프로토타입의 기록이 `미정`이면 이 조건도 `미정`이다. 프로토타입을 `해당 없음`으로 닫았으면 그 방법은 수행 대상에서 뺀다.
- **역할별 서명 완료**는 역할마다 마지막 라운드의 행에서 결과가 승인이면 충족이다. 조건부 승인이나 반려가 하나라도 있으면 미충족이고 결과가 `미정`인 역할만 남으면 `미정`이다.
- **종료 판정**은 다섯 조건이 모두 충족이면 충족이고 하나라도 미충족이면 미충족이다. 미충족은 없고 `미정`이 있으면 `미정`이다.
- 단일 오너의 기준선 선언과 변경요청 절차는 여기에 쓰지 않는다. 우선순위·릴리스 단계가 기준선으로 선언한다.
- 근거는 판정에 쓴 표와 행(집계 칸, 행 ID)을 가리키는 참조로 시작한다.

<!-- 해설: 집계 -->
### 3.7 집계

- 숫자는 표의 행을 세어 쓴다. 근거는 센 표를 가리키는 참조(`35 워크스루 리뷰 1번 표`처럼 `NN 산출물 이름`)로 시작한다. 0도 `0`으로 쓴다.
- 입력 기능 수와 닿은 기능 수와 닿지 못한 기능 수는 기능 트리에서 센다. 닿은 기능 수는 서로 다른 기능 ID의 수이고 닿은 기능 수와 닿지 못한 기능 수의 합은 기능 트리의 기능 행의 수와 같다.
- 역할 수는 서로 다른 역할의 수이고 역할마다 마지막 라운드의 행으로 네 결과 수를 센다. 네 수의 합은 역할 수와 같다.
- 프로토타입 과제 수는 과제가 값인 행만 센다. 기록이 없어 `미정`으로 닫은 행은 세지 않는다.
- 여섯 조치 유형 수의 합은 발견 수와 같다. 발견이 없어 한 줄 `해당 없음`으로 닫았으면 발견 수는 0이다.
- v1.0 후보 기능 수는 입력 기능 수에 기능 추가 수를 더하고 기능 삭제 수를 뺀 수다. 반영 대기가 있어 기능 트리의 현재 행 수와 다르면 근거에 차이를 쓴다.

## 4. 누락 점검

- 모든 사람 액터와 운영 역할이 한 시나리오 이상의 대상 액터인가. 비사람 액터가 시작하는 시나리오가 있는가.
- 모든 플로우가 한 시나리오 이상에 지나갔는가.
- 시나리오마다 비정상 경로를 하나 이상 따랐는가. 비정상 경로 없는 워크스루 수가 0인가.
- 닿지 못한 기능에 시나리오가 빠졌다는 신호는 없는가. 닿지 못한 기능은 시나리오를 더 쓰거나, 근거 ID가 운영이나 규제의 직접 근거인지 본다.
- 역추적 검증의 갭이 있던 기능을 지나는 시나리오가 있는가.
- 첫 라운드에서 발견이 0이면 시나리오 수와 비정상 경로를 다시 본다. 발견이 0이라는 사실만으로 충족을 쓰지 않는다.
- 기능이 처음 후보로 나온 단계를 통합·정규화의 병합 후보에서 거슬러 센 분포를 읽는다. 이 단계에서 새로 나온 기능이 많으면 앞 단계의 도출이 얇았다는 신호이므로 사용자에게 알린다. 분포는 표로 쓰지 않는다.
- 앞 단계 산출물 중 맡는 역할이 없는 것은 없는가. 역할의 행이 마지막 라운드까지 이어지는가.
- 기능 추가가 의존성 단계의 웨이브 행도 필요로 한다는 것을 알렸는가.

## 5. `미정`·`해당 없음` 판단

- **사람이 주는 자료가 없을 때**: 역할 검토의 의견, 검토자, 결과, 일자와 프로토타입의 모든 칸을 `미정`(확인처: 기록을 가진 담당 역할, 담당, 기한은 이 문서의 완료 전)으로 닫는다. 프로토타입은 ID `WP-01`과 라운드를 쓰고 나머지를 같은 `미정`으로 한 줄에 닫는다. 이 기록이 필요한 종료 조건과 종료 판정도 `미정`이다. 에이전트가 의견, 서명, 테스트 결과를 대신 쓰지 않는다.
- **선택지 칸, ID 칸, 날짜 칸, 숫자 칸**: 값을 모르면 추측하지 않고 `미정`(확인처·담당·기한)으로 닫는다.
- **칸의 일부만 모를 때**: 아는 값에 `미정`을 이어 쓴다. 검토자 이름은 아는데 일자를 모르면 이름은 이름 칸에, 일자 칸을 `미정`으로 쓴다. 따라간 기능 가운데 일부만 알면 아는 ID 뒤에 `미정`을 잇는다.
- **`해당 없음`**: 닫힌 목록이 개념을 배제할 때만 쓴다. 프로토타입을 만들지 않기로 한 결정을 입력이 보여 주면 프로토타입 표를 한 줄 `해당 없음`(사유)으로 닫는다. 기능 트리와 범위 목록을 닫힌 목록으로 본다. 입력에 언급이 없다는 사실만으로는 `해당 없음`이 아니다.
- 발견이 하나도 없으면 발견 표는 한 줄만 쓴다. ID 칸에 `WF-01`을 쓰고 나머지 칸은 `해당 없음`과 같은 사유(점검한 표에서 발견이 없다)로 닫는다. 이 줄은 발견이 아니므로 집계에서 세지 않는다.
- 입력이 얇아 `미정`이 많아지는 것은 구조의 결함이 아니다. 칸을 줄이려고 행을 합치거나 생략하지 않는다.

## 6. 흔한 실수

- 가상의 참가자, 역할 의견, 서명, 테스트 결과를 만든다. 기록이 없으면 `미정`이다.
- 정상 경로만 따라간 시나리오로 끊김 없음을 쓴다.
- 기능 트리에 없는 기능 ID를 쓰거나 필요한 기능이 없는데 비슷한 이름의 기능으로 대신한다.
- 기능 추가의 대상 기능에 새 기능 ID를 직접 만들어 쓴다.
- 문제없다는 확인까지 모두 발견 행으로 올리거나 변경이 필요한 의견을 의견 칸에만 쓴다.
- 범위 밖으로 보이는 제안을 기능 추가로 올린다.
- 포화를 기능 추가만 세어 판단하거나 라운드 하나에서 한 방법만 다시 수행하고 충족을 쓴다.
- 단일 오너 선언이나 변경요청 절차를 종료 조건에 쓴다.
- 라운드 표의 수가 발견 표를 세어 맞지 않는다.
- 샘플이나 예시의 시나리오, 기능, 역할을 값으로 옮긴다.
- 근거 칸을 설명 문장으로 시작한다. 맞는 모양은 `내부 자료: 검토 기록 2쪽, 입력에 언급 없음`처럼 쉼표로 이어 쓰는 것이고 틀린 모양은 `내부 자료: 검토 기록 2쪽; 입력에 언급 없음`이다.
